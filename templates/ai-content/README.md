# AI 콘텐츠 신규 작성 템플릿

- 개발 건: `AI-BLOG`. 글·Fragment 틀은 ABT01 사용자 통과(`0fdfab2`), 카테고리·프로젝트 틀은 ABT02 사용자 통과(`f0f58ca`). 개발 브랜치 push 완료.
- 판단 기준: [AI 콘텐츠 작업 규약](../../docs/guide/AI-콘텐츠-작업규약.md)
- 요청·인계·보고: [AI 콘텐츠 작업 지시문](../../docs/guide/AI-콘텐츠-작업지시문.md)
- 예시와 실제 계약의 검사·한계: [검증 결과](../../docs/guide/AI-콘텐츠-검증결과.md)

이 폴더는 새 글·새 Fragment·카테고리·프로젝트 이력의 작성 틀이다. 콘텐츠 수집 경로 밖에 있으므로 템플릿 자체는 공개 글이나 카드로 수집되지 않는다. 기존 `src/content/blog/templates/index.md` 공개 예제는 그대로 보존한다.

## 1. 파일 선택

| 파일 | 신규 작성 대상 | 실제 저장 위치 |
| --- | --- | --- |
| [글 템플릿](./blog/index.md) | 배경·설명·예시·정리를 담는 글 | `src/content/blog/<확정한 폴더>/index.md` |
| [Fragment 템플릿](./fragment.md) | 한 개념의 요약·보충 설명·관계 | `src/content/fragments/<고정 ID>.md` |
| [카테고리 템플릿](./category.json) | 등록할 키와 색상 한 쌍 | `src/consts.ts`의 `CATEGORIES` 객체 |
| [프로젝트 이력 템플릿](./project.json) | 소개 페이지의 프로젝트 항목 하나 | `src/consts.ts`의 `PROJECTS` 배열 |

JSON 틀은 항목 값의 전달용이다. 앱이 이 파일을 자동으로 읽는 기능을 추가하지 않았으며, 실제 반영 위치는 위 표의 현행 원본이다. 전체 CATEGORIES·PROJECTS를 이 틀로 교체하지 않는다.

## 2. 사용 순서

1. 사용자 요청과 원본을 조회해 기존 대상·제목·별칭 후보를 먼저 확인한다. 이 틀은 신규 작성용이다. 기존 항목 수정에서는 실제 원본의 요청된 부분만 바꾸며 템플릿 전체로 덮어쓰지 않는다.
2. 사용할 경로·본문·메타데이터·자산·공개 범위를 확정한다. 원래 요청 식별자와 확정 입력을 인계 기록에 보존한다.
3. 치환 표시를 확정 값으로 채워 별도의 콘텐츠 파일 또는 항목 변경안을 준비한다. 템플릿 원본은 그대로 유지한다. 문자열의 따옴표·줄바꿈은 YAML·JSON에 맞게 작성한다.
4. 사용하지 않는 선택 본문 절은 입력 확정 단계에서 정리하고, 확정 뒤에는 같은 본문을 재사용한다. 빈 절을 채우려고 사실·출처·성과를 만들어내지 않는다.
5. 남은 치환 표시, 필수 정보, 실제 이미지, 등록 카테고리, 고정 ID와 전체 관계를 확인한다. 관련 검사·사용자 판정·저장은 공통 규약을 따른다.

`{{...}}`는 바꿀 값을 표시하는 문법이다. 자동 치환 프로그램이나 템플릿 엔진을 추가한 것이 아니다. 치환하지 않은 날짜·ID는 현행 스키마에 맞지 않으므로 원본을 그대로 콘텐츠 경로에 복사해 빌드하거나 저장하지 않는다.

문자열 값에 따옴표가 있으면 다음처럼 올바르게 표현한다. 원문을 손실 없이 보존하며 값을 단순히 이어 붙여 새 frontmatter 키를 만들지 않는다.

```yaml
title: "주소: \"변환\""
```

## 3. 치환할 값

| 표시 | 대상 | 확정할 내용 |
| --- | --- | --- |
| `{{TITLE}}` | 공통 | 사용자 요청과 내용에 맞는 제목. 제목을 대상 ID로 사용하지 않음 |
| `{{CATEGORY}}` | 공통 | 현재 `CATEGORIES`에 등록된 키. 기존 미등록 값 이관과 신규 등록은 별도 작업 |
| `{{DESCRIPTION}}` | 글 | 카드·검색에 사용할 한 줄 설명 |
| `{{PUB_DATE}}` | 글 | 한 번 확정한 `YYYY-MM-DD` 발행일. 매 실행 시 현재 날짜로 바꾸지 않음 |
| `{{INTRO}}` | 글 | 글의 질문·목적·다룰 범위 |
| `{{CONTEXT}}` | 글 | 독자가 알아야 할 배경과 조건 |
| `{{DETAILS}}` | 글 | 근거에 맞는 핵심 설명 |
| `{{EXAMPLE}}` | 공통 | 코드·사례·검증 결과·그림 등 확정한 예시. 실행하지 않은 예시는 설명용으로 구분 |
| `{{TAKEAWAYS}}` | 글 | 배운 점·결과·남은 제약 |
| `{{FRAGMENT_ID}}` | Fragment | 기존 조회 후 한 번 정한 영문 소문자·숫자·하이픈 ID |
| `{{SUMMARY}}` | Fragment | 해당 개념을 짧고 독립적으로 설명하는 요약 |
| `{{EXPLANATION}}` | Fragment | 개념의 보충 설명과 적용 조건 |
| `{{RELATION_NOTES}}` | Fragment | 선택한 관계의 의미·방향 설명. 관계가 없으면 이 절을 입력 확정 전에 제외 가능 |
| `{{SOURCES}}` | 공통 | 사용자 자료와 확인한 출처를 본문에 기재. 확인하지 못한 사실은 구분 |
| `{{CATEGORY_KEY}}` | 카테고리 | 기존 키 후보를 확인한 뒤 확정한 등록 키 |
| `{{CATEGORY_COLOR}}` | 카테고리 | 확정한 색상 문자열. 실행마다 임의 색을 고르지 않음 |
| `{{PROJECT_NAME}}` | 프로젝트 | 실제 소개할 프로젝트 이름 |
| `{{PROJECT_DESCRIPTION}}` | 프로젝트 | 무엇을·왜 했는지 사용자가 제공한 사실에 맞게 설명 |
| `{{PERIOD}}` | 프로젝트 | 제공된 기간. 없으면 신규 항목에서 이 선택 필드를 제외 |
| `{{ROLE}}` | 프로젝트 | 제공된 역할. 없으면 신규 항목에서 이 선택 필드를 제외 |
| `{{PROJECT_LINK}}` | 프로젝트 | 확인한 GitHub·데모 URL. 없으면 신규 항목에서 이 선택 필드를 제외 |

템플릿에 있는 배열은 신규 항목의 시작값이다. `tags`, `aliases`, `relations`가 필요하면 확정한 내용으로 채운다. 기존 항목을 수정하면서 템플릿의 빈 배열로 원래 값을 지우지 않는다.

## 4. 글의 저장과 이미지

글의 필수 frontmatter는 `title`, `description`, `category`, `pubDate`다. `readingTime`이 필요하면 확정한 문자열로 추가하고, 필요 없으면 생략한다. 요청 식별자·승인·기준 SHA·출처 목록을 새 frontmatter 필드로 넣지 않는다.

기본 `draft: true`는 준비 중인 새 글의 초기 공개 상태다. 로컬에서도 목록·검색·상세 페이지에 나오지 않으며 초안도 스키마 검증을 받는다. 공개가 확정되면 별도 판정 범위에 맞춰 `draft: false`를 적용한다. 재실행에서 공개 여부를 임의로 바꾸지 않는다.

이미지는 실제 글의 `index.md`와 같은 폴더에 두고 Markdown 상대 경로로 참조한다. 이미지가 없는 글에는 예시 파일이나 깨진 이미지 링크를 덧붙이지 않는다.

```text
src/content/blog/<확정한 폴더>/
  index.md
  diagram.png
```

```markdown
![그림이 설명하는 내용을 작성](./diagram.png)
```

이미지 본문은 확정한 `{{EXAMPLE}}` 등의 위치에 넣을 수 있다. 파일 내용과 경로·설명을 함께 인계하고 실제 파일 존재 여부와 빌드 결과를 확인한다. Obsidian 위키 이미지 문법이나 글 폴더 자산을 직접 가리키는 HTML img 대신 Markdown 이미지 문법을 사용한다.

## 5. Fragment의 ID와 관계

Fragment 필드는 `id`, `title`, `summary`, `category`, `aliases`, `tags`, `relations`이며 본문은 frontmatter 뒤에 둔다. 현재 Fragment에 `draft`·`pubDate`·`readingTime` 필드를 추가하지 않는다. 출처는 본문에 적는다.

저장소 신규 작업은 `{{FRAGMENT_ID}}`와 파일명을 같은 고정 ID로 정한다. 기존 UUID ID는 수정 시 유지하고 제목 변경으로 파일을 옮기지 않는다. 웹 신규 화면에서는 ID를 직접 정할 수 없으므로 템플릿의 내용을 폼에 사용하되 실제 저장 결과의 UUID·경로를 인계한다. 특정 ID가 필요하면 저장소 작업으로 수행한다.

관계 대상이 실제로 있고 연결이 확정된 경우에만 `relations`를 채운다. 다음 ID는 형식 설명용이며 운영 카드가 아니다.

```yaml
relations:
  - target: "existing-card-id"
    type: prerequisite
```

유형은 `related`, `prerequisite`, `part-of`, `contrasts` 중 하나를 사용한다. 선행 관계의 대상은 먼저 알아야 할 개념이고, 상위 관계의 대상은 이 카드가 속하는 개념이다. 같은 두 카드 사이에 방향·유형만 바꿔 중복 연결하지 않고 양쪽 파일에 관계를 복제하지 않는다. 관계 설명 본문과 실제 `relations`가 서로 맞는지 확인한다.

Fragment의 초안은 frontmatter 플래그가 아니라 작성 경로와 브랜치로 구분한다. 웹은 `fragments-draft`, 저장소 작업은 확인한 개발 브랜치의 준비·검토 절차를 따른다. 저장 결과와 운영 발행·배포 결과를 구별한다.

## 6. 카테고리의 신규·수정 대상

1. `CATEGORIES`에서 정확한 키와 대소문자·공백이 비슷한 후보를 조회한다. 키와 확정한 색상이 이미 같으면 변경 없음이다.
2. 신규 요청인데 같은 키에 다른 색상이 있으면 충돌이다. 색상 수정 요청으로 임의 전환하거나 비슷한 새 키를 추가하지 않는다.
3. 수정 요청은 기존 키·색상·기준 상태와 바꿀 색상을 기록한다. 적용 직전 다시 대조하며 다른 변경을 덮어쓰지 않는다.
4. 등록할 키·색상 한 쌍만 현재 객체에 반영한다. 예시 JSON을 CATEGORIES 전체로 대체하거나 다른 등록 키를 지우지 않는다.
5. 키 이름 변경과 콘텐츠 값 이관은 별도 요청으로 구분한다. 기존 `Infra` 카드처럼 미등록 값을 관련 없는 수정에서 자동 정리하지 않는다.

색상은 표시를 바꾸는 값이다. 실제 색을 정하는 작업에서는 저장소의 시안·캡처 절차를 따른다. 이번 틀은 치환 표시만 제공하며 사이트 색상을 바꾸지 않는다.

## 7. 프로젝트 이력의 신규·수정 대상

프로젝트 틀은 현행 `ProjectItem` 항목 하나다. 필수 값은 `name`, `description`, 선택 값은 `period`, `role`, `highlights`, `stack`, `link`다. 신규 항목에서 근거가 없는 선택 문자열은 해당 필드를 제외한다. 배열은 확정한 사실로 채우고, 성과 수치·기술·주소·기간을 만들어내지 않는다.

1. 신규 요청 전에 이름·기간·역할·링크와 실제 항목 내용을 조회한다. 같은 항목·같은 내용이면 변경 없음이며 같은 이름의 다른 프로젝트도 후보로 구분한다.
2. 후보가 여러 개이거나 같은 항목에 다른 내용이 있으면 원래 항목과 차이를 보여주고 대상을 확정한다. 신규 요청을 임의 수정으로 바꾸지 않는다.
3. 수정에는 원래 이름·기간·역할·링크·전체 값과 기준 상태를 요청서의 `target.selector`·`baseline`에 기록한다. 이 식별 정보를 프로젝트 객체의 새 필드로 넣지 않는다.
4. 배열 순번만으로 대상이라고 판단하지 않는다. 다른 항목 삽입·정렬 뒤에도 원래 값을 대조하고 요청한 부분만 수정한다.
5. 이름이나 기간을 수정하면 원래 항목으로 대상을 찾고 그 항목 안에서 값을 바꾼다. 새 항목을 추가해 원래 이력을 중복시키지 않는다.
6. JSON 틀을 기존 항목 전체에 덮어쓰지 않는다. 수정에서 생략한 선택 값·성과·기술은 유지하고, 비우거나 제거하는 명시적 요청만 반영한다.

현재 `ProjectItem`에는 ID가 없으므로 `id`·요청 식별자·출처·승인을 임의 필드로 추가하지 않는다. 사용자 자료와 승인·조회 결과는 요청서·인계 기록에 보존한다. 기존 배열을 재정렬하는 작업도 별도 범위로 구분한다.

프로젝트 이력은 소개 페이지 데이터이고 개발 작업 로그와 다르다. 현재 웹에는 카테고리·프로젝트 관리 화면이 없으므로 웹 전용 AI는 확정 자료를 저장소 작업으로 인계한다.

## 8. 확인 범위

ABT01은 글·Fragment의 파일 틀과 사용 안내를 제공했고 YAML·필드·치환 표시·수집 경로와 실제 빌드를 확인했다. ABT02는 JSON 문법과 카테고리 키·색상 형태, 현행 ProjectItem의 필드·타입, 치환 표시 안내를 확인한다. 채운 데이터의 유효·무효 계약 검사와 격리 재실행 증거는 ABV01·ABV02에서 다룬다.

## 9. 자동화 도구용 요청 예시

ACTC02의 [operation-request.example.json](./operation-request.example.json)은 인계용 YAML과 구별한 기계 입력 예시다. 콘텐츠 파일로 복사하거나 현행 frontmatter에 넣지 않는다. [요청 계약](../../docs/guide/AI-콘텐츠-요청-계약.md)에서 대응 필드·미지원 범위·계획/기록의 의미를 확인한다. 현재 ACTB01의 [글 신규 생성 CLI](../../docs/guide/AI-콘텐츠-글-생성-CLI.md)를 연결했으며 다른 대상·수정은 후속 구현이다.
