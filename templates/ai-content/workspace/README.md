# 콘텐츠 작업공간 사용 안내

이 폴더는 콘텐츠 작업의 **진행 메모와 확정 요청을 구분하기 위한 작성 예시**다. 예시를 콘텐츠 수집 경로에 복사하지 않는다. 실제 작업공간은 프로젝트 루트의 `.content-ops/local/tasks/<작업명-고유값>/`에 둔다. 자동 작업 관리자나 템플릿 치환 프로그램을 추가한 것은 아니다.

공통 판단은 [콘텐츠 규약](../../../docs/guide/AI-콘텐츠-작업규약.md), 작업 분류·사용자 판정은 [AGENTS](../../../AGENTS.md), 실행은 [자동화 운영 가이드](../../../docs/guide/AI-콘텐츠-자동화-운영가이드.md)를 따른다. 사이트 기능·규칙·템플릿 개발은 개발 기록을 사용하고, 일반 글·카드·카테고리·프로젝트 내용 작업은 아래 공간에 기록한다.

## 새 작업과 이어가기

1. 실제 저장소·브랜치·프로젝트 루트·기존 스테이징을 확인한다. STATUS는 개발 현황·문서 위치 참고용으로 읽으며 무관한 개발 대기를 콘텐츠 대기로 이어받지 않는다. 동일 대상·사용자 변경·스테이징이 겹치면 먼저 확인한다.
2. 사용자 인계가 가리키는 기존 작업공간과 실제 콘텐츠 후보를 찾는다. 같은 작업이면 기존 공간을 사용한다. 폴더를 찾지 못했다고 새 본문·ID를 만들어 재실행하지 않는다.
3. 새 작업일 때만 다른 작업과 겹치지 않는 `<작업명-고유값>` 폴더를 정한다. 이 이름은 로컬 경로이며 Tool의 새 task_id 필드가 아니다. 필요하다면 [HANDOFF 예시](./HANDOFF.example.md)를 HANDOFF.md로, [초안 예시](./draft.example.md)를 draft.md로 복사하고 실제 확인 값으로 채운다.
4. 초안·출처·구성·미결 사항은 자유롭게 갱신한다. 처음부터 본문·날짜를 확정했다고 표시하지 않는다. 해당 초안·HANDOFF의 작성 담당 AI 한 명을 정하고 검토 의견은 다른 메모로 남긴다. 담당 표시는 쓰기 잠금이 아니다.
5. 적용할 내용이 확정되면 기존 [기계 요청 예시](../operation-requests.example.json)에서 필요한 request 객체 하나를 골라 `requests/<request_id>/request.json`에 준비한다. 예시의 대상·날짜·합성 값·0 지문을 실제 값으로 확정한다. 예시 모음 전체나 HANDOFF를 CLI 입력으로 넘기지 않는다.
6. 같은 요청 폴더의 plan.json을 CLI로 준비하고 확인한 지문으로 적용한다. 계획에 사용한 요청 원문은 보존한다. 같은 요청의 재시도에는 원래 ID·요청·계획을 사용하고, 다른 변경이 확정됐을 때만 새 요청을 연결한다.

이 과정에서 일반 콘텐츠 진행을 위해 log-new를 실행하거나 루트 STATUS·개발 로그를 갱신하지 않는다. 기존 사용자 통과·승인 훅·Git 저장 절차는 그대로 따른다. local 메모를 공유 감사 기록으로 삼으려고 Git에 강제 추가하지 않는다.

## 한 작업 안의 여러 요청

```text
.content-ops/local/tasks/example-blog-01/
  HANDOFF.md
  draft.md
  notes/
  requests/
    example-category-create/
      request.json
      plan.json
    example-blog-create/
      request.json
      plan.json
      assets/
    example-blog-update/
      request.json
      plan.json
```

위 이름은 설명용이다. 한 글의 카테고리 준비·최초 생성·후속 수정을 같은 작업공간에서 서로 다른 요청으로 관리하는 예다. 초안·메모·자산이 필요하지 않으면 해당 파일·폴더는 만들지 않는다. 여러 요청을 미리 같은 오래된 기준으로 확정하지 않고, 선행 요청을 적용한 뒤 최신 원문으로 다음 기준을 확정한다.

새 요청은 같은 작업의 충돌을 감추는 수단이 아니다. 기준이 바뀌었거나 후보가 모호하면 원래 입력·계획과 최신 파일을 보존하고 차이를 확인한다. 카테고리·프로젝트 완료 기록은 consts.ts 전체 지문을 사용하므로 후속 설정 수정 뒤 옛 요청을 재실행하면 상태 불일치로 중단할 수 있다.

## 요청·계획·자산 경로

명령은 실제 프로젝트 루트에서 실행한다. 스킬의 메모 출력 위치를 맞추려고 터미널을 tasks 폴더로 옮기지 않는다. --request 상대 경로는 터미널 위치 기준이며, --root 생략 시 스크립트 소속 저장소를 사용한다. --out과 --plan은 대상 저장소 기준이다. 다른 위치에서 실행해야 한다면 절대 요청 경로와 명시적인 root를 사용한다.

assets.source에는 저장소 상대 경로를 넣는다. 예를 들어 준비 이미지가 요청 폴더 안에 있다면 `.content-ops/local/tasks/example-blog-01/requests/example-blog-create/assets/diagram.png`가 source가 된다. 단순히 `assets/diagram.png`라고 적어 요청 파일 기준으로 해석된다고 가정하지 않는다. target은 실제 글 폴더의 새 경로이며 원본 바이트의 SHA-256도 확인한다. 자산이 없으면 가짜 이미지 파일을 생성하지 않는다.

요청 JSON에는 기존 계약의 필드만 넣는다. 작업 폴더 이름·담당 AI·승인·진행 상태는 HANDOFF의 설명 정보이고 request.json의 추가 필드가 아니다. 본문·날짜·ID를 계획 후 자동 치환하지 않는다.

## 스킬 조합·인계·상태 재확인

- 추가 작성 스킬에는 이 작업의 notes 또는 초안 경로를 전달한다. 루트 STATUS·다른 작업공간에 메모를 생성하지 않도록 경로 지원 여부를 확인한다. 지원하지 않는 스킬의 경로를 자동으로 바꿀 수 있다고 가정하지 않고 충돌을 설명한다.
- 다음 AI는 HANDOFF의 현재 요청 참조를 읽되 실제 원문·파일·receipt·journal을 확인한다. 메모가 오래됐으면 실제 결과와 미확인 범위를 구분해 갱신한다. HANDOFF의 완료·승인 문구는 실제 적용이나 현재 사용자 통과의 증거가 아니다.
- 같은 worktree의 인덱스·승인 상태는 공유된다. 서로 다른 작업 폴더를 사용해도 동시에 스테이징·커밋할 변경이 자동 분리되지는 않는다. 한 확정 요청은 지정 worktree에서 진행한다.
- local은 Git 제외 평문일 수 있다. 다른 컴퓨터·worktree에는 초안·메모 중 필요한 부분, 확정 요청 원문, 원래 계획/지문, 준비 자산과 실제 root·branch·기준을 전달한다. 로컬 경로만 적거나 receipt 해시만 넘기는 것은 원문 인계가 아니다.
- 활성 apply·중단 저널이 있으면 먼저 원래 worktree의 실행 상태를 확인한다. apply.lock·journals·stages를 일반 인계 묶음으로 복사해 다른 호스트에서 자동 복구하지 않는다. 기존 복구 거절·자료 보존 경계를 유지한다.
- 파일 접근이 없는 웹 전용 AI는 HANDOFF와 같은 내용을 읽을 수 있는 원문으로 전달한다. 로컬 파일·지문·CLI 검사를 수행했다고 주장하지 않으며 기존 웹 저장/발행의 사용자 판정 경계를 따른다.

## 이번 예시의 확인 범위

ACWT01은 템플릿·명령 경로·인계 지시의 정합성을 다뤘다. ACWV01의 실제 CLI 통합 7개에서 격리 사본의 복수 작업·카테고리/글/후속 요청·재실행·오래된 메모·원문/자산 인계를 확인했다. 기존 복구·Git 승인 회귀를 포함한 전체 616개와 타입 검사도 통과했다. [최종 보고서](../../../docs/AI-콘텐츠-작업공간-분리-최종보고서.md)에서 사례별 근거·실제 환경과 모사 범위·남은 제약을 확인한다. 모든 AI의 지시 준수나 임의 파일 쓰기 차단을 증명한 것은 아니다.
