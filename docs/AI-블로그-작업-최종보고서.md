## 지금 사용할 수 있는 결과

다른 AI에게 글·Fragment·카테고리·프로젝트 이력 작업을 맡길 공통 판단 기준과 요청·인계·보고 형식을 마련했다. AI가 기존 대상을 찾고 입력을 확정한 뒤 그 내용과 대상·기준을 다음 세션으로 넘길 수 있다. 같은 대상·같은 내용은 변경 없음으로, 다른 내용이나 기준 변경은 충돌로 다루는 절차를 정했다.

평소에는 [AI 콘텐츠 운영 가이드](./guide/AI-콘텐츠-운영가이드.md)에서 시작한다. 상세 원문은 [작업 규약](./guide/AI-콘텐츠-작업규약.md), 복사할 형식은 [작업 지시문](./guide/AI-콘텐츠-작업지시문.md), 실제 파일 형태는 [템플릿 안내](../templates/ai-content/README.md)에서 찾는다. STATUS·AGENTS·CLAUDE는 같은 규약을 가리키고 세션 시작에 STATUS만 읽는 기존 절차를 유지한다.

이번 체계는 확정한 결과의 재사용을 지원한다. 서로 다른 AI가 같은 자연어에서 같은 본문을 만들어낸다거나 모든 작성 경로에서 자동으로 멱등성을 강제한다는 보장은 제공하지 않는다.

상세 재현과 진단은 [템플릿·빌드 결과](./guide/AI-콘텐츠-검증결과.md), [인계·재실행 결과](./guide/AI-콘텐츠-인계-검증결과.md)에 있다. 공통 Verify 워크플로는 `npm test`와 `npm run test:ai-content:build`를 수행하도록 연결했다. 원격 워크플로 성공을 확인한 증거는 아직 없다.

Fragment 재실행은 실제 앱 함수를 파일 기반 모의 API에 연결해 검사했다. 글·카테고리·프로젝트는 규약을 재현한 파일 절차를 검사했다. 실제 AI를 여러 채팅 세션에서 실행한 평가나 일반 콘텐츠 처리 엔진의 자동 보장으로 해석하지 않는다.

화면·작성기·OAuth를 변경하지 않아 브라우저 E2E를 재실행하지 않았다. 실제 OAuth·GitHub 콘텐츠 쓰기·발행·운영 배포도 수행하지 않았다. 이 검증을 위해 운영 데이터를 저장하지 않는다.

## 남은 한계

1. 현재 스키마는 카테고리 등록 여부와 모든 관계 쌍 중복을 검사하지 않는다. 글의 일부 빈 문자열도 통과할 수 있다. 정책 확인은 공통 규약을 따라 별도로 수행한다.
2. 프로젝트 이력에 영구 ID가 없다. 항목 값·이름·기간·역할·링크와 기준 원문을 대조하며 순번이나 이름 하나만으로 수정하지 않는다.
3. 웹 신규 Fragment는 첫 저장 때 UUID가 발급된다. 응답 유실 후 다른 세션이 실제 ID를 모르는 경우의 자동 중복 방지는 검증하지 않았다. 최신 초안 후보·내용 조회와 입력 복구가 필요하다.
4. 웹 발행은 초안 브랜치 전체를 병합하며 대기 목록은 카드만 집계한다. 전체 변경 범위·별도 발행 판정을 AI가 확인해야 한다. 로컬 훅은 웹 쓰기를 검사하지 않는다.
5. 사실·출처·경력·성과의 진위와 문체 품질은 스키마·빌드로 증명하지 않는다. 확정 입력의 지문도 사실성·권한·승인을 증명하지 않는다.
6. 현재 자료는 개발 브랜치에만 있다. 기본 브랜치 반영이 필요하면 최신 기준과 충돌·검증·PR 범위를 별도로 확인한다. 1차 판정은 main 병합·운영 배포 승인으로 해석하지 않는다.

## 최종 판정할 내용

평소 위임을 [운영 가이드](./guide/AI-콘텐츠-운영가이드.md)에서 시작해 규약·요청·템플릿·검증 근거를 찾을 수 있는지, 1차 결과와 자동화 한계가 분명한지가 판정 대상이다. 실제 화면 변화가 없어 브라우저 조작은 필요하지 않다. 자동 검사·문서 차이·저장 증거 대조는 에이전트가 수행한다.
