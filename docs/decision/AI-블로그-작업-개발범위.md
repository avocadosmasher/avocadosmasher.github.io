# AI 블로그 작업 체계의 독립 개발 건과 단계 구분

- 날짜: 2026-10-13
- 개발 건: `AI-BLOG`
- 상태: ABP01 계획과 함께 사용자 통과 — `0b7c84a`, 개발 브랜치 push 완료
- 관련 계획: [AI 블로그 작업 개발계획](../plan/AI-블로그-작업-개발계획.md)

## 문제와 사용자 요청

다른 채팅 세션·AI에게 블로그 작업을 맡길 때 결과가 달라질 수 있다. 사용자는 저장소 직접 수정과 웹 등록 모두를 대상으로 하고, 내부 규정·지시문 추가를 기존 Fragment 작업에 붙이지 말고 새 개발 건으로 진행하도록 요청했다. 개발 절차는 `gated-tdd`를 명시적으로 요청했다.

## 검토한 선택지

| 선택지 | 장점 | 제약 |
| --- | --- | --- |
| 기존 Fragment 계획에 작업 추가 | 기존 흐름과 연결하기 쉬움 | 글·카테고리·프로젝트 이력이 Fragment 기능에 종속되고 작업 ID·완료 범위가 섞임 |
| 규약부터 독립 개발하고 자동화·웹 확장은 후속 합의 | 공통 입력·중복 판단·승인 기준을 먼저 검증하며 작은 단위로 진행 가능 | 규정만으로 모든 경로의 멱등성을 자동 보장하지는 못함 |
| 규약·처리 CLI·웹 관리 기능을 한 번에 구현 | 두 작성 경로의 자동화까지 한 번에 다룸 | 현재 내부 규정·지시문 요청을 넘어 데이터 이관·운영 쓰기·UI·인증 범위가 커짐 |

## 이번 계획의 선택

두 번째 선택지를 제안한다. `AI-BLOG`와 `AB` 작업 ID, `feat/ai-blog-operations` 브랜치로 분리한다. 1차는 공통 규약·AI 진입점·요청 지시문·템플릿·격리 검증까지다. 처리 CLI와 웹 기능 확장은 목표에서 버리지 않고, 별도 합의할 2차·3차 후보로 남긴다.

현재 작업 폴더에는 이번 개발과 관계없는 삭제 3건이 이미 스테이징되어 있다. 이 인덱스를 변경하거나 승인 트리에 섞지 않도록 저장소 내부 `.worktrees/ai-blog-operations/`에 별도 worktree를 만들었다.

시작 기준은 선행 조사에서 확인한 `f2d0081`이다. 로컬 `main`은 오래된 상태이고, 현재 저장된 `origin/main`과도 이력이 갈라져 있어 브랜치를 만들기 위해 기존 작업을 강제로 이동·병합하지 않았다. 신규 변경은 이 기준 이후의 AI-BLOG 작업으로만 관리한다. 이후 PR 준비 시 원격을 갱신하고 실제 `main` 기준에서 기존 Fragment 커밋이 새 변경으로 포함되는지 확인한다. 현재 원격 추적 정보만으로 최신 운영 상태를 단정하지 않는다.

## 현재 동작과 향후 규정의 구분

- 기존 Fragment의 고정 ID·내용 비교·버전 충돌 검사 등은 재사용할 근거다. 새 세션이 같은 개념을 새 ID로 만드는 문제까지 자동 해결한다고 설명하지 않는다.
- 기존 프로젝트 이력에는 ID가 없으므로, 1차 템플릿은 현재 구조에 맞춘다. 새 ID와 데이터 파일 분리는 후속 설계다.
- 기존 미등록 카테고리와 공개 템플릿을 정책 정리라는 이유로 이동·삭제하지 않는다.
- 웹 전용 AI가 지원하지 않는 글·카테고리·프로젝트 관리를 수행한 것처럼 보고하지 않게 한다.
- 웹 저장은 GitHub API 커밋이므로 로컬 승인 훅의 보장 범위와 구분한다. 저장·발행 전에 필요한 판정과 변경 범위를 공통 지시문에 명시한다.
- 문서 단계의 검증은 규약의 일관성과 시나리오 결과에 대한 증거다. 운영 자동화나 배포 인수 완료의 증거로 사용하지 않는다.

## 확인이 필요한 가정

현재 요청의 1차 범위는 내부 규정·지시문 중심으로 해석했다. 사용자가 처리 도구나 웹 기능 구현을 1차 범위에 포함하려면 ABP01 판정 전에 계획과 작업 단위를 조정한다. 기존 M01·M02 판정 상태는 별도 작업이며 이번 개발 시작을 통과 판정으로 해석하지 않는다.

## ABR01에서 확인한 웹 신규 ID의 제약

- 상태: ABR01 사용자 통과 — `8d04158`, 개발 브랜치 push 완료.
- 관찰: 웹 폼에는 ID 지정란이 없고, 첫 저장 시 `draftFromFields`가 UUID를 생성한다. 입력 초안을 유지하는 재시도와 다른 세션에서 신규 카드를 다시 여는 것은 다르다.
- 선택지: 웹 폼에 새 ID 입력 기능을 추가하거나, 현재 화면을 유지하면서 생성 결과의 실제 ID를 인계하거나, 특정 ID가 필요한 작업을 저장소로 넘길 수 있다.
- 이번 선택: 현재 화면을 유지한다. 웹에서는 확정 내용과 기존 후보 조회 결과로 생성 승인을 받고 저장 후 실제 ID·경로를 기록한다. 특정 ID를 요구하면 저장소 작업으로 인계한다. 응답 유실 뒤 세션이 바뀌면 재생성보다 최신 초안 조회를 먼저 한다.
- 근거: 화면 변경은 현재 ABR01 범위를 넘으며, 존재하지 않는 ID 지정 기능을 규정으로 요구하면 웹 전용 AI가 수행할 수 없다. 모든 세션의 자동 중복 방지는 후속 처리 도구에서 다룬다.

## ABI01의 공통 AI 진입점

- 상태: ABI01 사용자 통과 — `fd6d085`, 개발 브랜치 push 완료.
- 선택: 세션 시작에는 STATUS만 읽는 기존 규칙을 유지한다. 작업 범위를 확인한 뒤 AGENTS는 작업 절차, CLAUDE는 프로젝트 구조, 공통 규약은 콘텐츠 판단 기준을 안내한다. 세 파일 모두 같은 규약 원문을 참조한다.
- 검토한 대안: AI별 지침에 전체 콘텐츠 규칙을 복제하면 처음 읽기는 편하지만 수정 시 서로 다른 규칙이 남을 수 있다. 기존 문서를 모두 하나로 합치면 구조 설명과 작업 판정 절차를 찾는 부담이 커진다.
- 이번 근거: 기존 문서 역할을 유지하면서 콘텐츠 규칙은 한 원문으로 연결하면, 다른 AI가 들어와도 동일 기준을 찾을 수 있고 불필요한 전체 문서 읽기를 줄일 수 있다.
- 적용 범위: 개발 계획은 현재 개발 건에 맞춰 선택한다. Fragment 전용 커밋 전략을 모든 새 개발 건의 작업 번호·범위 기준으로 적용하지 않는다. 공통 사용자 판정·Git 훅은 그대로 유지한다.

## ABI02의 공통 요청·인계 형식

- 상태: ABI02 사용자 통과 — `499049c`, 개발 브랜치 push 완료.
- 선택: 공통 요청서와 접근 경로별 짧은 지시문, 확정 입력과 결과를 전달하는 인계 기록, 단계별 완료 보고를 제공한다. 사용자는 자연어 요청과 자료를 주고 AI가 조회 가능한 정보를 채운다.
- 검토한 대안: 대상마다 별도 요청서를 만들면 바로 작성하기 쉽지만 공통 기준·판정·저장 결과 필드가 달라질 수 있다. 자연어 요청만 넘기면 입력은 짧지만 새 세션이 대상·날짜·본문을 다시 선택할 수 있다.
- 근거와 한계: 공통 필드를 두면 원래 요청·대상·결과를 재사용하기 쉽지만 미확정 정보를 조회하는 단계는 필요하다. YAML 형식은 인계용이며 현행 콘텐츠 필드나 자동 처리 프로그램이 아니다. 대상별 실제 파일 템플릿은 다음 ABT01·ABT02에서 추가한다.

## ABT01의 실제 파일 템플릿

- 상태: ABT01 사용자 통과 — `0fdfab2`, 개발 브랜치 push 완료.
- 선택: 콘텐츠 수집 경로 밖의 `templates/ai-content/`에 글 index.md와 Fragment Markdown을 두고, 필수 날짜·카테고리·ID 등은 명시적 치환 표시로 남긴다. 새 글의 시작 공개 상태는 `draft: true`다.
- 검토한 대안: 실제 콘텐츠 폴더에 템플릿을 두면 복사하기 가깝지만 공개 예제와 작성 원본의 역할이 섞인다. 실제 날짜·예시 ID를 기본값으로 넣으면 바로 읽기는 쉽지만 재실행 때 잘못된 값이 그대로 등록될 수 있다.
- 근거와 한계: 치환 전 상태를 실제 콘텐츠로 사용하지 않도록 구분하고 기존 공개 예제를 보존한다. 자동 치환 엔진을 구현하지 않으므로 AI는 확정 입력에 맞게 YAML을 작성하고 남은 표시·문법·실제 자산을 확인해야 한다. 템플릿 전체를 기존 항목에 덮어쓰지 않는다.

## ABT02의 카테고리·프로젝트 값 전달

- 상태: ABT02 사용자 통과 — `f0f58ca`, 개발 브랜치 push 완료.
- 선택: 카테고리는 키·색상 한 쌍, 프로젝트는 현재 ProjectItem 항목 형태의 JSON 틀로 제공한다. 반영 위치는 기존 consts.ts의 객체·배열이며 자동 JSON 로딩은 추가하지 않는다.
- 검토한 대안: TypeScript 설정 전체를 템플릿으로 두면 복사하기 쉽지만 기존 설정과 다른 항목을 덮어쓸 수 있다. 새 프로젝트 ID를 도입하면 식별이 쉬워지지만 현재 타입·표시·기존 데이터 이관 범위가 커진다.
- 근거와 한계: 한 항목 값만 전달해 현행 데이터 계약을 유지한다. 프로젝트 수정에는 이름·기간·역할·링크와 원래 항목 값을 대조하며 순번만으로 식별하지 않는다. 자동 중복 판정·수정 엔진과 ID 이관은 후속 범위다.

## ABV01의 실제 빌드 격리

- 상태: ABV01 사용자 통과 — `9a84ac9`, 개발 브랜치 push 완료. [검증 결과와 한계](../guide/AI-콘텐츠-검증결과.md).
- 선택: 앱 소스의 임시 사본에 합성 콘텐츠만 넣고 실제 빌드를 실행한다. 운영 콘텐츠·Git·환경 파일은 복사하지 않으며 Fragment 관련 빌드 환경변수도 제거한다.
- 검토한 대안: 실제 콘텐츠 폴더에 예시를 넣었다가 지우면 준비는 짧지만 중단 시 원본에 잔여물이 남을 수 있다. 글 로더에 시험 전용 환경변수를 추가하면 격리가 쉬워지지만 운영 코드까지 바뀐다. 스키마만 실행하면 페이지 수집·이미지·초안 제외를 확인하지 못한다.
- 근거와 한계: 원본을 수정하지 않고 현행 수집·렌더링까지 확인한다. 실제 빌드 4건만큼 검사 시간이 늘며 사본·진단 파일은 ignored 폴더에 남긴다. 자동 콘텐츠 등록 도구·실제 외부 연동·모든 작성 정책 강제로 범위를 넓히지 않는다.

## ABV02의 인계·재실행 검증 수준

- 상태: ABV02 사용자 통과 — `f27a2d4`, 개발 브랜치 push 완료. [인계 검증 결과](../guide/AI-콘텐츠-인계-검증결과.md).
- 선택: 기존 Fragment 함수는 파일 기반 모의 API로 재시도·충돌을 확인하고, 다른 콘텐츠는 규약을 따르는 참조 절차와 인계 자료로 검사한다. 운영 쓰기·일반 등록 엔진은 추가하지 않는다.
- 검토한 대안: 모든 대상을 자동 처리하는 함수로 시험하면 적용 재실행이 쉬워지지만 합의한 2차 처리 엔진을 1차에 구현하게 된다. 실제 AI를 여러 세션에서 운영 저장까지 실행하면 범위 밖 쓰기·계정 접근·비결정적 실행이 필요하다.
- 근거와 한계: 기존 자동 보장과 문서 절차를 구별하면서 고정 입력·파일 차이·보존·충돌의 실행 근거를 남긴다. 실제 AI의 지시 준수율이나 웹 미지원 작업 자동 라우팅을 검증했다고 표현하지 않는다.
- 발견과 보완: 요청 ID가 같아도 참조한 입력 파일이 달라질 수 있어 인계에 선택적인 원문 SHA-256 지문을 추가했다. 원문이 같은지 확인하는 자료이며 실제 대상 버전·승인·내용의 사실성을 증명하지 않는다. 지문을 읽을 수 없는 웹 AI는 원문과 미확인 사유를 인계한다.

## ABA01의 운영 시작점과 마감 범위

- 상태: ABA01 최종 사용자 판정 대기. [운영 안내](../guide/AI-콘텐츠-운영가이드.md), [1차 최종 보고서](../AI-블로그-작업-최종보고서.md).
