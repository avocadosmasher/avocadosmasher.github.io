# 결정: 카드 관계의 양방향성

2026-09-24 · 사용자 지적에서 출발: "비교 개념처럼 한쪽만 일방적으로 갖는 관계가 아닌데, 지금은 어떤 관계든 한쪽에서만 등록된다."

## 문제

관계는 **편집한 카드의 파일에만** 한 줄로 저장된다(`A.relations = [{target: B, type}]`). 그런데 이 데이터를 읽는 곳마다 해석이 달랐다.

| 기능 | 양방향으로 다루고 있었나 |
| --- | --- |
| 그래프(`graphData`) | ✅ 어느 쪽에 저장됐든 선을 그리고 이웃 탐색도 양쪽으로 확장 |
| 중복 관계 차단 | ✅ 상대가 나를 가리키면 "이미 연결됨"으로 잠금 |
| 삭제 차단 | ✅ 나를 가리키는 카드가 있으면 삭제를 막음 |
| 카드 팝업 관계 목록 | ❌ 자기 파일의 관계만 |
| 카드 푸터 "N개의 연결" | ❌ 자기 파일의 관계만 |
| 편집 폼 관계 목록 | ❌ 자기 파일의 관계만 → 반대편에서 제거 불가 |

그래서 **"B에서는 그 관계가 보이지도 않는데, B를 지우려 하면 그 관계 때문에 차단되는"** 앞뒤가 맞지 않는 상태였다. 데이터는 이미 엣지 하나로 다루고 있었고, 읽는 화면 세 곳만 한쪽 방향이었다.

## 유형별 검토

양방향으로 **보여야 하는 것은 4개 전부**다. 차이는 "반대편에서 같은 이름이냐, 역 이름이냐"뿐이다.

| 유형 | 저장한 카드에서 | 반대편 카드에서 | 성격 |
| --- | --- | --- | --- |
| `related` | 관련 개념 | 관련 개념 (동일) | 대칭 |
| `contrasts` | 비교 개념 | 비교 개념 (동일) | 대칭 |
| `prerequisite` | 선행 개념 | **후속 개념** | 비대칭 |
| `part-of` | 상위 개념 | **하위 개념** | 비대칭 |

방향 자체는 의미가 있으므로 지우지 않는다. 그래프는 이미 화살촉·선 모양으로 방향을 구분하고 있다(설계 결정기록 6장).

## 선택지

| 안 | 내용 | 버린 이유 / 고른 이유 |
| --- | --- | --- |
| 1. 한 곳 저장 + 양쪽 표시 | 파일은 그대로 두고, 읽을 때 들어오는 관계를 합쳐 역 라벨로 보여준다 | **채택.** 관계는 본래 엣지 하나다. 그래프·중복 검사·삭제 차단이 이미 이 해석으로 동작하므로 나머지를 여기에 맞춘다. 마이그레이션 0, 저장 1회 |
| 2. 양쪽 파일에 기록 | 저장할 때 상대 카드 파일에도 역방향 항목을 쓴다 | 쓰기 2회·커밋 2개, 한쪽만 성공하는 부분 실패, 기존 카드 일괄 마이그레이션, 삭제·되돌리기 로직 2배. 얻는 것은 "파일만 봐도 양쪽에 보인다"뿐 |
| 3. 역방향 유형을 스키마에 추가 | `has-part`·`후속` 같은 역 유형을 만들어 각자 자기 파일에 저장 | 같은 엣지를 두 가지로 표현할 수 있게 되어 정규화 규칙이 필요하다. 유형이 4→6으로 늘고 스키마·그래프·검증이 모두 바뀐다 |

역 이름은 **표시 전용**이다. 저장되는 유형은 그대로 4개이고 카드 파일 형식은 바뀌지 않는다.

## 결정

1. `inverseRelationLabels`(후속 개념·하위 개념)와 `cardRelations(cards, id)`를 `src/lib/fragments.ts`에 둔다. 후자는 **자기 관계 + 들어오는 관계**를 합쳐 돌려주며, 들어오는 항목은 역 라벨과 `inbound: true`를 갖는다.
2. 한 쌍은 한 번만 센다. 어떤 이유로 양쪽에 관계가 있어도 목록에는 하나로 보인다(저장 시점에는 이미 차단되어 있다).
3. 두 단계로 나눠 반영한다.
   - **R01(표시)**: 팝업 목록과 카드 푸터 개수를 양방향으로. 편집 폼은 손대지 않는다.
   - **R02(편집)**: 편집 폼에도 들어오는 관계를 띄우고, 거기서 **제거하면 상대 카드의 파일이 수정**되게 한다. 사용자 선택(2026-09-24): 안내만 하는 대신 반대편에서도 직접 제거할 수 있어야 한다.
4. R02에서는 저장 대상이 다른 파일이 되므로 충돌·권한·응답 유실 복구를 **상대 카드 기준으로 다시 검증**하고, 발행 대기 목록에 상대 카드가 뜬다는 점을 운영 가이드에 적는다.

## 구현에서 드러난 정정 (R02)

"양쪽 파일에 기록"을 버린 이유로 "쓰기 2회·커밋 2개·부분 실패"를 들었는데, 저장 경로는 이미 Git tree → commit → ref 순서로 커밋을 만들고 있었고 **Tree API는 파일 여러 개를 한 번에 받는다.** 그래서 두 카드를 고치는 일도 커밋 하나로 끝나고 절반만 반영되는 상태가 없다.

이 사실이 결정을 뒤집지는 않는다. 복제 저장은 여전히 기존 카드 마이그레이션과 삭제·되돌리기 로직의 이중화를 요구한다. 다만 **"상대 카드를 고치는 것"의 비용은 처음 추정보다 훨씬 낮고**, 그래서 R02의 "반대편에서 제거" 를 같은 커밋 안에서 안전하게 구현했다.

## 영향

- 카드 파일·스키마·기존 데이터 변경 없음. 배포된 카드도 그대로 읽힌다.
- 푸터 숫자가 늘어난다(예: GPA `0개의 연결` → `1개의 연결`). 관계가 사라진 것처럼 보이던 카드가 실제 연결을 보여주는 것이므로 의도된 변화다.
