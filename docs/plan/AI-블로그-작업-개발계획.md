- 개발 건: **AI-BLOG** — AI가 블로그 콘텐츠를 다루기 위한 내부 규정과 지시문
- 등록 작업: **ABP01**, 2026-10-13, 사용자 통과 — `0b7c84a`, 개발 브랜치 push 완료
- 개발 브랜치: `feat/ai-blog-operations`
- 작업 폴더: 저장소 루트 아래 `.worktrees/ai-blog-operations/`
- 시작 기준: `f2d0081`의 코드·문서. 기존 Fragment 개발계획과 작업 ID를 확장하지 않는다.
- 절차: `AGENTS.md`와 사용자가 명시적으로 요청한 `gated-tdd`를 따른다.
- 분리 근거: [독립 개발 건과 단계 구분](../decision/AI-블로그-작업-개발범위.md)

## 1. 해결하려는 문제

다른 채팅 세션이나 AI에게 글 작성, Fragment 추가, 카테고리 추가, 소개 페이지 프로젝트 이력 추가를 맡겨도 저장 위치·필수 정보·중복 판단·검증·발행 기준이 같아야 한다. 현재는 코드와 운영 문서의 규칙이 일부 다르고, 콘텐츠 작업 지시가 여러 문서에 흩어져 있다.

사용자가 선택한 대상은 **저장소를 직접 수정하는 AI와 웹 화면에서 등록하는 AI 모두**다. 현재 웹 작성 기능은 Fragment만 지원하므로, 두 경로의 현재 가능한 작업과 후속 확장을 구분한다.

### 일관성과 멱등성의 구분

- 작성의 일관성: 필수 정보, 문체, 사실·출처 처리, 결과 보고 형식을 공통 규약으로 정한다.
- 등록의 멱등성: 확정된 요청·대상 식별자·내용을 다시 적용했을 때 중복 항목이나 불필요한 파일 변경이 생기지 않아야 한다.
- 동일한 자연어 요청에서 서로 다른 AI가 동일 본문을 생성한다고 보장하지 않는다. 생성된 본문과 메타데이터를 확정한 뒤 재실행 입력으로 보존한다.
- 1차 범위의 규정은 에이전트가 따라야 할 절차다. 모든 작성 경로에서 멱등성을 자동 강제하는 처리 도구가 완성되었다고 표현하지 않는다.

## 2. 현재 동작과 작성 경로

| 대상 | 현재 원본 | 저장소 작업 | 현재 웹 작업 |
| --- | --- | --- | --- |
| 블로그 글 | `src/content/blog/<폴더>/index.md` | Markdown·frontmatter·같은 폴더의 이미지 | 지원하지 않음 |
| Fragment | `src/content/fragments/<id>.md` | 고정 ID와 관계를 보존하여 수정 | 작성·수정·삭제·초안 저장·발행 지원 |
| 카테고리 | `src/consts.ts`의 `CATEGORIES` | 기존 키 조회 후 명시적 추가·수정 | 별도 관리 화면 없음 |
| 프로젝트 이력 | `src/consts.ts`의 `PROJECTS` | 소개 페이지 데이터 수정 | 지원하지 않음 |
| 경력·프로필 | `CAREER`, `PROFILE` 등 | 관련 항목만 수정 | 지원하지 않음 |
| 개발 작업 로그 | `docs/log/`, `STATUS.md` | 개발 작업 기록 절차 | 지원하지 않음 |

프로젝트 이력은 소개 페이지에 표시하는 데이터이고, 개발 작업 로그는 저장소 변경의 검증 기록이다. 요청과 결과 보고에서 둘을 구별한다.

### 조사에서 확인한 불일치

| 관찰 | 계획에 반영할 기준 |
| --- | --- |
| 글 로더는 `**/index.md`인데 운영 가이드는 단일 `.md`도 안내 | 실제 수집 형식과 이미지 경로를 공통 안내로 통일 |
| 문서는 등록된 카테고리를 요구하지만 두 콘텐츠 스키마는 임의 문자열을 허용 | 작성 정책과 자동 검사의 보장 범위를 구별 |
| 기존 Fragment에 미등록 `Infra`가 있음 | 임의 이동·삭제 없이 기존 값 처리 선택지를 정리 |
| 신규 Fragment ID는 기본 UUID이고 제목 중복은 허용 | 기존 후보 조회와 고정 ID 재사용, 모호한 후보 확인 절차 |
| 프로젝트 이력에는 고정 ID가 없음 | 현재는 항목 위치·링크·기간 등으로 대상을 확인; ID 도입은 후속 설계 |
| 웹 저장에는 관계 중복 검사가 있으나 공통 검증 함수가 모든 규칙을 검사하지 않음 | 직접 파일 수정에서도 전체 관계를 확인하도록 안내; 자동 강제는 후속 범위 |
| 템플릿 글이 `draft: false`로 공개됨 | 기존 공개 예제는 보존하고 AI용 템플릿은 콘텐츠 수집 경로 밖에 추가 |
| 웹 저장은 GitHub API 커밋이고 발행은 브랜치 전체 병합 | 저장·발행 모두 변경 범위와 승인 시점을 명시; 로컬 훅이 웹 쓰기를 보장한다고 설명하지 않음 |
| 로그 생성 명령은 실행할 때마다 새 항목 생성 | 중단된 동일 작업은 생성된 항목을 이어서 채움; 재실행을 새 개발 작업으로 중복 등록하지 않음 |

## 3. 이번에 합의할 1차 범위

1. AI가 사용할 공통 콘텐츠 작업 규약을 `docs/guide/AI-콘텐츠-작업규약.md`에 정리한다.
2. `AGENTS.md`·`CLAUDE.md`는 공통 규약으로 연결하고, 기존 운영 문서의 잘못된 안내를 정정한다. 세션 시작에는 `STATUS.md`만 읽는 규칙을 유지한다.
3. 다른 세션·AI에 전달할 요청서와 완료 보고 지시문을 `docs/guide/AI-콘텐츠-작업지시문.md`에 제공한다. 특정 제품이나 도구의 설치를 전제로 하지 않는다.
4. `templates/ai-content/`에 글·Fragment·카테고리·프로젝트 이력 작성용 예시를 둔다. 템플릿이 글로 수집되지 않게 한다.
5. 격리된 예시로 문서·템플릿의 필수 정보와 기존 데이터 계약이 맞는지 확인하고, 신규·수정·재실행·충돌 시나리오를 검증한다.
6. 지원하지 않는 웹 작업은 저장소 작업으로 인계하는 지시를 제공한다. 현재 웹에서 하지 못하는 작업을 완료했다고 보고하지 않는다.

### 반드시 정할 작업 규칙

- 입력: 작업 종류, 신규/수정/삭제 구분, 요청 식별자, 대상 경로·ID, 확정할 내용, 출처, 날짜, 공개 여부, 승인 범위.
- 기존 대상: 경로·ID 우선 조회, 제목·별칭 등은 후보 탐색에 사용. 중복 제목만으로 자동 병합하지 않는다.
- 재실행: 같은 대상·같은 내용이면 변경 없음. 같은 생성 대상에 다른 내용이면 충돌로 보고하고 수정 요청으로 임의 전환하지 않는다.
- 수정: 원래 경로·ID·발행일·관계·요청하지 않은 필드를 보존한다. 기준 버전이 바뀌면 최신 상태를 확인한다.
- 누락 정보: 재실행마다 현재 날짜·임의 색상·새 UUID를 덧붙이지 않는다. 필요한 선택을 확정하고 요청에 남긴다.
- 작성 품질: 사용자가 제공하지 않은 경력·성과를 만들어내지 않는다. 글·Fragment의 설명 수준과 출처 처리 기준을 구분한다.
- 카테고리: 신규 작성은 등록된 키를 사용한다. 기존 미등록 항목의 정리는 별도 합의하며, 빌드 성공을 카테고리 정책 준수로 해석하지 않는다.
- 승인: 저장소 커밋·push와 웹의 GitHub API 저장·발행에 적용되는 사용자 판정 시점을 명시한다. 기능 실행 가능과 실행 권한을 구별한다.
- 개발 로그: 실제 신규 개발 작업의 기록은 기존 완료 절차를 따른다. 중단된 작업 재개와 동일 콘텐츠 재실행은 중복 로그를 만들지 않는다.

## 4. 제외 범위와 후속 단계

이번 1차 범위에서 콘텐츠 처리 CLI, 공통 변경계획 엔진, 신규 웹 관리 화면, OAuth 변경, 데이터 파일 분리, 프로젝트 ID 마이그레이션, 기존 URL 변경을 구현하지 않는다. 운영 콘텐츠·기존 공개 템플릿을 일괄 수정하거나 삭제하지 않는다. 운영 쓰기와 `main` 배포도 포함하지 않는다.

| 후속 단계 | 후보 범위 | 시작 조건 |
| --- | --- | --- |
| 2차: 공통 처리 도구 | 조회·변경 계획·적용·검증 명령, 고정 입력과 충돌·재실행 처리, 공통 스키마 보완 | 1차 규약 검증 후 별도 개발계획과 사용자 합의 |
| 3차: 웹 작성 확장 | 공통 처리 로직을 기존 Fragment 화면에 연결하고 글·카테고리·프로젝트 관리 확장 | 2차 데이터 계약 검증과 실제 연동 최소 실험 후 별도 합의 |

2차·3차를 후보로 기록한 것은 구현·운영 쓰기·배포 승인이 아니다. 두 작성 경로 모두를 다루는 목표는 유지하며, 1차 완료와 전체 자동화 완료를 구분한다.

문서·조사 작업에는 문자열 존재 여부만 검사하는 억지 Red 테스트를 만들지 않는다. 코드가 추가되는 검증 작업은 실제 데이터 계약과 실패 결과를 먼저 검사한다. 검증용 도구가 실제 쓰기 기능으로 확대되면 2차 범위로 분리한다.

## 6. 테스트 계층과 실행 범위

| 계층 | 이번 개발에서의 적용 |
| --- | --- |
| 문서 검사 | 상대 링크, 작업 ID·선행 관계, 대상 위치, 현행 명령과 계획 명령의 구분, `git diff --check` |
| 단위 | 코드 추가 시 기존 스키마·직렬화·ID 유지·실패 진단을 검증; 문서 단계에서 불필요한 테스트를 추가하지 않음 |
| 통합 | 격리 fixture의 유효·무효 콘텐츠, 요청 인계·재실행 차이, 템플릿이 실제 페이지로 수집되지 않는 실제 빌드 확인 |
| 브라우저 | 화면 변경 없는 계획 등록에는 적용하지 않음. 이후 공개 결과 영향이 있으면 빌드 산출물 preview로 확인 |
| 실제 연동 | 1차는 외부 서비스에 쓰지 않음. 로컬 운영 OAuth가 불가능한 점과 웹 저장·발행 검증의 장소·시점을 안내 |
| 배포 인수 | 1차 범위에 없음. 2차·3차가 운영 기능을 포함하면 배포 조건을 별도로 합의 |

기존 기준선 점검에서는 `f2d0081`에서 단위·통합 107개, 타입 검사 오류 0·힌트 5, 프로덕션 빌드 성공을 확인했다. 이는 선행 조사 결과이며 새 변경의 검사 결과를 대신하지 않는다. 이번 ABP01은 문서 변경에 맞는 검사 결과를 별도 로그에 남긴다.

외부 쓰기를 도입하는 후속 단계에서는 위험한 연동을 먼저 격리 환경에서 최소 실험한다. 실제 토큰·운영 저장소에 의존하는 테스트를 기본 검사에 넣지 않는다.

ABV01의 [실행 명령·결과·한계](../guide/AI-콘텐츠-검증결과.md)를 별도로 기록한다. 이 결과는 세션 인계·재실행 검증이나 전체 개발 완료를 대신하지 않는다.

ABV02의 [세션 인계·재실행 결과](../guide/AI-콘텐츠-인계-검증결과.md)는 실제 Fragment 함수 검사와 다른 콘텐츠의 규약 참조 절차를 구별한다. 임의 AI의 자동 지시 준수나 후속 처리 엔진의 완료 증거로 사용하지 않는다.

## 7. 1차 끝의 정의

다음 조건을 모두 충족해야 1차 완료라고 표시한다.

1. 글·Fragment·카테고리·프로젝트 이력의 위치·작성 기준·신규/수정/재실행/충돌 절차가 공통 규약에 있다.
2. 저장소 AI와 웹 전용 AI가 동일 규약을 찾고, 가능한 작업·인계할 작업·승인 시점을 구분할 수 있다.
3. 다른 세션으로 확정 입력·대상 ID·기준 상태·판정 대기를 전달할 요청서와 완료 보고 예시가 있다.
4. 템플릿과 지시문이 현행 코드에 없는 필드·명령·웹 기능을 사용하도록 요구하지 않는다.
5. 격리 시나리오의 결과와 한계를 기록하고, 문서 기반 절차와 자동 강제의 차이를 명시한다.
6. 기존 콘텐츠·URL·기존 작업의 판정을 임의 변경하지 않고 각 작업의 사용자 판정을 받는다.

## 8. 이번 ABP01의 판정 대상

ABP01은 독립 개발 건과 1차 계획을 등록했다. 사용자에게 명시적 `통과` 판정을 받아 `0b7c84a`로 커밋하고 개발 브랜치에 push했다. 이후 작업도 각 작업의 검증·기록·별도 판정을 거쳐 진행한다.

판정할 내용은 개발 건 분리, 1차 범위, 후속 단계의 구분, 끝의 정의다. 화면·운영 동작 변화가 없으므로 브라우저 조작은 필요하지 않다. 자동 검사와 문서 차이는 에이전트가 확인한다.

## 9. ABA01 최종 마감 판정

선행 ABP01~ABV02는 각각 사용자 통과 뒤 개발 브랜치에 저장했다. 마지막 [운영 안내](../guide/AI-콘텐츠-운영가이드.md)와 [1차 최종 보고서](../AI-블로그-작업-최종보고서.md)는 산출물·끝의 정의·검증 증거·한계를 연결한 ABA01 판정 대상이다. 최종 통과 뒤 승인 기록·커밋·개발 브랜치 push를 확인하면 합의한 1차를 마감한다. main 병합·운영 배포나 후속 처리 도구 개발을 자동으로 시작하지 않는다.
