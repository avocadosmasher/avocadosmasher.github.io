## 1. 목표와 이번 판정의 의미

1차는 다른 AI가 따라야 할 규약·지시문·템플릿과 검증 예시를 마련했다. 2차는 그중 프로그램이 판정할 수 있는 규칙을 실제 처리 도구로 옮긴다. 사용자의 후속 진행 요청에 따라 개발 건을 등록했으며, 이 계획에서 범위·실패 기준·데이터 보관·적용 경계를 구체화한다.

저장소 작업을 먼저 구현한다. AI가 확정 요청을 전달하면 도구가 기존 대상과 기준을 확인해 변경안을 만들고, 동일 입력은 변경 없음으로, 다른 입력·동시 수정은 충돌로 처리한다. 글·Fragment·카테고리·프로젝트 이력이 대상이다. 최종 결과는 사람이 검토할 수 있는 로컬 변경이며 도구가 Git 커밋·push·발행을 대신 수행하지 않는다.

이 계획의 통과는 아래 작업 순서와 명시한 선택의 승인이다. 운영 콘텐츠에 시험 데이터를 추가하거나 main에 반영하는 승인은 아니다.

## 2. 현재 조사 결과와 보존 기준

2026-10-15 읽기 전용 조사에서 글 로더 대상 13개, Fragment 3개를 확인했다. 별도 단일 Markdown 1개는 기존 글 로더가 수집하지 않으므로 검사기가 몰래 새 글로 포함하지 않는다.

등록되지 않은 `Infra` 카테고리 사용은 다음 4건이다.

| 대상 | 실제 경로 | 현재 값 |
| --- | --- | --- |
| 글 | `src/content/blog/가상화 파헤치기 인트로/index.md` | Infra |
| 글 | `src/content/blog/가상화 파헤치기-1장/index.md` | Infra |
| Fragment | `src/content/fragments/ept.md` | Infra |
| Fragment | `src/content/fragments/gpa.md` | Infra |

이 4건을 고치거나 새 카테고리로 등록하지 않는다. 검사기의 기존 예외 기준은 **규칙 ID·실제 경로·문제 값**으로 좁혀 버전 관리한다. 같은 파일의 제목만 바꾸면 기존 예외를 보존하고, 다른 파일에 Infra를 새로 쓰면 실패시킨다. 새 예외는 자동으로 추가하지 않는다. 다른 기존 위반이 발견되면 원인과 처리 선택을 먼저 보고하고 기대값을 낮추지 않는다.

현재 Fragment 공통 검증은 필수 필드·중복 ID·없는 관계 대상·자기 참조를 검사한다. 등록 카테고리와 관계 쌍 중복은 별도 검사 보완이 필요하다. 프로젝트는 `src/consts.ts`의 ProjectItem 항목이며 영구 ID가 없다. 기존 배열 순번만으로 수정 대상을 정하지 않는다.

## 3. 사용자에게 제공할 기능

| 기능 | 입력 | 결과 |
| --- | --- | --- |
| 콘텐츠 검사 | 저장소의 현재 또는 제안된 콘텐츠 | 위치·규칙·이유를 포함한 진단, 성공/실패 종료 코드 |
| 변경계획 준비 | 확정 요청·실제 대상·기준 원문 | 생성·수정할 차이 또는 변경 없음·충돌 |
| 로컬 적용 | 확정한 변경계획과 그 지문 | 같은 계획인지·현재 기준이 같은지 확인한 뒤 로컬 파일 반영 |
| 재실행 | 같은 작업 식별자·같은 확정 입력 | 실제 현재 파일까지 대조해 변경 없음 또는 상태 불일치 보고 |
| 기계·사람용 보고 | 검사·준비·적용의 결과 | JSON 결과와 짧은 요약, 확인하지 않은 단계 구분 |

실행 프로그램은 Node.js 기반 CLI로 제공하고 핵심 판단은 별도 모듈로 분리한다. 기존 YAML·Zod·TypeScript 의존성을 먼저 사용한다. 이 계획에는 아직 구현하지 않은 실행 명령을 사용 가능한 명령처럼 제시하지 않는다. 실제 명령 이름과 인자 계약은 ACTC02에서 테스트로 고정한다.

## 4. 입력과 보관할 정보

확정 요청은 `request_id`, 대상 종류, 생성/수정 구분, 실제 대상, 기준 원문/버전, 확정 콘텐츠 또는 변경 필드를 포함한다. 경로가 다르거나 본문·날짜·자산이 바뀌면 같은 입력이라고 취급하지 않는다. 현재 콘텐츠 스키마에 작업 식별자나 승인 필드를 추가하지 않는다.

확정 요청 파일은 도구가 읽을 수 있는 위치에서 명시적으로 전달한다. 사용자는 다음 AI에게 그 원문이나 읽을 수 있는 참조를 넘긴다. 도구가 본문을 생성하거나 빠진 날짜·색상·UUID를 매번 보충하지 않는다. 입력 원문을 잃으면 복구가 필요한 상태로 보고한다.

재시도 기록은 저장소의 `.content-ops/receipts/` 아래에 둔다. 작업 식별자·정규화한 확정 입력 지문·대상 경로·적용 전후 지문·결과만 기록한다. 토큰·승인 비밀값·채팅 원문은 기록하지 않으며 확정 본문 전체를 또 저장하는 용도로 쓰지 않는다. 기록과 해당 콘텐츠 변경은 같은 검토 범위에 포함한다.

잠금·임시 파일·복구 저널은 `.content-ops/local/`에 두고 Git에서 제외한다. 상태 파일은 도구가 관리하지만 사람이 한 통과 판정의 증거로 해석하지 않는다. 다른 컴퓨터에서 재실행하려면 공유된 적용 기록과 확정 요청 원문 모두가 필요하다.

계획 지문은 입력과 변경 내용을 묶고, 대상 파일 지문은 읽어 둔 원문을 가리킨다. 두 지문은 목적이 다르다. 배열 순서·본문·이미지 바이트처럼 의미 있는 차이는 유지하고, 재실행이 변경 없음이면 원본을 정렬·재직렬화하지 않는다.

## 5. 대상별 적용 경계

| 대상 | 신규 생성 | 기존 항목 수정·보존 |
| --- | --- | --- |
| 글 | 확정 경로의 폴더/index.md와 명시한 자산만 준비 | 원래 경로·요청 밖 필드·본문·발행일·자산 보존 |
| Fragment | 호출자가 확정한 안전한 ID 사용, 전체 관계 검사 | 원래 ID·경로 유지, 관계 변경 시 관련 파일도 계획에 포함 |
| 카테고리 | CATEGORIES의 확정 키·색 한 쌍만 추가 | 원래 키와 값 대조, 다른 설정 유지; 키 변경·콘텐츠 일괄 이관 제외 |
| 프로젝트 | 현행 ProjectItem 형태로 한 항목 추가 | 이름·기간·역할·링크와 원래 항목 전체 값 대조; 여러 후보면 중단 |

consts.ts는 TypeScript 구문을 해석해 대상 항목의 필요한 범위만 수정한다. 소스 전체 실행이나 정규식 기반의 전체 설정 교체는 하지 않는다. 지원하지 않는 표현식·동적 값은 추측해 덮어쓰지 않고 진단한다. 영구 프로젝트 ID와 데이터 파일 분리는 이번에 도입하지 않는다.

신규 생성은 명시 대상이 이미 있으면 내용을 비교한다. 다른 경로·다른 ID로 이미 존재할 수 있는 개념의 완전한 의미 중복 판정은 보장하지 않는다. 제목·별칭·프로젝트 후보는 보여주고 모호하면 선택을 요청한다. 작업 식별자를 새로 만들었다는 이유로 기존 조회를 생략하지 않는다.

## 6. 안전한 적용과 승인의 구분

변경계획은 적용할 차이를 보여주는 자료다. 로컬 적용은 사람이 검토할 파일을 만드는 단계이며, Git 저장·push·운영 발행과 구별한다. 사용자는 적용 대상과 확정 계획을 지정할 수 있지만, 명령의 확인 플래그나 JSON의 approved 값만으로 실제 사용자 승인이 증명되지는 않는다.

현재 저장소의 AGENTS.md와 승인 훅은 그대로 유지한다. 명시적 사용자 통과 뒤 승인 기록·커밋·개발 브랜치 push를 수행한다. 새 스킬 버전의 자동 커밋·예산 장치로 훅을 바꾸는 작업은 이번 범위에 포함하지 않는다. 기존 사용자 지시를 스킬 버전 변경으로 완화하지 않는다.

도구 내부의 중복 실행은 잠금과 기준 재확인으로 처리한다. 쓰기 전에 전체 변경안을 검증하고, 적용 중 실패하면 복구 가능한 상태와 실제 변경 범위를 남긴다. 여러 파일에 대해 운영 데이터베이스처럼 완전한 트랜잭션을 보장한다고 주장하지 않는다. 외부 편집기의 동시 쓰기를 포함한 충돌·중단·복구 사례를 검사하고 해결하지 못한 범위는 사용 안내에 명시한다.

외부 쓰기를 구조적으로 통제하는 서버, AI의 파일 쓰기 권한 회수, 사용자만 발급 가능한 승인 서비스는 이번 범위 밖이다. 따라서 이번 도구는 명시한 적용·검사 조건을 강제하지만 모든 AI의 행동 전체를 통제하지 않는다.

## 7. 제외 범위

신규 웹 관리 화면, 기존 웹 작성기의 저장 API 변경, OAuth 변경, 실제 외부 저장·발행·배포, main 병합, 브랜치 보호 설정 변경, 프로젝트 ID 이관, 카테고리 키 변경, 자동 콘텐츠 삭제, 원격 이미지 다운로드는 제외한다. 경력·프로필 전용 수정 어댑터도 이번 대상 네 가지 이후 별도 검토한다.

파일을 삭제하거나 자산을 정리하는 기능은 포함하지 않는다. 자산은 사용자가 제공한 로컬 파일의 명시적 추가를 먼저 지원하고, 기존 경로 덮어쓰기·이동·삭제는 거절한다. 사용자 파일을 자동으로 되돌리는 정리 기능을 만들지 않는다.

## 10. 검증 계층과 끝의 정의

단위 검사는 순수 계약·지문·부분 변경·진단을, 통합 검사는 임시 저장소·실제 파일·CLI·Git 훅을 검증한다. 빌드 검사는 운영 콘텐츠와 분리한 사본에서 수행한다. 화면을 바꾸지 않는 동안 브라우저 디자인 판정은 만들지 않는다. 외부 서비스 쓰기 없이 동작해야 한다.

완료 조건은 다음과 같다.

1. 현재 수집 경로에 맞는 읽기 전용 검사 명령과 명확한 실패 진단이 있다.
2. 기존 예외를 명시적으로 보존하면서 새 카테고리·관계·형식 위반을 차단한다.
3. 네 대상의 확정 요청을 계획·적용하고, 같은 요청의 재실행에서 추가 파일 변경이 없다.
4. 요청하지 않은 값과 기존 경로·ID를 보존하며 입력 충돌·대상 모호성·동시 변경을 거절한다.
5. 중단·복구·잠금·기록의 한계와 실제 발생 상태를 숨기지 않는다.
6. 기존 승인 훅과 공통 CI에서 같은 검사 결과를 사용하며, 승인 절차를 우회하지 않는다.
7. 격리 실제 사용·빌드·회귀 검사와 필요한 사람의 기능 확인, 운영 안내·최종 보고가 있다. 자동 판정 가능한 CLI 흐름에는 수동 실행을 별도로 요구하지 않는다.
8. 운영 콘텐츠·URL·사용자 변경을 임의로 고치지 않으며 main에 직접 반영하지 않는다.

## 11. 이번 ACTP01 판정 대상

이번 변경은 계획·결정 기록·진입점 상태·선행 완료 표기만 추가·갱신한다. 검사기·적용 도구·훅 변경은 아직 구현하지 않는다. 계획의 통과 뒤 ACTV01의 테스트와 구현을 시작한다. 현재 저장소의 기존 사용자 판정·승인 훅을 유지하며 스킬 업데이트를 이유로 자동 커밋 정책을 새로 도입하지 않는다.
