## 1. 결론과 이번 변경 범위

사용자가 서브 에이전트 3개의 검토 결과를 확인하고 **로컬 작업 폴더와 개별 확정 요청을 나누는 보완안**을 채택했다. 루트 STATUS.md 이름은 유지하고 개발 현황과 콘텐츠 진행 기록의 갱신 범위를 분리한다. 글의 기획·초안·후속 수정을 작업 폴더로 묶되, Tool의 request_id는 확정된 개별 변경에 계속 사용한다.

ACWP01은 확정한 구조·작업 순서·완료 기준을 계획과 결정 기록에 반영한 단계다. 등록 당시에는 운영 지시문·실행 코드·템플릿을 변경하지 않았다. ACWR01에서 공통 기록 범위를 반영하고 ACWT01에서 예시·복사 지시문·운영 안내를 연결한다. 계획·규약 정리는 개발 작업이므로 기존 개발 로그와 STATUS를 갱신한다. 사용자 통과 후 Git 저장 순서는 유지한다.

보완안의 구조 선택은 이미 확정됐다. 현재 작성한 계획 변경을 Git에 저장하는 판정과, 후속 각 변경의 검증·판정은 현행 절차로 구분한다. 이전 개발 건의 통과를 새 변경의 통과로 해석하지 않는다.

## 2. 해결할 문제와 확인 근거

| 확인된 구조·계약 | 발생 가능한 문제 | 이번 해결 방향 |
| --- | --- | --- |
| AGENTS는 콘텐츠에도 개발 로그·루트 STATUS 갱신을 요구함 | 글 작성 상태가 사이트 개발의 지금·다음 작업을 교체할 가능성 | 작업 목적별 기록 규칙 분리 |
| 복사용 콘텐츠 지시문도 같은 개발 진입 절차를 전달함 | 하위 가이드가 이전 갱신 의무를 다시 적용할 가능성 | 공통 규약·복사 지시문·운영 가이드 함께 정리 |
| request_id는 같은 확정 입력의 재실행을 식별함 | 글 생성 뒤 후속 수정을 같은 요청에 덮어쓸 가능성 | 작업 폴더와 개별 요청의 수명 분리 |
| local은 Git 제외이고 완료 기록은 최소 지문만 보관함 | 경로·완료 기록만 넘겨 원문·자산을 잃을 가능성 | 인계할 원문·자산과 실제 작업 루트 명시 |
| Tool 잠금은 apply/recover를 보호함 | 메모·요청 직접 편집과 Git 스테이징까지 잠겼다고 오인할 가능성 | 한 작업 담당·지정 worktree·저장 단계 경계 명시 |

실제 덮어쓰기 사고를 확인한 것은 아니다. 현행 문서와 프로그램에서 확인한 지시 충돌·실패 가능성을 근거로 예방 구조를 정한다. 상세 근거와 세 검토의 결과는 결정 기록에 남긴다.

## 3. 확정한 작업공간 구조

```text
.content-ops/local/tasks/<작업명-고유값>/
  HANDOFF.md
  draft.md
  notes/
  requests/
    <request_id>/
      request.json
      plan.json
      assets/
```

- 작업 폴더는 사람이 맡긴 콘텐츠 작업을 묶는 로컬 공간이다. 초안이 필요 없는 카테고리·프로젝트 수정에는 draft.md를 만들지 않아도 된다. 비어 있는 보조 폴더도 의무 생성하지 않는다.
- 작업 폴더 이름은 경로 관례다. CLI JSON에 task_id 필드·새 데이터 스키마·영구 작업 ID를 추가하지 않는다. 기존 작업을 재개할 때 실제 폴더를 찾아 재사용하며 매 세션 새 폴더를 만들지 않는다.
- HANDOFF와 초안·메모는 가변 자료다. 계획에 사용한 확정 요청은 원문 그대로 보존한다. 후속 내용 변경이 확정되면 새 request_id와 하위 폴더를 만들고 원래 대상·선행 요청을 연결한다.
- 확정 요청·계획은 기존 CLI 인자로 지정한다. 기존 계획을 확인 없이 덮어쓰거나 지문만 최신 값으로 바꿔 충돌을 우회하지 않는다.
- assets에는 요청이 참조할 준비 자산을 필요할 때만 둔다. source는 실제 저장소 상대 경로와 바이트 지문을 사용한다. 자산 경로를 요청 폴더 상대 경로라고 추측하지 않는다.
- 기존 `.content-ops/receipts/`, local의 apply.lock·journals·stages는 Tool 소유 경로로 유지한다. 작업 메모 폴더 안으로 옮기지 않는다.

예를 들어 카테고리 추가·글 생성·후속 도입부 수정은 같은 작업 폴더의 서로 다른 확정 요청 3개다. 카테고리 적용이 끝난 뒤 최신 설정·파일 기준을 읽어 다음 요청을 확정한다. 서로 다른 요청을 전부 같은 오래된 기준으로 미리 확정하지 않는다.

## 4. 문서 소유권과 작업 분류

| 작업·영역 | 읽기·기록 기준 |
| --- | --- |
| 사이트 기능·Tool·운영 규칙 개발 | 루트 STATUS·개발 계획·docs/log 절차 유지 |
| 글·Fragment·카테고리·프로젝트의 내용 작업 | 저장소 규칙과 실제 브랜치 확인 후 해당 작업공간 사용, 개발 STATUS의 지금·최근 3건·날짜와 개발 로그를 콘텐츠 진행 기록으로 갱신하지 않음 |
| 개발과 콘텐츠가 섞인 요청 | 목적과 변경 범위를 나누어 개발 이력은 개발 기록, 콘텐츠 진행은 작업 HANDOFF에 기록하고 Git 검토 범위는 실제 변경 전체로 확인 |
| 공통 규약·지시문·템플릿 변경 | 운영 규칙 개발에 해당하므로 개발 기록 사용 |
| 확정 요청·계획 | 기존 입력·계획 계약 적용, 작성 스킬의 자유 메모와 구분 |
| 적용·완료·복구 상태 | 실제 파일·receipt·journal로 확인, HANDOFF의 상태 문자열을 실행 결과나 사용자 승인 증거로 대신하지 않음 |

파일 확장자만으로 작업을 분류하지 않는다. 카테고리·프로젝트 내용 변경은 src/consts.ts를 편집해도 콘텐츠 작업이며, 사이트 기능을 바꾸는 문서·설정 수정은 개발 작업일 수 있다.

루트 STATUS는 개발 현황과 문서 위치를 확인하는 진입점으로 유지한다. 콘텐츠 AI가 무관한 개발 확인 대기를 자신의 작업 승인 대기로 이어받지 않도록 범위를 명시한다. 콘텐츠 작업에도 현재 변경의 사용자 통과·기존 Git 승인·정책 훅은 유지한다. gated-tdd 등 개발 스킬을 콘텐츠 작업에 자동 적용하지 않으며 사용자가 별도로 명시하면 해당 적용 범위를 먼저 맞춘다. 스킬의 자동 커밋 규칙이 저장소의 사용자 통과 조건을 완화하지 않는다.

콘텐츠 진행 이력을 위해 개발 로그를 중복 생성하지 않는다. 적용 기록이 있는 작업은 기존 receipt·실제 결과와 Git 저장 증거를 사용한다. 순수 초안이나 unchanged처럼 receipt가 없는 상태도 있으며, HANDOFF에 확인한 범위만 기록한다. 공유 진행 목록·승인 문자열 저장소를 새로 만들지 않는다. 기존 개발 로그는 이동·삭제하지 않는다.

## 5. 인계·담당·실행 위치

HANDOFF의 최소 정보는 목적·대상, 실제 작업 루트·브랜치·확인한 기준 커밋, 현재 초안/확정 요청 참조, 확정·미결정 사항, 수행한 검사와 관찰 시점, 실제 저장 단계와 증거 참조, 다음 행동이다. 적용·사용자 통과·커밋·push·운영 공개를 별도 상태로 설명하고 확인하지 않은 상태를 완료라고 기록하지 않는다. 사용자 판정은 실제 대화에서 확인하며 메모만으로 승인하지 않는다.

같은 초안·HANDOFF에는 한 AI가 작성 담당을 맡는다. 다른 AI는 검토하거나 별도 메모를 만들 수 있으나 동일 파일을 동시에 갱신하지 않는다. 이 담당 규칙은 실제 파일 쓰기 잠금이 아니다. 같은 worktree의 Git 인덱스·사용자 승인 상태를 여러 작업이 동시에 변경하지 않으며, 자동 격리가 필요한 경우는 별도 설계 대상으로 남긴다.

한 확정 요청은 지정한 worktree에서 실행한다. CLI는 해당 프로젝트 루트에서 실행하고 요청·계획 경로를 명시한다. --request 상대 경로는 터미널 위치, --root 생략은 스크립트 소속 저장소, --plan/--out은 대상 저장소 기준이라는 현행 의미를 유지한다. 외부 폴더에서 실행하는 안내가 필요하면 절대 요청 경로와 명시적 root를 사용한다. 스킬 메모 위치를 바꾸려고 터미널 실행 루트를 작업 메모 폴더로 옮기지 않는다.

다른 컴퓨터·worktree·웹 전용 AI에 넘길 때는 local 경로만 제공하지 않는다. 필요한 초안·HANDOFF·확정 요청·원래 계획/지문·준비 자산 원문과 저장소/브랜치/기준 정보를 전달하고 수신 측에서 실제 파일을 대조한다. Git 제외는 암호화나 비밀 보관을 의미하지 않으며 local 자료는 평문일 수 있다.

활성 apply가 있거나 중단된 실행은 먼저 지정 worktree의 실제 상태를 확인한다. 잠금·저널·stages를 일반 인계 묶음에 복사해 다른 호스트에서 복구를 자동 재개하는 규칙은 도입하지 않는다. 다른 호스트·불명 소유자·손상·외부 변경의 복구 거절과 기존 한계를 유지한다. 다른 worktree 사본끼리 잠금이 공유된다고 설명하지 않는다.

문서 작업은 내용·참조·시나리오 정합성으로 판정하며 가짜 Red를 만들지 않는다. 기존 동작 검사는 호환성 검사로 구분한다. 실행 코드 변경 필요성이 새로 발견되면 원인·필요 범위를 먼저 기록하고 계획 범위 변경을 확인한다. 기존 테스트 삭제·skip·기대값 완화로 통과시키지 않는다. 새 상태 엔진이나 반복적인 문구 대조 전용 테스트는 만들지 않는다.

자동으로 확인할 수 있는 CLI·파일 보존·문서 링크 검사는 에이전트가 수행한다. 화면·외부 계정 흐름을 변경하지 않으므로 사용자의 직접 실행 항목은 만들지 않는다. 사람이 판단할 추가 항목이 없더라도 현행 AGENTS의 명시적 통과 후 승인·커밋·개발 브랜치 push 순서를 유지한다.

## 7. 검증 시나리오와 끝의 정의

| 사례 | 실제로 확인할 결과 |
| --- | --- |
| 글 두 건의 독립 작업 | 서로 다른 작업 폴더·확정 요청 사용, 상대 초안/HANDOFF와 루트 개발 STATUS·개발 로그 바이트 보존 |
| 하나의 작업에 여러 요청 | 카테고리 생성→글 생성→후속 수정의 개별 요청 유지, 원래 요청 원문과 다른 작업 내용 보존 |
| 새 AI가 같은 요청 재실행 | 원래 입력·계획·실제 결과 대조, 변경 없음과 파일 바이트·mtime 보존, 임의 ID 재생성 없음 |
| HANDOFF의 오래된 상태 | 미적용/완료 메모와 달라도 실제 파일·receipt·journal 기준으로 다음 행동 결정 |
| 같은 ID의 다른 확정 입력 | 기존 충돌 거절 유지, 원래 요청을 보존하고 새 작업인 척 우회하지 않음 |
| 작업 루트·자산이 다른 인계 | 명시한 root·요청 위치 확인, 없는 자산/다른 기준은 실패로 분류, 현재 루트에 묵시적으로 적용하지 않음 |
| 중단·다른 호스트 경계 | 현행 관련 회귀로 거절/보존 확인, 잠금·저널을 복사해 자동 재개하는 절차가 없는지 확인 |
| 지시문·스킬의 적용 범위 | 루트 하드코딩 스킬은 경로 지원 여부 확인, 지원 불가 시 충돌 보고, 파일 분리가 실제 권한 통제라고 설명되지 않음 |

시나리오는 합성 자료의 격리 사본에서 실행한다. 자동 검증 가능한 파일·CLI 결과와, AI가 규칙을 해석하는 시나리오 검토를 구분해 보고한다. 문서를 읽은 모든 AI의 지시 준수를 테스트로 증명했다고 주장하지 않는다. 새 템플릿은 운영 콘텐츠 수집 경로 밖에 두며 실제 블로그에 시험 등록하지 않는다.

완료 조건은 공통 규칙의 모순 제거, 작업/요청 수명 분리, 스킬 메모 범위와 인계 안내 제공, 기존 CLI/receipt/복구/승인 호환성 유지, 실제 검증 증거와 미보장 공개다. 검사 선택은 변경 영향에 맞춘다. 실행 코드·웹·빌드를 바꾸지 않는 문서 작업에서 전체 브라우저 검사를 의례적으로 반복하지 않으며, 최종 실제 CLI 시나리오와 관련 회귀는 수행한다.

## 8. 제외 범위와 현재 진행

루트 파일 전체 이름 변경, 전역 작업 목록·DB·자동 동기화·새 잠금/권한 엔진, CLI 공개 계약 변경, 기존 기록/저널 이관, 실제 콘텐츠·URL·ID 변경, 외부 스킬 패키지 수정·설치, 웹 작성기/OAuth 변경, main 병합·운영 발행은 제외한다.

ACWP01은 사용자 통과 후 `7d3fb16`으로 커밋·개발 브랜치 push했다. ACWR01은 AGENTS·CLAUDE·공통 콘텐츠 규약에서 목적별 기록 범위·작업/요청 수명·실제 결과/승인 구별을 반영한 검토 자료다. 이전 가이드의 일반적인 개발 로그 안내에도 새 분류를 적용하도록 공통 원문에 명시했다. 실제 운영 코드·완료 기록·복구·승인 프로그램은 유지한다. ACWR01의 현재 변경 통과 뒤 저장하고 ACWT01 작업공간 예시·상세 지시문, ACWV01 실제 격리 시나리오를 진행한다. 해당 후속 두 단계는 아직 미구현이다.
