# devlog 운영 가이드

블로그를 처음 올리는 순간부터, 매일 글을 쓰고 관리하는 일까지의 전체 흐름입니다.

AI에게 작업을 맡길 때는 [AI 콘텐츠 작업 규약](./AI-콘텐츠-작업규약.md)의 대상 식별·재실행·충돌 규칙을 함께 따릅니다. 검증과 사용자 판정, 커밋·push는 [AGENTS.md](../../AGENTS.md)의 완료 절차를 따릅니다.

---

## 한눈에 보는 흐름

```
[내 컴퓨터]                             [개발 브랜치]                  [공개 사이트]
  폴더/index.md 작성 → 검증·사용자 통과 → 커밋·push → 공개 범위 판정 → main 검사·빌드·배포
  npm run dev로 미리보기
```

- **딱 한 번 하는 일**: 아래 1단계(초기 배포)
- **평소 반복하는 일**: 2단계(글 작성·검증·판정·개발 브랜치 보존), 공개할 때는 배포 범위도 확인합니다.

## 1. 초기 배포 (처음 한 번만)

### 1-1. 준비물 확인

```bash
node -v   # v18.20.8 이상 또는 v20+ 이면 OK
```

### 1-2. 프로젝트 설치

압축을 푼 폴더에서:

```bash
npm install      # 최초 1회 (몇 분 소요)
npm run dev      # 현재 설정은 http://localhost:4321/ 로 미리보기
```

### 1-3. 내 정보로 바꾸기

- `src/consts.ts` → 이름·소개·이메일·소셜·카테고리·기술 스택
- `astro.config.mjs` → 배포 주소 설정 (아래)

배포 주소는 두 가지 중 하나입니다:

| 방식            | 주소                   | 설정                                               |
| ------------- | -------------------- | ------------------------------------------------ |
| 프로젝트 페이지 | `유저명.github.io/레포명/` | `site: 'https://유저명.github.io'`, `base: '/레포명/'` |
| 유저 페이지 (현재) | `유저명.github.io/` | 레포 이름을 `유저명.github.io` 로 만들고 `base` 줄 삭제 또는 `/` |

> `base` 를 잘못 맞추면 사이트는 뜨는데 디자인이 전부 깨져 보입니다. 가장 흔한 실수이니 주소 방식을 먼저 정하세요.

### 1-4. GitHub 원격 확인

현재 프로젝트는 이미 GitHub 저장소와 연결되어 운영 중입니다. 원격 주소와 현재 작업 브랜치를 확인하고 2-3의 검증·판정 절차로 변경을 보존합니다. 새 저장소 개설이나 원격 주소 변경이 필요하면 콘텐츠 추가와 별도의 작업 범위로 준비합니다.

### 1-5. Pages 켜기

레포 → **Settings → Pages → Build and deployment → Source** 를 **GitHub Actions** 로 선택합니다. (한 번만 하면 됩니다.)

### 1-6. 배포 확인

레포의 **Actions** 탭에서 워크플로가 초록 체크(✓)로 끝나면, 위 표의 주소로 접속해 확인합니다. 처음 한 번은 반영까지 2~3분 걸릴 수 있습니다.

## 2. 평소 글쓰기 (가장 자주 하는 일)

### 2-1. 미리보기 서버 켜기 (선택)

```bash
npm run dev
```

글을 저장할 때마다 브라우저가 자동으로 새로고침됩니다.

### 2-2. 새 글 파일 만들기

`src/content/blog/` 안에 글 폴더를 만들고 그 안의 **`index.md`**에 씁니다. 실제 글 로더는 `**/index.md`만 수집하므로 루트에 단일 `.md` 파일만 추가하면 글로 수집되지 않습니다.

```text
src/content/blog/
  my-first-post/
    index.md
    my-diagram.png
```

- 이 예시 글의 주소는 `/blog/my-first-post/`입니다. 현재 사이트는 별도의 base 경로가 없습니다.
- 신규 폴더명은 영문 소문자와 하이픈을 권장합니다. 기존 한글·공백 폴더는 제목 수정만으로 변경하지 않습니다. 실제 URL은 Astro가 수집한 ID와 `postSlug()`를 통해 생성됩니다.
- 생성 전에 기존 경로·제목 후보를 찾습니다. 같은 대상·같은 내용이면 변경 없음으로 보고하고, 다른 내용이면 신규 파일을 더 만들거나 기존 파일을 덮어쓰지 않습니다.

내용 형식:

```markdown
---
title: 글 제목
description: 카드·검색에 보이는 한 줄 요약
category: Frontend
tags: [React, 성능]
pubDate: 2026-06-30
readingTime: 6분
draft: false
---

여기부터 본문을 마크다운으로 씁니다.

## 이렇게 ## (h2) 와 ### (h3) 로 쓴 제목이
오른쪽 목차에 자동으로 들어갑니다.
```

프론트매터(맨 위 `---` 사이) 필드 정리:

| 필드 | 필수 | 설명 |
|------|:---:|------|
| `title` | ✅ | 글 제목 |
| `description` | ✅ | 카드·검색·SEO 에 쓰이는 요약 |
| `category` | ✅ | 작성 정책상 `consts.ts`의 `CATEGORIES` 키 사용. 현재 스키마는 등록 여부를 자동 검사하지 않음 |
| `tags` | | 태그 배열. 예: `[React, 성능]` |
| `pubDate` | ✅ | 확정한 발행일 (`YYYY-MM-DD`). 재실행이나 제목 수정으로 바꾸지 않음 |
| `readingTime` | | 읽는 시간. 비워도 됨 |
| `draft` | | `true`면 목록·검색·상세 페이지에 안 나옴. 생략하면 `false`. 공개 여부를 명시 |

### 2-3. 올리기

1. 현재 개발 브랜치와 기존 변경을 확인하고, 본문·frontmatter·이미지 경로·등록 카테고리·공개 여부를 검증합니다. 관련 검사와 빌드는 에이전트가 수행합니다.
2. 이번 작업 로그를 남기고, 글 폴더·해당 이미지·로그·메뉴판·STATUS 등 **현재 작업의 파일만** 정확한 경로로 스테이징합니다.
3. 확인할 파일이나 미리보기를 준비해 사용자에게 변경 내용과 예상 결과를 안내합니다. 사용자의 명시적 **통과** 판정을 기다립니다.
4. 통과 뒤 승인 상태를 기록하고 검토받은 변경을 그대로 커밋·개발 브랜치 push합니다. 판정 후 내용을 바꿨으면 다시 검증받습니다.
5. 공개 반영은 별도로 배포 범위를 확인하고 판정받아 `main`에 반영합니다. `main` push가 Actions 검사·빌드·배포를 실행합니다. 개발 브랜치 push는 사이트 공개 반영이 아닙니다.

실제 승인 명령과 훅 절차는 `AGENTS.md`를 따릅니다. 커밋 수·push 성공·빌드 성공과 운영 배포 완료를 구별해 보고합니다.

## 3. 자주 하는 운영 작업

### 글 수정
기존 글 폴더의 `index.md`에서 요청한 부분만 수정하고 2-3의 절차를 따릅니다. 폴더·원래 발행일·이미지·요청하지 않은 메타데이터를 보존합니다. 내용이 이미 반영되어 있으면 새 변경이나 커밋을 만들지 않습니다.

### 글 삭제
정확한 글 폴더와 연결된 이미지·참조를 확인하고 삭제 범위를 검증받습니다. `main` 반영과 배포가 완료되면 글 페이지와 주소가 사라집니다. 다른 글이 사용하는 자산까지 함께 지우지 않습니다.

### 임시저장 (초안)
프론트매터에 `draft: true` 를 넣으면 목록·검색·페이지에서 모두 제외됩니다.
초안도 컬렉션에 수집되어 스키마 검증을 받습니다. 로컬에서도 숨겨지므로 미리보기하려면 공개 여부를 임시로 바꾼 상태임을 구분해 확인합니다. 임시 미리보기 뒤에는 원래 `draft: true`를 복원해 스테이징 내용을 검사하고, 공개가 승인된 경우에만 최종 `draft: false` 상태를 포함합니다.

완성한 글은 공개 여부와 변경 범위를 판정받아 2-3의 절차로 반영합니다. 현재 `src/content/blog/templates/index.md`는 공개 예제입니다. 그 파일을 정책 정리 과정에서 삭제·비공개 전환하지 않으며, AI용 신규 템플릿은 콘텐츠 수집 경로 밖에 둡니다.

### 새 카테고리 추가
`src/consts.ts`의 `CATEGORIES`에 등록하면 사이드바와 카드·라벨 색에 반영됩니다. 기존 키를 먼저 찾고 신규 키·색상을 확정한 뒤 검증·판정 절차를 따릅니다. 같은 키·색상이 이미 있으면 변경 없음이고, 같은 키의 다른 색상은 명시적 수정 요청으로 다룹니다.

콘텐츠에 임의 카테고리 문자열을 쓰는 것만으로 등록되지는 않습니다. 기존 Fragment의 `Infra`처럼 미등록 값이 있는 항목은 관련 없는 수정에서 그대로 보존하며, 신규 키 등록이나 기존 값 이관은 별도로 합의합니다.

```ts
export const CATEGORIES: Record<string, string> = {
  AI: '#007FFF',
  Frontend: '#5849E0',
  Backend: '#0EA5A4',
  DevOps: '#F0883E',
  Database: '#D6336C',
  '회고/생각': '#8B5CF6',
  Security: '#16A34A',   // 신규 키와 색상을 확정한 경우의 예시
};
```

### 글에 이미지 넣기
이미지 파일을 글의 `index.md`와 **같은 글 폴더**(`src/content/blog/my-first-post/` 등)에 두고 상대경로로 참조합니다. Astro의 이미지 처리 경로를 사용하므로 base 변경에 맞춰 글별 이미지 주소를 수동으로 조합할 필요가 줄어듭니다. 실제 파일이 존재하는지 빌드로 확인합니다.

```markdown
![설명 글](./my-diagram.png)
```

> 파비콘처럼 사이트 전역 자산은 `public/` 폴더에 둡니다. 단, `public/` 의 파일을 본문에서 참조할 땐 base 주소를 신경 써야 하므로, 글 이미지는 위의 상대경로 방식이 더 편합니다.

**반드시 위 마크다운 문법(`![]()`)으로만 넣으세요.** 아래 두 방식은 쓰지 않습니다.

- Obsidian 의 `![[파일명.png]]` 위키링크 문법 — 브라우저는 이걸 이미지로 인식하지 못하고 글자 그대로 노출됩니다. Obsidian 에서 쓴 글을 옮길 때 꼭 `![alt](./파일명.png)` 형태로 바꿔주세요.
- `<img src="...">` 같은 raw HTML 태그 — Astro 의 이미지 최적화·복사 파이프라인은 마크다운 `![]()` 문법만 처리합니다. HTML `<img>` 로 넣으면 빌드 시 파일이 `dist/` 에 복사되지 않아 배포 후 이미지가 깨집니다.

**세로로 긴 이미지(모바일 스크린샷 등)** 는 폭 100%로 그대로 두면 너무 커 보일 수 있습니다. 이럴 땐 `<div>` 로 감싸 폭을 제한하세요 — 이때도 안쪽은 반드시 마크다운 문법을 쓰고, 앞뒤로 빈 줄을 넣어야 정상 처리됩니다.

```markdown
<div style="max-width: 40%; margin: 0 auto;">

![설명 글](./mobile-screenshot.png)

</div>
```

### 디자인 손보기
포인트 색만 바꾸려면 `src/styles/global.css` 맨 위 `:root` 의 `--accent` 한 줄만 수정하면 전체에 반영됩니다.

## 4. 문제가 생겼을 때

### Actions 가 빨간불(빌드 실패)
필수 필드 누락, 날짜 해석 오류, 이미지 경로·파일 누락 등 실제 오류 메시지를 확인합니다. 등록되지 않은 `category`는 현재 스키마에서 빌드 오류가 되지 않을 수 있으므로, 별도로 `CATEGORIES`와 비교합니다.

> **습관 팁**: push 전에 로컬에서 한 번 `npm run build` 를 돌려보세요. 똑같은 에러를 미리 잡을 수 있어 헛걸음을 막아줍니다.

### 사이트는 뜨는데 디자인이 다 깨짐
`astro.config.mjs` 의 `base` 설정이 실제 주소와 안 맞는 경우입니다. (프로젝트 페이지인데 `base` 가 빠졌거나, 유저 페이지인데 `base` 가 남아있음.) 1-3 의 표를 다시 확인하세요.

### 이미지가 안 보임
경로 문제일 가능성이 큽니다. 3장의 상대경로(`./파일명`) 방식으로 바꿔보세요.

### 변경이 반영이 안 됨
순서대로 확인: ① 개발 브랜치에만 저장한 상태인지, 승인받은 공개 범위가 `main`에 반영됐는지 ② **Actions**의 해당 커밋 검사·배포가 완료됐는지 ③ 브라우저 새로고침(캐시) — `Cmd/Ctrl + Shift + R`.

### 글씨체가 평범하게 보임
구글 폰트가 차단된 네트워크(일부 사내망 등)일 때 생깁니다. 일반 방문자에게는 정상적으로 보이니 걱정하지 않아도 됩니다.

---

## 5. 백업과 안전

- GitHub에 push한 변경 이력은 해당 브랜치에 남습니다. 개발 브랜치에 보존한 변경과 `main`에 반영된 공개 변경을 구별합니다.
- 실수로 글을 지웠어도 git 히스토리에서 되살릴 수 있습니다.
- 개발은 해당 기능 브랜치에서 진행하고 작업별 판정을 받습니다. `main` 반영은 배포 인수 조건과 별도 판정을 충족한 뒤 준비합니다.

## 6. 나중에 붙이면 좋은 것들 (선택)

필요해지면 하나씩 추가할 수 있습니다: RSS 피드, 댓글(giscus), 사이트맵, 글 목록 페이지네이션, SNS 공유용 OG 이미지 자동 생성 등. 그때 도움이 필요하면 언제든지요.
