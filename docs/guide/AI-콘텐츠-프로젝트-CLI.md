## 결론과 이번 확인 범위

- 확정한 프로젝트 한 항목 추가와 기존 항목의 요청 필드만 수정 가능함.
- 같은 결과 재실행 시 파일 목록·바이트·수정 시각 보존함. 새 프로젝트 ID·배열 순번 식별자 도입 없음.
- 원래 항목 전체 값으로 대상을 찾고, 겹치는 후보를 임의로 고르지 않음. 모호한 경우 실제 후보 값을 표시하고 중단함.
- 이번 개발은 합성 데이터를 격리 사본에만 적용함. 운영 이력·화면·계정 흐름 변경 없음.
- 사람이 직접 실행해야 할 항목 없음. 파일 결과·종료 코드·실제 빌드로 검증 가능한 내부 도구 변경이며 에이전트가 자동 확인함.
- ACTJ01의 아래 동작·충돌 처리·미보장 범위는 사용자 통과 후 커밋·개발 브랜치 push 완료함. 후속 잠금·복구 작업은 별도 판정 범위임.

## 입력과 실행

- [요청 계약](./AI-콘텐츠-요청-계약.md)의 버전 1 JSON과 같은 plan/apply 명령 사용함.
- `resource: "project"`, `target.path: "src/consts.ts"` 사용함. 생성도 기존 설정을 편집하므로 baseline.sha256에 전체 파일 바이트의 SHA-256 필요함. Git SHA·배열 순번·null 기준 사용 불가함.
- 항목 필수값은 name·description, 선택값은 period·role·highlights·stack·link임. 기존 입력 계약을 공유 스키마로 추출했으며 새 필드나 기본값 추가 없음.
- create는 content에 확정 항목 하나 지정함. update는 target.selector에 **수정 전 항목 전체 값**, changes에 바꿀 필드만 지정함. selector를 이름만으로 축약하지 않음.
- 생략한 changes 필드는 보존함. highlights·stack의 명시적 빈 배열은 비우기이며 배열 순서도 입력의 일부임. 선택 필드 부재와 빈 배열은 같지 않음. null 삭제·항목 삭제·새 id·index 필드 지원 없음.
- 본문·기간·역할·성과·URL의 사실성은 확정 자료로 확인해야 함. 도구가 빠진 사실이나 ID를 생성하지 않음.

```powershell
node scripts/content-ops.mjs plan --request 'input/project-request.json' --root 'C:\작업폴더' --out '.content-ops/local/project-plan.json'
node scripts/content-ops.mjs apply --request 'input/project-request.json' --root 'C:\작업폴더' --plan '.content-ops/local/project-plan.json' --expect-plan '<plan에서 확인한 64자리 지문>'
```

- 요청 상대 경로는 터미널 작업 폴더, 대상·계획 경로는 지정 root 기준임. root 생략 시 스크립트 소속 저장소 사용함.
- plan은 수정 전후 TypeScript와 계획 지문을 표시하고 로컬 계획 파일만 저장함. 같은 계획 파일 재실행 시 다시 쓰지 않음.
- apply는 확정 입력·계획·기대 지문·현재 기준·실제 제안 결과·정책을 다시 대조한 뒤 로컬 파일과 최소 완료 기록 반영함.
- `--json` 지원함. 종료 코드 0 성공/변경 없음·1 입력/충돌/적용 실패·2 명령 사용 오류임. Git 승인·커밋·push·발행은 수행하지 않음.

## 신규 등록에서 중복을 피하는 기준

- 후보 비교에는 name·period·role·link 사용함. 양쪽에 있는 값이 다르면 별개 후보로 구별함. 한쪽 값이 빠졌다는 사실만으로 다른 프로젝트라고 단정하지 않음.
- 후보 0개이면 한 항목 추가함. 후보 1개와 전체 내용이 같으면 변경 없음, 내용이 다르면 target.conflict임. 후보 여러 개이면 완전히 같은 항목이 포함돼 있어도 target.ambiguous임.
- 같은 이름·같은 기간·같은 역할·같은 링크인데 설명만 다른 create는 기존 항목 수정일 수 있으므로 추가하지 않음. 수정 의도를 확인한 뒤 update 요청으로 별도 확정 필요함.

| 실제 상태와 요청 | 처리·이유 |
| --- | --- |
| 같은 항목 전체가 이미 존재함 | 변경 없음. 인용·주석·줄바꿈도 그대로 유지함 |
| 이름·기간 등은 같고 설명만 다른 신규 요청 | 충돌. 기존 이력을 복제하거나 임의 수정하지 않음 |
| 기존 항목에 기간이 없고 요청에 기간만 추가됨 | 같은 이력일 가능성이 있어 충돌. 누락을 별개 증거로 사용하지 않음 |
| 같은 이름이나 양쪽의 확정 기간이 서로 다름 | 다른 후보로 구별하여 신규 추가 가능함 |
| 기존 후보 여러 개와 새 요청이 겹침 | 모호함으로 중단. 실제 후보 전체 값 표시함 |

- 이 기준은 보수적인 값 비교임. 이름까지 다른 두 기록이 실제로 같은 프로젝트인지 알아내는 의미 중복 판정 엔진은 아님.

## 기존 수정에서 원래 항목을 찾는 기준

- selector의 전체 값과 같은 항목이 정확히 하나여야 일반 수정 가능함. 다른 항목 추가·정렬 후에도 현재 기준을 다시 확보하고 원래 값으로 찾음. 배열 2번 같은 위치를 요청에 넣지 않음.
- 예: 원래 항목이 name·description·period·role·highlights·link를 가지고 있다면 그 값을 모두 selector에 유지하고 changes에는 `{"role":"백엔드 개발"}`만 지정함.
- 이름·기간·역할·링크를 바꾸더라도 원래 항목에서 수정함. 새 항목을 추가하지 않으며 수정 결과가 다른 항목과 충돌하면 중단함.
- 원래 전체 값이 같은 항목이 여러 개이면 첫 항목을 고르지 않고 target.ambiguous로 중단함. 같은 식별 값이지만 설명이 다른 항목들은 원래 전체 selector로 유일하게 구별되는 경우에만 수정 가능함.
- 후보 오류의 JSON에는 candidates로 실제 항목 값을 제공함. 기본 출력의 ‘후보 1’ 등은 설명용 번호이며 요청 식별자가 아님.

| 계획·재실행 상황 | 결과 |
| --- | --- |
| 역할만 수정함 | 역할 값 범위만 교체. 설명·성과·다른 프로젝트·설정 보존함 |
| 계획 뒤 카테고리나 프로필만 바뀜 | 아직 수정이 필요하면 전체 설정 기준 불일치로 중단함 |
| 기록 없이 요청 역할이 이미 반영되고 설명만 최신 값으로 바뀜 | 요청 결과가 반영된 유일한 항목이고 유지된 식별 근거가 있으면 쓰기 없음. 최신 설명 보존함 |
| 이미 반영된 것으로 볼 항목이 여러 개임 | 모호함으로 중단. 하나를 임의로 성공 처리하지 않음 |
| 원래 selector와 맞는 항목이 없고 반영 여부도 확정할 수 없음 | missing/conflict/ambiguous로 중단. 현재 후보·원문 확인 후 요청 재확정 필요함 |
| 완료 기록 뒤 다른 설정만 편집됨 | receipt.state-mismatch. 전체 consts.ts 최종 지문을 대조하므로 상태 변화 보고함 |

- 기록 없는 이미 반영 상태는 고유한 전체 결과 또는 동일한 최종 식별 값·요청 값과 변경되지 않은 비어 있지 않은 식별 근거로 확인함. 단순히 역할 문자열이 같다는 이유로 다른 프로젝트를 성공 처리하지 않음.
- 완료 기록이 있으면 더 엄격하게 요청 지문·계획·현재 전체 파일 지문을 대조함. 기록 없는 값 비교로 이 검사를 우회하지 않음.

## 설정 원문·지원 구문·전체 정책

- TypeScript AST로 export const PROJECTS에 직접 지정된 정적 배열과 정적 객체 항목의 위치를 읽음. 설정 모듈 실행 없음.
- 값은 허용된 필드의 문자열 또는 문자열 배열만 해석함. 별칭·계산식·spread·getter·동적 키·배열 구멍·중복/알 수 없는 필드·지원 밖 타입 단언은 registry.invalid로 거절함.
- 선언 밖 PROJECTS 변수 참조는 별칭이나 후속 수정의 영향을 확정할 수 없어 patch.unsupported로 거절함. 다른 객체의 정적 속성 이름과 실제 변수 참조는 구별함. 다른 파일의 런타임 수정까지 분석하지 않음.
- 요청한 값의 범위만 교체하거나 없는 선택 필드를 추가함. 신규 항목은 배열 끝에 추가하며 필요한 쉼표만 보충함. 다른 항목·설정·주석·BOM·CRLF/LF 보존함. 새로 넣거나 수정한 값의 표현은 안전한 문자열·배열 인코딩 사용함.
- 카테고리와 프로젝트의 참조 검사·멤버 삽입·원문 범위 편집을 공유함. 기존 카테고리 동작 55개 회귀 사례 유지함.
- 제안 PROJECTS를 스키마로 검사하고, 제안 설정의 정적 CATEGORIES와 현재 글·Fragment·관계·기존 예외를 메모리에서 검사함. 오류가 있으면 설정 쓰기 전 중단함.
- 이 검사는 TypeScript 전체 타입 검사와 실제 Astro 빌드를 대체하지 않음. 적용 후 기존 자동 검사·타입 검사·빌드도 필요함.
