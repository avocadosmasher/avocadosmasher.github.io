# AI 콘텐츠 동시 적용 잠금·중단 복구 CLI

- 개발 건: AI-CONTENT-TOOLS / ACTS01, 2026-10-19 사용자 통과, `69cd526` 커밋·개발 브랜치 push 완료.
- 선행: ACTJ01 사용자 통과, `f93588e` 커밋·개발 브랜치 push 완료.
- 이번 대상: 글·Fragment·카테고리·프로젝트의 로컬 적용 잠금·준비 자료·명시적 복구 명령.

## 결론과 이번 판정

- 같은 저장소의 도구 적용은 한 번에 하나만 실행하도록 잠금 추가함.
- 콘텐츠 쓰기 전에 최종 바이트와 요청/계획 지문을 준비하고, 실행 중단 시 실제 파일 상태를 확인한 뒤 남은 파일만 적용하는 recover 명령 추가함.
- 외부 수정·손상·모호한 잠금은 자동으로 덮어쓰거나 지우지 않음. 완전한 트랜잭션·모든 중단 상태의 자동 해결은 보장하지 않음.
- 이번 결정: 저장소 전체 적용의 상호 배제, 원래 요청·계획을 지정하는 명시적 복구, 확인 불가능한 상태의 자동 처리 중단임.
- 사람이 직접 실행해야 할 항목 없음. 화면·운영 계정 흐름 변경 없이 파일 결과·종료 코드·실제 프로세스 강제 종료로 자동 확인함.
- ACTS01의 아래 동작·미지원 범위는 사용자 통과 후 커밋·개발 브랜치 push 완료함. 후속 저장 차단·공통 CI는 [Git 훅 안내](./AI-콘텐츠-Git-검사-CLI.md)의 별도 판정 범위임.

## 어떤 문제를 해결하는가

| 발생 가능한 상황 | 이번 처리 |
| --- | --- |

| 첫 실행 후 오래된 계획으로 재시도 | 다시 읽은 실제 기준과 대조. 아직 다른 수정이 필요하면 기준 충돌로 중단함 |
| Fragment 본인만 수정되고 관련 카드 수정 전 종료 | 원래 계획의 결과와 실제 상태 대조 후 남은 관련 카드만 수정함 |
| 글은 추가되고 이미지 추가 전 종료 | 완성된 글은 보존하고 준비한 누락 이미지 바이트만 추가함 |
| 콘텐츠는 모두 저장됐으나 완료 기록 쓰기 실패 | 콘텐츠를 재작성하지 않고 전체 결과 확인 후 완료 기록 추가함 |
| 완료 기록까지 쓰고 응답 전 종료 | 실제 결과·기록 일치 확인 후 로컬 복구 자료만 정리함 |
| 종료 후 사람이 본문을 별도로 수정함 | 계획 전후 어느 쪽도 아니므로 복구 충돌. 최신 원문 보존함 |

- 위 ‘세션’은 AI 대화/작업 실행을 의미함. 블로그 방문자의 브라우저 로그인 세션을 제어하는 기능은 아님.
- 공개 사이트의 이력·화면·OAuth·배포 동작은 이번 작업에서 변경하지 않음.

## 평소 적용과 중단 후 복구

- 평소에는 기존 plan → apply 명령 사용함. [요청 계약](./AI-콘텐츠-요청-계약.md)과 종류별 [글](./AI-콘텐츠-글-생성-CLI.md)·[Fragment](./AI-콘텐츠-Fragment-CLI.md)·[카테고리](./AI-콘텐츠-카테고리-CLI.md)·[프로젝트](./AI-콘텐츠-프로젝트-CLI.md) 입력 유지함.
- 적용 도중 실패하면 오류 코드·이미 반영한 경로와 가능한 경우 recovery.journal 경로 보고함. 종료된 실행의 잠금이 남으면 일반 apply는 lock.busy로 중단함.
- 남은 저널이 있으면 다른 작업의 apply도 recovery.required로 중단함. 미완료 변경 위에 새 작업을 쌓지 않도록 먼저 원래 작업 상태 확인 필요함.
- 복구에는 **원래 확정 요청 파일·원래 계획 파일·그 계획의 64자리 지문** 필요함. 최신 본문으로 요청을 다시 생성하거나 지문을 새로 맞추지 않음.

```powershell
node scripts/content-ops.mjs recover --request 'input/original-request.json' --root 'C:\작업폴더' --plan '.content-ops/local/original-plan.json' --expect-plan '<원래 확인한 64자리 계획 지문>'
```

- `--json` 지원함. 종료 코드 0 성공/변경 없음·1 입력/충돌/복구 실패·2 명령 사용 오류임. --force·승인 우회 인자 없음.
- 복구 후 apply 재실행은 기존 완료 기록과 실제 파일을 대조해 콘텐츠·완료 기록 추가 쓰기 없이 종료함.
- 복구 명령은 로컬 변경만 만듦. 해시 일치는 사용자 승인 증거가 아니며 Git 승인·커밋·push·발행은 기존 AGENTS 절차를 따름.

## 잠금 범위와 해제 조건

- 잠금 위치는 .content-ops/local/apply.lock 폴더임. 배타적 폴더 생성으로 같은 실제 저장소의 다섯 적용 진입점과 recover를 보호함. 다른 파일 작업도 한 번에 하나만 수행하는 보수적 방식임.
- 소유 자료는 버전·임의 토큰·프로세스 ID·호스트 이름임. 토큰은 자기 잠금 확인용 값이며 사용자 인증·승인 토큰이 아님.
- 일반 종료·처리 가능한 예외에서는 자신의 소유 정보가 유지될 때만 잠금 해제함. 소유 정보가 바뀌거나 해제가 실패하면 임의 해제하지 않고 오류와 이미 반영한 경로 보고함.
- 강제 종료로 남은 잠금은 recover에서 같은 호스트의 해당 프로세스가 실제 종료됐음을 확인한 경우에만 복구 점유 가능함. 시간 경과만으로 잠금 삭제 없음.
- 동시 recover는 별도의 배타적 recovery.json 점유로 중복 진입 차단함. 원래 소유 정보를 다시 대조하고 종료 확인 후 복구 수행함.
- 실행 중·다른 호스트·정보 손상·종료 확인 권한 없음·PID 재사용으로 살아 있는 프로세스가 보이는 경우에는 자동 해제하지 않음.
- **중단된 recover의 recovery.json이 남은 상태는 추가 자동 해제 미지원**임. 소유 정보·프로세스·자료를 별도로 확인해야 하며 무조건 삭제 후 재실행하는 안내는 하지 않음.
- 읽기 전용 검사와 plan은 잠금 없이 사용 가능함. plan 후 상태가 바뀔 수 있으므로 apply가 현재 기준을 다시 확인함. 도구 밖 편집기는 이 잠금을 따르지 않을 수 있음.

## 보관 자료와 실제 복구 조건

| 위치 | 내용·보관 경계 |
| --- | --- |
| .content-ops/local/journals/request-id.json | 버전·요청 ID/지문·계획 지문·준비 폴더 ID. 본문·대화·승인 복제 없음 |
| .content-ops/local/stages/고유ID/ | 계획 파일별 최종 바이트와 완성된 저널 원본. 본문·자산을 포함할 수 있는 로컬 임시 자료 |
| .content-ops/receipts/request-id.json | 기존 최소 완료 기록. 콘텐츠와 함께 Git 검토할 공유 자료 |

- 준비 바이트를 완성·fsync한 뒤 완성 저널을 하드 링크로 배타적으로 게시함. 게시 전에는 콘텐츠 쓰기를 시작하지 않음. 하드 링크를 지원하는 같은 파일시스템이 필요함. 지원하지 않으면 적용을 진행하지 않음.
- local 전체는 기존 Git 제외 규칙 적용됨. 준비 파일은 암호화 저장소가 아니므로 로컬 콘텐츠와 같은 취급 필요함. 토큰·채팅·추가 인증 자료를 수집하지 않음.
- 정상 완료 후 자신의 저널·준비 파일만 정리함. 다른 내용으로 바뀐 준비 자료는 지우지 않고 cleanup_pending으로 보고함. 디렉터리 전체를 재귀 삭제하거나 사용자 콘텐츠를 되돌리지 않음.
- 저널 게시 전에 프로세스가 종료되면 콘텐츠는 미변경이며 게시되지 않은 임시 파일이 남을 수 있음. 새 실행은 새 고유 준비 폴더를 사용함. 남은 자료를 일괄 삭제하는 기능은 이번 범위 밖임.
- 복구는 원래 계획·요청과 저널의 일치, 모든 현재 대상이 계획 전 또는 후 지문인지, 준비 바이트가 최종 지문과 같은지 먼저 확인함. 그 뒤 제안 전체 문서/관계/카테고리 정책을 다시 검사함.
- 모든 선행 검사가 끝난 후 아직 계획 전 상태인 파일만 씀. 계획 후 상태인 파일은 바이트·mtime 보존함. 관련 파일의 변하지 않는 상태도 전체 결과 대조에 포함함.
- 모든 대상이 최종 결과이며 완료 기록도 정확하면 준비 파일 손실과 무관하게 완료 상태로 인정하고 로컬 정리만 수행함.
- **임의 중간 바이트·잘린 신규 파일·불완전한 완료 기록·없거나 손상된 준비 자료는 자동 복구하지 않음**. 원문·기록을 삭제/덮어써서 맞추지 않으며 충돌과 근거 보고함.
- local 자료가 없는 다른 컴퓨터나 작업 폴더에서는 저널 복구 불가함. 확정 요청 원문도 필요하며 완료 기록의 해시만으로 본문을 복원할 수 없음.

- Red → Green: 잠금 중에도 적용되던 사례, 교체 실패 시 저널이 없던 사례, 미지원 recover 명령, 종료된 소유자 잠금을 회수하지 못하던 사례를 각각 실제 assertion 실패로 확인 후 구현함.

## 미보장 범위와 다음 단계

- 마지막 기준 확인과 rename 사이에 도구 밖 편집기가 쓰는 경우의 원자적 비교·교체 미보장임. 여러 파일은 순차 반영되며 데이터베이스 트랜잭션이 아님.
- 위 조건 밖 손상·복구 점유 자체의 강제 종료·다른 호스트 잠금은 자동 해결하지 않음. OS 전원 손실·디스크 손상·모든 운영체제/파일시스템의 점유 오류까지 검증한 것으로 주장하지 않음.
- 이번 EBUSY/EACCES 검사는 오류 응답 주입에 대한 보존·재시도 검증임. 실제 Windows의 모든 파일 점유·백신 동작을 재현한 실험은 아님.
- 모든 AI의 도구 사용 강제, 파일 쓰기 권한 회수, 원격 승인 인증은 제외 범위임.
- ACTS01 당시 기존 사용자 승인 훅은 변경하지 않았음. 이후 ACTH01에서 기존 승인 검사 뒤 콘텐츠 정책 Git 검사와 공통 CI를 연결함. 최신 내용은 위 Git 훅 안내를 따름. 다음 작업은 ACTA01 최종 운영 안내·원격 실행 확인·인수임.
