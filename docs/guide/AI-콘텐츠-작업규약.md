# AI 콘텐츠 작업 규약

- 개발 건: `AI-BLOG`, 작업 `ABR01`
- 상태: ABR01 사용자 통과 — `8d04158`, 개발 브랜치 push 완료. 계획·검증 이력은 [개발계획](../plan/AI-블로그-작업-개발계획.md)과 [규약 작성 로그](../log/61-ABR01.md)를 따른다.
- 적용 대상: 블로그 글, Fragment, 카테고리, 소개 페이지의 프로젝트 이력·경력·프로필을 다루는 AI.
- 기준 코드: `f2d0081`. 이번 작업은 규약을 추가하며 저장 기능이나 콘텐츠 스키마를 변경하지 않는다.

## 1. 규약의 역할과 우선순위

사용자의 현재 요청과 명시적 판정을 먼저 따른다. 저장소 작업 절차는 [AGENTS.md](../../AGENTS.md), 프로젝트 구조는 [CLAUDE.md](../../CLAUDE.md)를 따른다. 이 문서는 콘텐츠의 입력·대상 식별·신규/수정/재실행/충돌 판단을 정한다. 개발 건의 범위는 각 개발계획으로 확인한다.

세션 시작에는 `STATUS.md`만 읽는다. 이후 작업에 필요한 규칙과 원본만 읽으며 과거 로그 전체를 읽지 않는다. 원본 위치는 Graft로 먼저 찾는다. 실제 코드와 안내가 다르면 차이를 보고하고, 빌드가 통과했다는 이유로 작성 정책까지 지켰다고 판단하지 않는다.

이 규약은 AI의 작업 절차다. 모든 경로에 공통 처리 엔진이나 요청 이력 저장소가 구현되어 있지는 않다. 에이전트는 확정 입력과 대상 상태를 비교하고 검사 결과를 보고해야 한다. 조회·비교를 못한 상태에서 멱등성을 검증했다고 보고하지 않는다.

## 2. 요청을 실행 가능한 입력으로 확정한다

| 정보 | 확정할 내용 |
| --- | --- |
| 요청 식별자 | 동일 작업을 인계·재시도할 때 재사용할 값. 새 세션이라고 바꾸지 않음 |
| 대상 종류 | 글 / Fragment / 카테고리 / 프로젝트 이력 / 경력·프로필. 개발 작업 로그와 구분 |
| 작업 종류 | 신규 생성 / 기존 수정 / 삭제 / 공개 발행. 생성 요청을 임의로 수정 요청으로 바꾸지 않음 |
| 접근 경로 | 저장소 수정 또는 웹 화면. 저장소·브랜치·작업 폴더를 명시 |
| 대상 식별 정보 | 글의 실제 경로, Fragment의 원래 경로·ID, 카테고리 키, 프로젝트·경력의 확인된 원래 항목 |
| 내용 | 생성은 완성할 본문·메타데이터·자산, 수정은 바꿀 필드와 값, 삭제는 정확한 대상 |
| 기준 상태 | 확인한 커밋·파일 SHA·원문 또는 항목 값. 로컬 미커밋 변경도 확인 |
| 날짜·카테고리 | 사용할 발행일과 등록 키. 기존 값 유지 여부까지 명시 |
| 작성 근거 | 사용자 자료, 확인한 출처, 확인하지 못한 사실. 출처 없는 경력·성과 수치를 만들지 않음 |
| 공개·승인 범위 | 로컬 준비 / 초안 저장 / 개발 브랜치 커밋·push / 운영 발행 중 이번 요청에 포함된 단계 |

이 정보는 작업 인계용이다. `requestId`, 기준 SHA, 승인 상태를 글이나 Fragment frontmatter에 임의로 넣지 않는다. 특히 Fragment 웹 편집기는 허용하지 않은 메타데이터가 있으면 수정을 거부한다.

AI가 처음 작성한 본문·식별자·선택값은 적용 전에 확정하고 인계 기록에 남긴다. 재실행에서는 확정 입력을 재사용하며 본문을 다시 생성하거나 날짜·색상·UUID를 다시 뽑지 않는다. 사용자가 내용을 바꾸면 새 수정 요청으로 구분한다.

현재 새 카드 웹 폼에는 ID 지정란이 없고 첫 저장 요청에서 UUID가 생성된다. 웹 신규 생성은 확정 본문·메타데이터와 기존 후보 조회 결과를 기록해 승인받고, 저장 결과에서 실제 ID·경로를 확인해 이후 대상 식별자로 보존한다. 특정 ID를 미리 지정해야 하는 요청은 저장소 작업으로 인계한다. 저장 결과가 불명확한 채 탭이나 세션이 바뀌면 최신 초안 조회와 내용 비교부터 하며, 새 카드를 다시 만들어 UUID를 바꾸는 방식으로 재시도하지 않는다.

필요한 정보가 없으면 기존 상태나 명시된 자료에서 확인한다. 공개일·대상 항목·기존 값을 바꿀지 여부처럼 결과를 달라지게 하는 선택을 확정할 수 없으면 그 부분을 확인하고, 독립적으로 할 수 있는 조회·초안 준비는 계속한다. 확정되지 않은 값으로 저장하지 않는다.

## 3. 기존 대상을 먼저 찾는다

| 대상 | 식별·보존 규칙 |
| --- | --- |
| 글 | `src/content/blog/<폴더>/index.md`의 실제 경로가 우선. 제목만으로 새 폴더를 만들지 않고 수정 시 폴더와 이미지 경로를 유지 |
| Fragment | 저장된 `id`와 실제 파일 경로가 우선. 제목·별칭은 후보 탐색용. 저장소 신규 작업은 ID를 한 번 정하고 `<id>.md`로 저장; 웹 신규 작업은 첫 저장에서 발급된 ID를 확인해 재사용 |
| 카테고리 | `src/consts.ts`의 `CATEGORIES` 키를 정확히 확인. 대소문자·공백이 비슷한 키도 후보로 보고 임의로 새 키를 추가하지 않음 |
| 프로젝트 이력 | `PROJECTS`의 이름·기간·역할·링크와 원래 항목 내용을 확인. 배열 순번만으로 식별하지 않고 수정 전 다시 대조 |
| 경력·프로필 | `CAREER`의 회사·기간·역할과 원래 항목, 또는 `PROFILE` 등의 정확한 필드를 확인 |

후보는 실제 원본에서 찾는다. 웹 카드 조회에 실패해 빌드 스냅샷만 남았으면 최신 초안에 대상이 없다고 단정하지 않는다. 해당 브랜치의 최신 내용을 확인하거나 조회 실패로 보고한다.

제목이 같다고 동일 항목으로 합치지 않는다. 제목·별칭·프로젝트명이 비슷한 후보가 여럿이면 후보와 차이를 제시해 정확한 대상을 정한다. 같은 요청 식별자를 다른 내용에 재사용하면 기존 입력을 덮어쓰지 않고 요청 충돌로 보고한다. 새 요청 식별자여도 기존 대상 조회는 생략하지 않는다.

기존 UUID Fragment나 한글 글 경로를 읽기 편한 이름으로 자동 변경하지 않는다. 기존 파일 경로와 frontmatter ID가 다르거나 같은 ID가 여러 파일에 있으면 일괄 정리하지 않고 현재 상태를 보고한다. 이동·URL 변경·데이터 이관은 별도 작업이다.

## 4. 신규·수정·삭제·재실행의 결과

| 작업과 현재 상태 | 결과와 행동 |
| --- | --- |
| 신규 대상이 없고 입력이 확정됨 | 생성 변경안을 준비하고 검증·판정을 받음 |
| 신규 대상에 확정 입력과 같은 내용이 이미 있음 | **변경 없음**. 새 파일·새 ID·새 저장 커밋을 만들지 않음 |
| 신규 대상에 다른 내용이 있음 | **충돌**. 덮어쓰거나 `-2` 같은 새 이름을 붙여 우회하지 않음 |
| 수정 대상이 있고 기준 상태가 같음 | 요청한 필드만 변경. 최종 내용이 같으면 변경 없음 |
| 수정 대상이 없거나 후보가 모호함 | 대상 확인 필요. 신규 생성으로 임의 전환하지 않음 |
| 수정 기준이 바뀌고 최종 내용이 다름 | **충돌**. 최신 내용을 다시 읽고 차이를 보고하며 강제로 덮어쓰지 않음 |
| 수정 기준이 바뀌었지만 확정한 최종 내용이 이미 반영됨 | 관련 범위를 비교하여 **변경 없음**으로 보고. 같은 쓰기를 다시 보내지 않음 |
| 삭제 대상이 있고 기준이 같고 참조 검사가 끝남 | 삭제 변경안을 준비하고 영향 범위를 포함해 판정받음 |
| 같은 삭제 재실행에서 대상이 이미 없음 | 실제 삭제 또는 이동 여부를 확인한 뒤 변경 없음. 이동된 대상을 찾아 추가 삭제하지 않음 |
| 저장·발행 응답이 없거나 결과 조회에 실패함 | **결과 미확인**. 완료로 보고하지 않고 확정 입력·기준 상태를 보존한 채 조회부터 재시도 |

### 내용 비교와 보존

원문과 요청 필드·본문·자산을 비교한다. YAML의 필드 순서나 생략된 선택 필드의 기본값처럼 표현만 다른 것은 현행 스키마의 해석을 기준으로 확인한다. 내용이 같으면 기존 파일을 정렬·재직렬화하기 위한 변경을 만들지 않는다. 본문·이미지 바이트·태그 순서·프로젝트 성과 배열처럼 결과에 영향을 주는 차이를 임의로 무시하지 않는다.

수정 요청에서 생략한 필드는 유지한다. 배열·본문을 명시적으로 교체하거나 비우는 요청과 해당 필드에 대한 요청이 없는 경우를 구별한다. 제목만 바꾸는 요청으로 관계·별칭·이미지·원래 발행일을 지우거나 목록 순서를 재배치하지 않는다.

GitHub API의 파일 SHA와 Git 커밋 SHA는 서로 다른 값이다. 로컬 파일 수정에서는 미커밋 원문까지 확인하며, 읽은 상태와 적용 직전 상태를 비교한다. 승인 후 대상 내용이나 변경 범위가 달라지면 이전 판정을 재사용하지 않는다.

## 5. 대상별 현행 데이터 계약

| 대상 | 작성 규칙 | 코드의 현재 보장과 한계 |
| --- | --- | --- |
| 글 | 필수 `title`, `description`, `category`, `pubDate`; 선택 `tags`, `readingTime`, `draft`. 날짜는 확정한 `YYYY-MM-DD`, 이미지는 글 폴더의 Markdown 상대 참조 | `**/index.md`만 수집. 스키마는 카테고리 등록 여부나 모든 빈 문자열을 검사하지 않음. `draft` 생략은 공개 대상 |
| Fragment | 필수 `id`, `title`, `summary`, `category`; 선택 `aliases`, `tags`, `relations`. 본문은 Markdown 영역. 신규 ID는 영문 소문자·숫자·하이픈 | 스키마는 ID 형식·필수 문자열·관계 유형을 검사하지만 카테고리 등록 여부는 검사하지 않음. `draft`·발행일 필드는 현재 없음 |
| 카테고리 | `CATEGORIES`에 키와 색상. 기존 색은 유지하고 신규 색은 한 번 확정해 인계 | 등록은 TypeScript 객체 편집. 콘텐츠에 문자열을 쓰는 것만으로 정식 등록되지 않음 |
| 프로젝트 이력 | 필수 `name`, `description`; 선택 `period`, `role`, `highlights`, `stack`, `link`. 사용자의 사실과 근거에 맞춰 작성 | `ProjectItem` 형태에 고정 ID가 없음. 요청 식별자를 새 데이터 필드로 추가하지 않음 |
| 경력 | 필수 `company`, `role`, `period`; 선택 `summary`, `points`, `stack` | `CareerItem` 형태에 고정 ID가 없음. 다른 회사·기간의 항목을 같은 이름이라는 이유로 합치지 않음 |

글·Fragment의 신규 카테고리 값은 현재 `CATEGORIES`에 등록된 키를 사용한다. 기존 미등록 카테고리는 관련 없는 수정에서 그대로 보존하고 제약을 보고한다. 예를 들어 제목만 수정하는 요청 때문에 기존 `Infra`를 다른 값으로 바꾸지 않는다. 새 키 등록과 기존 값 이관은 명시적 요청으로 구분한다.

Fragment 관계는 존재하는 ID를 대상으로 `related`, `prerequisite`, `part-of`, `contrasts` 중 하나를 사용한다. 자기 참조를 만들지 않고, 같은 두 카드 사이에는 방향·유형과 무관하게 관계 하나만 둔다. 읽을 때 양쪽에 보이는 관계를 양쪽 파일에 복제하지 않는다. 상대 카드에 저장된 관계의 제거·이동은 그 파일도 변경 대상으로 포함하며 관련 변경을 한 검토 범위로 다룬다.

전체 카드 검증은 중복 ID·없는 대상·자기 참조를 검사한다. 관계 중복은 웹 관계 저장 경로에서 추가 검사하므로 직접 파일 작업에서도 전체 관계를 확인해야 한다. 빌드 성공만으로 모든 관계 정책 검사를 대체하지 않는다.

템플릿·예시는 실제 콘텐츠 수집 경로 밖에 둔다. 기존 공개 예제와 운영 카드를 규약 정리라는 이유로 삭제하거나 비공개로 바꾸지 않는다.

## 6. 저장소와 웹 작업의 승인 경계

### 저장소를 수정하는 AI

1. 저장소·브랜치·작업 폴더·기존 스테이징을 확인한다. 무관한 사용자 변경을 정리하거나 함께 스테이징하지 않는다.
2. 확정 입력과 대상 상태로 변경안을 만들고 관련 자동 검사를 수행한다. 내용 검토에 필요한 준비·미리보기는 로컬에서 수행한다.
3. 실제 신규 작업은 기존 로그 생성 절차로 기록하고 그 작업의 파일만 스테이징한다. 현재 변경에 대한 수동 검증 가이드를 제시한다.
4. 사용자의 명시적 `통과` 뒤 `manual-review.mjs approve`로 승인 상태를 기록하고 검토받은 파일을 그대로 커밋·개발 브랜치 push한다. `main` 병합·운영 배포는 별도 인수와 판정 범위다.

### 웹 화면을 사용하는 AI

현재 웹 화면은 Fragment 작성·수정·삭제·초안 저장·발행만 지원한다. 글·카테고리·프로젝트 이력 관리 요청은 저장소 작업으로 인계한다. 브라우저 조작 권한이나 계정이 없으면 확정 내용과 변경안을 제공하고 실제 저장은 미수행으로 보고한다.

웹의 저장·삭제·초안 제거는 GitHub API 커밋을 만든다. 현재 변경 내용·확인된 대상 ID·관련 카드·초안 브랜치를 사용자에게 보여주고 명시적 `통과`를 받은 뒤 실행한다. 웹 신규 생성은 기존 후보가 없다는 조회 결과와 확정 내용을 제시하고, ID가 첫 저장 때 자동 발급됨을 안내한다. 일반적인 작성 요청이나 이전 항목의 통과를 현재 변경 승인으로 해석하지 않는다. 내용 변경 없는 재조회·비교에는 새 판정을 요구하지 않는다.

웹 저장에는 로컬 Git 훅이 적용되지 않는다. 웹 전용 AI가 로컬 승인 명령을 실행했다고 주장하지 않는다. 확정 입력·판정·저장된 경로·확인한 커밋·미확인 범위를 인계 기록으로 남기고, 로컬 로그·스테이징이 필요한 저장소 개발 작업은 저장소 접근 가능한 작업으로 인계한다.

운영 발행은 저장과 별도다. 현재 발행은 `fragments-draft` 전체를 `main`에 병합하며, 화면의 대기 목록은 카드 파일만 집계한다. 브랜치 전체 변경과 다른 작성자의 초안이 승인 범위에 들어가는지 확인한 뒤 발행 범위에 대한 명시적 판정을 받는다. 전체 변경을 확인할 수 없으면 발행 준비 상태와 미확인 범위를 보고하고 실행하지 않는다.

초안 저장과 운영 반영을 구별한다. 초안 브랜치는 공개 저장소에 있으며 비공개 저장 공간이 아니다. 저장 성공·발행 성공·배포 완료는 각각 확인한 단계만 보고한다. 로컬에서는 운영 OAuth 로그인이 불가능하므로 실제 웹 저장의 검증 장소는 운영 화면이다. 이 규약을 작성하는 현재 작업에서는 운영 쓰기를 하지 않는다.

## 7. 재실행·인계·실패 보고

인계 기록에는 확정 입력, 실제 대상 경로·ID, 확인한 브랜치·기준 상태, 준비한 변경, 자동 검사, 현재 판정, 저장·push·발행·배포 중 확인된 단계, 다음 행동을 남긴다. 요청서와 보고서의 재사용 형식은 계획의 ABI02에서 추가한다.

동일 작업이 중단되었다면 기존 작업 로그를 확인해 이어서 채운다. 아직 승인받지 않은 초안은 현재 작업의 수정으로 다루며 새 로그 항목을 반복 생성하지 않는다. 이미 완료된 동일 입력의 재실행에 변화가 없으면 변경 없음으로 보고하고 새 콘텐츠 커밋·새 개발 로그·STATUS 날짜 갱신을 만들지 않는다. 사용자가 새 범위·새 내용·새 개발 작업을 요청한 경우에는 별도 항목으로 기록한다.

충돌 보고에는 대상, 기대한 기준, 실제 차이, 보존한 입력, 필요한 사용자 선택을 적는다. 네트워크·권한·조회 실패를 중복 대상이나 빈 데이터로 바꾸어 설명하지 않는다. 응답이 유실되면 대상의 최종 내용을 읽어 이미 적용되었는지 확인한 뒤 같은 ID·내용으로 이어간다. 현재 상태를 확인하지 못하면 결과 미확인으로 남긴다.

비밀값과 로그인 토큰을 본문·요청서·로그에 넣지 않는다. 웹 전용 세션에서 전체 저장소 상태를 볼 수 없다는 제약도 숨기지 않는다.

## 8. 판정 예시

다음은 실행 명령이나 실제 운영 데이터가 아닌 입력·결과 설명이다. 요청 식별자는 콘텐츠 메타데이터에 추가하지 않는다.

### 예시 A: 신규 생성

- 입력: `example-create-01`, Fragment 신규 생성, `id=example-term`, `title=예시 개념`, `summary=예시 요약`, `category=AI`, 관계 없음, 확정 본문 있음.
- 상태: 최신 대상 브랜치에 동일 ID·경로가 없고, 제목·별칭 후보 확인도 끝남.
- 결과: `src/content/fragments/example-term.md` 생성 변경안 준비 → 검사 → 현재 변경 판정 → 승인 범위의 저장. 저장 단계에서 발행까지 자동 실행하지 않음.

### 예시 B: 동일 생성 재실행

- 입력: 예시 A와 동일한 요청·ID·본문·메타데이터.
- 상태: 해당 파일의 해석된 데이터와 본문이 확정 입력과 같음.
- 결과: 변경 없음. 새 UUID·새 파일·새 저장 커밋·새 개발 로그를 만들지 않음. 조회하지 못했다면 변경 없음이 아니라 결과 미확인.

### 예시 C: 기존 글의 제목 수정

- 입력: `example-edit-01`, 기존 글 수정, `src/content/blog/example-post/index.md`, 확인한 원문과 기준 상태, 변경 필드는 `title` 하나.
- 상태: 적용 직전 원문이 읽어 둔 기준과 같음.
- 결과: 해당 파일의 제목만 수정한 변경안. 폴더·발행일·태그·본문·이미지·공개 여부를 보존. 재실행 시 제목이 이미 반영되어 있으면 변경 없음.

### 예시 D: 동일 생성 대상의 다른 내용

- 입력: 예시 A의 생성 대상 `example-term`, 다른 요약·본문. 동일 요청 식별자를 재사용했거나 새 생성 요청으로 접수됨.
- 상태: 동일 ID의 기존 내용과 다름.
- 결과: 충돌. 기존 항목 수정인지 별개의 개념 신규 생성인지 확인할 차이를 제시. 덮어쓰기나 새 접미사·UUID로 우회하지 않음.

### 예시 E: 동시 수정

- 입력: 기존 프로젝트 이력의 역할만 수정. 원래 항목의 이름·기간·링크·전체 값을 확인해 둠.
- 상태: 적용 직전에 다른 세션이 같은 항목의 설명을 바꿈.
- 결과: 충돌. 최신 항목과 요청한 역할 변경을 보존하고 차이를 보고. 이전 원문 전체로 다른 세션의 설명을 덮어쓰지 않음.

## 9. 현재 보장 범위와 후속 작업

기존 Fragment 저장 함수는 같은 ID·같은 내용의 저장 재시도를 비교하고, 수정 시 SHA 충돌을 검사한다. 이는 새 세션의 개념 중복 탐색, 카테고리 등록 정책, 프로젝트 식별, 모든 웹 발행 범위를 자동 검사하는 기능과 다르다.

이번 ABR01은 규약 문서의 완료 기준으로 검증한다. 기존 안내 정정은 ABR02, AI 진입점 연결은 ABI01, 요청 지시문·템플릿은 ABI02·ABT01·ABT02, 격리 시나리오 실행 증거는 ABV01·ABV02에서 다룬다. 공통 처리 도구와 신규 웹 관리 기능은 별도 합의할 후속 단계다.
