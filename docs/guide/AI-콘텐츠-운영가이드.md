# AI에게 블로그 작업을 맡기는 방법

AI에게 자연어 요청과 자료를 주고, **확정한 내용·실제 대상·기준 상태를 보존한 뒤 재사용**한다. 신규 작성·수정·재실행의 상세 판단은 [AI 콘텐츠 작업 규약](./AI-콘텐츠-작업규약.md)을 원문으로 사용한다. 이 문서는 평소 위임을 시작하는 안내다.

## 1. 사용할 폴더와 문서

현재 AI-BLOG 자료는 `feat/ai-blog-operations` 개발 브랜치에 있다. 로컬 작업 폴더는 저장소의 `.worktrees/ai-blog-operations/`다. 원래 프로젝트 폴더는 별도 Fragment 작업 상태를 유지하며, 이번 자료를 `main`에 반영하거나 운영 배포한 것은 아니다. 다른 컴퓨터·세션에서는 자료가 있는 브랜치를 먼저 확인한다. 기존 사용자 변경을 처리하려고 임의로 브랜치를 바꾸거나 파일을 정리하지 않는다.

저장소에 접근 가능한 AI는 그 작업 폴더의 `STATUS.md`부터 읽는다. 웹만 사용할 AI에는 필요한 규약 원문과 아래 지시문을 제공한다. 저장소·규약을 읽을 수 없는 AI가 접근 가능하다고 가정하지 않는다.

| 필요할 때 | 사용할 문서 |
| --- | --- |
| 작업 판단의 공통 원문 | [AI 콘텐츠 작업 규약](./AI-콘텐츠-작업규약.md) |
| 복사할 요청·인계·완료 보고 형식 | [AI 콘텐츠 작업 지시문](./AI-콘텐츠-작업지시문.md) |
| 새 파일·항목의 형식 | [템플릿 사용 안내](../../templates/ai-content/README.md) |
| 개발 검증·사용자 판정·Git 저장 절차 | [AGENTS.md](../../AGENTS.md) |
| 프로젝트 구조·명령 | [CLAUDE.md](../../CLAUDE.md) |
| 현재 Fragment 화면의 사용법 | [Fragment 운영 가이드](./Fragment-운영가이드.md) |
| 자동 검사가 확인한 내용과 한계 | [템플릿·빌드 결과](./AI-콘텐츠-검증결과.md), [인계·재실행 결과](./AI-콘텐츠-인계-검증결과.md) |

전체 문서를 매번 읽게 할 필요는 없다. `STATUS.md`에서 작업 범위를 확인하고 규약과 해당 대상의 지시·템플릿만 선택한다. 과거 개발 경위는 로그 메뉴판에서 필요한 항목 하나만 고른다.

## 2. 새 작업을 맡길 때

다음 문장에 요청과 자료를 붙여 전달하면 된다. 요청서의 모든 칸을 사용자가 먼저 채울 필요는 없다. AI가 실제 원본에서 확인 가능한 값을 채우고, 결과를 달라지게 하는 미확정 선택만 질문한다.

```text
이 블로그에서 아래 콘텐츠 작업을 진행해줘.
작업 폴더의 STATUS.md부터 읽고 AGENTS.md와 AI 콘텐츠 작업 규약을 따라줘.
docs/guide/AI-콘텐츠-작업지시문.md의 요청·인계·보고 형식을 사용해줘.
기존 대상을 조회하고 확정 입력·실제 경로/ID·기준 상태를 기록해줘.
현재 변경의 사용자 판정 전에 커밋·push·웹 저장·발행을 수행하지 마.
중단되면 확정 입력과 실제 결과, 미확인 범위, 다음 행동을 인계해줘.

요청: [대상과 원하는 작업]
자료: [본문·출처·프로젝트 사실·이미지 등]
```

웹만 가능한 AI에는 작업 폴더를 읽으라는 문장 대신 규약 원문을 제공한다. 지시문의 웹 작업 절을 함께 전달하고 실제 계정·조회 권한의 제약을 밝혀 둔다.

| 요청 예시 | AI가 준비할 것 |
| --- | --- |
| “이 자료로 블로그 초안을 작성해줘.” | 기존 글 후보 확인, 실제 폴더/index.md·날짜·카테고리·본문·자산·공개 여부 확정 |
| “이 개념을 Fragment로 추가해줘.” | 기존 제목·별칭·ID 후보와 관계 확인, 확정 내용 준비; 특정 ID 요구 시 저장소 경로 사용 |
| “이 이름과 색상으로 카테고리를 추가해줘.” | 기존 키·유사 후보 확인, 확정한 한 항목만 CATEGORIES에 반영할 변경안 |
| “제공한 사실로 프로젝트 이력을 추가해줘.” | 기존 항목 확인, 현행 ProjectItem 형태의 값 준비; 사용자가 주지 않은 성과 생성 금지 |

색상·화면의 시각 선택이 필요하면 저장소의 캡처 비교 절차를 따른다. 템플릿의 미확정 색이나 날짜를 임의 값으로 등록하지 않는다. 웹에서 글·카테고리·프로젝트를 요청하면 저장소 작업으로 인계한다.

## 3. 중단한 작업이나 같은 요청을 다시 맡길 때

앞 세션의 확정 요청과 인계 기록을 함께 넘긴다. “아까 한 작업 이어서 해줘”만 전달하면 대상·날짜·본문·승인 범위가 빠질 수 있다. [인계 형식](./AI-콘텐츠-작업지시문.md#6-세션-인계-지시문과-기록)을 사용한다.

```text
앞 세션의 작업을 이어서 진행해줘.
아래 확정 요청과 인계 기록을 실제 대상·브랜치·최신 내용과 대조해줘.
같은 내용이 이미 있으면 변경 없음으로 보고하고 새 파일·ID·커밋·로그를 만들지 마.
기준과 다른 내용이면 내 입력과 최신 원본을 보존한 채 충돌을 보고해줘.
앞 보고의 승인 문자열만으로 새 쓰기를 승인된 것으로 해석하지 마.

확정 요청: [원문 또는 읽을 수 있는 원본 참조]
인계 기록: [앞 세션이 남긴 기록]
```

확정 입력 파일을 넘길 때는 원문을 보존한다. 선택적인 SHA-256 지문은 파일 변경 여부를 확인하는 자료다. 실제 대상 버전이나 사용자 판정의 증거와 구별한다. 인계 기록에 참조만 있고 파일을 읽을 수 없으면 원문을 다시 제공한다.

| AI의 보고 상태 | 다음 행동 |
| --- | --- |
| 준비 완료·판정 대기 | AI가 연 검토 자료와 사람이 판단할 내용 확인 → 해당 변경에 통과 또는 수정 판정 |
| 변경 없음 | 확인한 내용·대상·저장 단계를 확인하고 종료; 같은 쓰기나 새 개발 로그를 요구하지 않음 |
| 충돌·대상 모호함 | 후보·기준 차이와 보존한 입력을 보고 정확한 대상·원하는 수정 확정 |
| 결과 미확인 | 최신 상태 조회부터 재시도; 새 UUID·새 파일로 우회하지 않음 |
| 인계 필요 | 확정 내용과 미수행 범위를 저장소 접근 가능한 AI에게 전달 |

사용자가 판정하는 것은 문구·내용·방향·실제 화면 등 사람이 보아야 아는 항목이다. 자동 검사 실행과 diff 확인은 AI가 수행하고 결과를 요약한다. 확인이 필요한 파일은 AI가 직접 연다.

## 4. 저장과 공개 결과를 확인할 때

저장소 변경은 현재 변경의 통과 뒤 승인 기록·개발 커밋·요청 범위의 push를 수행한다. 개발 브랜치 push는 운영 배포와 구별한다. 웹 Fragment의 저장은 GitHub API 커밋을 만들며 저장 전 판정이 필요하다. 운영 발행은 초안 저장과 별도로 브랜치 전체 변경 범위를 확인하고 판정한다.

보고서에서 실제 ID·경로·커밋·push 확인·발행 커밋·배포 확인 중 존재하는 증거만 확인한다. 초안 저장 성공을 운영 배포 성공으로 읽지 않는다. 로컬 Git 훅은 웹 쓰기를 검사하지 않으며, 로컬에서는 운영 OAuth 로그인이 불가능하다. 웹 초안 브랜치는 비공개 공간이 아니다.

## 5. 검사와 규칙을 유지할 때

AI가 변경 영향에 맞춰 관련 검사를 실행한다. `npm test`는 단위·통합과 인계 검사를, `npm run test:ai-content:build`는 합성 데이터의 실제 빌드 4건을 실행한다. 타입 검사와 일반 빌드 명령은 `npm run check`, `npm run build`다. 검증용 명령은 콘텐츠를 등록하는 명령이 아니다.

콘텐츠 정책이 바뀌면 공통 규약을 먼저 고치고 관련 지시문·템플릿·검사를 함께 확인한다. AI별 지침에 상세 규칙을 복제하지 않는다. 현재 스키마가 검사하지 않는 등록 카테고리·전체 관계 정책은 규약대로 별도 확인한다.

이번 1차는 내부 규정·지시문·템플릿·검증 체계를 마련했다. 모든 AI의 자동 중복 방지나 동일 자연어에서 동일 본문 생성은 보장하지 않는다. 자동 처리 도구와 웹 작성 확장은 [최종 보고서의 후속 후보](../AI-블로그-작업-최종보고서.md#후속-후보)에 따라 별도 계획·합의 후 진행한다.
