## 무엇이 가능해졌는가

저장소를 지정해 글·Fragment를 읽고, 오류가 있으면 파일 경로·필드·규칙·이유를 확인할 수 있다. 이전에는 검사 모듈을 호출하는 코드를 작성해야 했지만, 이제 터미널 명령으로 실행한다. 검사 대상과 설정을 읽기만 하며 원문 수정·예외 추가·Git 승인·커밋·발행은 수행하지 않는다.

사람이 읽는 안내와 AI·후속 프로그램이 읽는 JSON을 제공한다. 실패는 화면에 문구만 남기는 것으로 끝내지 않고 비정상 종료 코드로 전달한다. Hook·CI가 이 결과를 사용해 저장을 차단하도록 연결하는 작업은 ACTH01에 남아 있다.

## 준비와 실행

Node.js와 프로젝트 의존성이 설치된 작업 폴더에서 실행한다. 이번 검증 환경은 Windows와 Node.js 24이며 다른 OS에서의 실행은 이번 작업에서 확인하지 않았다. 브라우저·계정·OAuth·개발 서버는 필요하지 않다.

```powershell
Set-Location 'C:\Users\user\Desktop\github\Blog\.worktrees\ai-content-tools'
npm run content:check
```

다른 저장소 사본을 검사하려면 경로를 명시한다. 공백이 있는 경로는 따옴표로 감싼다. 상대 경로는 현재 터미널의 작업 폴더를 기준으로 해석한다.

```powershell
node scripts/content-check.mjs --root 'C:\path\to\repository'
```

`--root`를 생략하면 스크립트가 속한 저장소를 검사한다. 다른 폴더에서 스크립트의 절대 경로로 실행하더라도 기본 검사 대상이 바뀌지 않는다.

```powershell
node scripts/content-check.mjs --help
node scripts/content-check.mjs --json
```

순수 JSON이 필요하면 위의 `node ... --json`을 사용한다. npm으로 실행하면 npm 자체의 명령 안내가 JSON 앞에 출력될 수 있다. `--fix`·`--apply`·알 수 없는 옵션·중복 옵션·값 없는 `--root`는 사용 오류다. `--help`는 단독으로 사용한다.

## 무엇을 읽는가

| 입력 | 읽는 범위 | 포함하지 않는 대상 |
| --- | --- | --- |
| `src/content/blog` | 하위 폴더의 `index.md`, draft 포함 | 평면 글 `.md`, 숨김 파일·숨김 폴더 |
| `src/content/fragments` | 하위 폴더의 `.md` | 숨김 파일·숨김 폴더 |
| `src/consts.ts` | `export const CATEGORIES`의 정적 키·문자열 값 | 설정 코드 실행, 프로젝트·경력 데이터 검사 |
| `config/content-policy-baseline.json` | 버전과 명시적 기존 예외 | 새 예외 자동 수집·자동 삭제 |

검사 경로는 위 저장소 구조로 고정한다. 빌드 테스트용 `FRAGMENT_CONTENT_DIR` 환경변수로 다른 폴더를 선택하지 않는다. 실제 소스 수집 설정이 바뀌면 검사기의 수집 계약도 함께 조정해야 한다.

필수 설정·입력 폴더가 없으면 빈 저장소로 성공 처리하지 않는다. 링크·junction을 포함한 입력도 명확히 거절한다. Astro가 처리할 수 있는 모든 파일 배치를 지원한다는 의미는 아니며, 지원 범위 밖을 읽지 않은 채 성공했다고 보고하지 않기 위한 제한이다.

CATEGORIES는 TypeScript 구문 구조를 분석해 읽는다. 계산식·함수 호출·spread·중복 키·문자열이 아닌 값은 실행하거나 추측하지 않고 `registry.invalid`로 반환한다. 설정 파일의 다른 실행문도 실행하지 않는다. 예외 JSON의 문법 오류·중복 키·잘못된 버전은 `baseline.invalid`다.

## 결과를 읽는 방법

현재 저장소에서는 글 13개·Fragment 3개를 수집하고, 오류 0건·기존 예외 4건·미사용 예외 0건을 보고한다. 여기서 통과는 기존 예외까지 없다는 뜻이 아니라, 승인된 예외 외의 위반이 없다는 뜻이다.

| 표시 | 의미 | 판단 예시 |
| --- | --- | --- |
| 검사 통과/실패 | 오류 유무에 따른 최종 결과 | 새 미등록 카테고리는 실패 |
| 콘텐츠 수집 완료/미완료 | 입력을 끝까지 읽었는지 | 폴더 누락이면 미완료, 개수는 중단 전 읽은 문서 수 |
| 오류 | 통과를 막는 진단 | 파일·규칙·필드·이유 제공 |
| 기존 예외 | 정확한 규칙·경로·값이 일치한 문제 | 기존 Infra 4건은 별도 표시 후 허용 |
| 미사용 예외 | 이번 입력에서 발생하지 않은 예외 | 오래된 항목을 검토할 단서, 자동 삭제 없음 |
| 관계 검사 수행/미수행 | 전체 Fragment 대상을 확정해 관계를 검사했는지 | 중복 ID나 형식 오류로 대상을 확정하지 못하면 미수행 |

예를 들어 `src/content/blog/example/index.md`에 `category: Unknown`을 넣으면 해당 경로와 `category.unregistered`, `category`, 미등록 값의 이유를 함께 출력한다. YAML 중복 키처럼 원문 위치를 알 수 있는 진단에는 줄·열도 포함한다. 모든 진단에 줄 번호를 추측해 붙이지는 않는다.

입력 읽기나 설정 해석이 실패하면 먼저 발견한 문제를 반환한다. 이를 고친 뒤 재실행해야 다른 문제까지 확인할 수 있다. 수집이 완료돼도 중복 ID나 없는 관계 대상 등의 콘텐츠 오류가 있을 수 있으므로 수집 상태만으로 통과를 판단하지 않는다.

JSON에서는 `ok`, `summary`, `diagnostics`, `knownIssues`, `unusedExceptions`, `collectionComplete`, `graphChecked`로 같은 정보를 전달한다. 진단의 세부 사례와 기존 예외 기준은 [검사 모듈 개발 현황](./AI-콘텐츠-검사기-개발현황.md)을 참고한다.

## 종료 코드

| 코드 | 의미 | 예시 |
| --- | --- | --- |
| 0 | 검사 통과 또는 도움말 표시 | 기존 예외만 있는 저장소도 통과 |
| 1 | 콘텐츠·설정·입력 읽기 오류 | 중복 ID, YAML 오류, 설정 파일 누락 |
| 2 | 명령 사용 오류 | 미지원 옵션, 경로 값 누락 |

PowerShell에서는 명령 실행 직후 `$LASTEXITCODE`로 확인할 수 있다. 도움말은 검사 결과가 아니므로 자동 검사에는 `--help`를 사용하지 않는다.

## C1에서 사람이 확인할 흐름

에이전트가 수집 범위를 갖춘 정상·오류 예시 저장소를 `.fragment-test/` 아래 별도 폴더에 준비한다. 실제 운영 글을 고치거나 계정을 연결할 필요가 없다. 확인용 폴더의 실제 경로와 복사할 실행 명령은 별도로 연 임시 확인 안내에 제공한다. 임시 예시는 버전 관리하지 않으며 다른 체크아웃에서 필요하면 다시 준비한다.

1. 정상 예시 명령 실행 → 통과 안내와 글·Fragment 개수 확인.
2. 오류 예시 명령 실행 → 실패 안내와 잘못된 파일·category·Unknown 이유 확인.
3. 실제 저장소의 `npm run content:check` 실행 → 오류와 기존 Infra 예외가 구별되는지 확인.

자동 검사 성공 여부나 코드 diff를 사용자가 검증할 필요는 없다. 이번 확인 대상은 실제 명령 사용 흐름과 진단 문구만 보고 수정할 대상을 이해할 수 있는지다. JSON과 종료 코드의 일관성·반복 실행·파일 보존은 에이전트가 자동 검사했다.

## 확인한 범위와 남은 일

ACTC01 검증 당시 CLI 통합 검사 39개를 포함한 전체 테스트 251개 통과, 타입 오류·경고 0건, 기존 힌트 5개를 확인했다. 일반 빌드는 11페이지·18이미지로 성공했다. 반복 실행에서 결과·파일 목록·바이트가 유지됐으며 실제 콘텐츠도 읽기 전용으로 검사했다.

검사는 읽은 자료의 오류를 판단한다. 외부 편집기가 검사 중 파일을 바꾸면 서로 다른 시점의 내용을 읽을 수 있으므로 검사 중 편집을 피하고 변경 후 다시 검사해야 한다. 변경 적용 직전의 기준 확인·잠금·복구는 이후 적용 도구의 작업이다.

글·Fragment·카테고리·프로젝트의 생성·부분 수정·재시도 기록은 아직 제공하지 않는다. 모든 AI의 파일 쓰기 권한을 통제하거나 사람의 통과 판정을 인증하는 기능도 아니다. C1 확인 뒤 ACTC02에서 확정 요청·변경계획·재시도 기록 계약을 진행한다.
