# Fragments 운영 가이드

웹에서 개념 카드를 쓰고 공개하는 방법, 각 구성 요소가 실제로 어떻게 동작하는지, 그리고 만들면서 겪은 시행착오와 그때 내린 선택을 함께 담는다. 블로그 글(마크다운) 운영은 `운영가이드.md`를 따른다.

- 공개 주소: `https://avocadosmasher.github.io/fragments/`
- 저장소: `avocadosmasher/avocadosmasher.github.io`
- 공개 브랜치: `main` / 초안 브랜치: `fragments-draft`

---

## 1. 평소 작업 흐름

1. `/fragments/`에서 **새 카드** → **GitHub 로그인**. 처음이면 GitHub 승인 화면이 뜬다.
2. 카드를 쓰고 저장한다. 저장은 **초안 브랜치에만** 쌓이고 사이트는 그대로다. 배포도 돌지 않는다.
3. 필요한 만큼 반복한다. 저장할 때마다 "발행 대기 카드 N개."가 올라간다.
4. **목록 보기**로 무엇이 대기 중인지 확인한다. 빼고 싶은 카드는 **제거**를 누른다.
5. **발행**을 누르면 초안이 `main`에 합쳐지고 배포가 **한 번** 돈다.
6. 배포 상태 줄이 "배포 중입니다." → "마지막 배포가 끝났습니다."로 바뀌면 사이트에 반영된 것이다. 보통 3~4분 걸린다.

### 알아 둘 점

- 로그인은 **탭을 닫을 때까지** 유지된다. 새로고침해도 풀리지 않는다. 공용 PC에서는 로그아웃한다.
- 저장하지 않은 **작성 중 입력**은 새로고침하면 사라진다. 저장한 카드는 초안 브랜치에 남는다.
- 로그인하지 않은 방문자에게는 발행 전 초안이 보이지 않는다. 다만 초안 브랜치는 공개 저장소에 있으므로 **저장소를 직접 열면 누구나 볼 수 있다.** 비공개가 필요한 내용은 쓰지 않는다.
- 카드를 만들었다가 목록에서 제거하면 커밋은 남지만 내용 차이가 없으므로 "발행할 변경이 없습니다."가 된다. 그 커밋들은 다음 발행 때 함께 합쳐지고 사이트에는 영향이 없다.

### 막혔을 때

| 증상 | 뜻과 대처 |
| --- | --- |
| 저장 버튼이 비활성 | 로그인 전이다. **GitHub 로그인**을 먼저 누른다. |
| "다른 곳에서 카드가 변경되었습니다" | 다른 탭·기기에서 같은 카드를 바꿨다. 입력을 복사해 두고 새로고침한 뒤 다시 수정한다. |
| "이 카드를 참조하는 카드가 있어 삭제할 수 없습니다" | 안내에 나온 카드를 먼저 수정해 관계를 지우고 다시 삭제한다. |
| "로그인이 만료되었습니다" | 실패 안내의 **다시 로그인**을 누르면 입력을 유지한 채 이어서 저장할 수 있다. |
| "최신 카드를 확인하지 못했습니다" | GitHub 조회가 실패했다. **↻ 새로고침**을 누른다. 반복되면 잠시 뒤 다시 시도한다(아래 API 한도 참고). |
| "마지막 배포가 실패했습니다" | 사이트는 **이전 내용 그대로**다. 배포 기록 링크에서 실패한 검사를 확인한다. 콘텐츠 문제면 카드를 고쳐 다시 발행한다. |
| 발행 버튼이 없음 | 발행할 카드 변경이 없다는 뜻이다. |

## 2. 구성 요소와 동작 원리

### 2-1. 브랜치 두 개

```
fragments-draft ──(발행: merge)──▶ main ──(Actions)──▶ GitHub Pages
      ▲                                  │
      └── 웹에서 저장/수정/삭제           └── 방문자가 보는 사이트
```

- 웹에서의 모든 쓰기는 `fragments-draft`로 간다.
- 발행은 `POST /repos/.../merges`(base `main`, head `fragments-draft`) 한 번이다. 그래서 여러 번 저장해도 배포는 한 번이다.
- 발행 후 초안 브랜치는 `main`보다 한 커밋 뒤처진 상태가 된다(병합 커밋은 `main`에만 생긴다). 정상이며, 다음 발행이 이를 흡수한다.

### 2-2. 로그인 (OAuth Worker)

- Cloudflare Worker `fragment-oauth`가 GitHub OAuth를 중계한다. 테스트용 `fragment-oauth-test`와 완전히 분리돼 있다.
- 공개 변수: `GITHUB_CLIENT_ID`, `CMS_ORIGIN`(`https://avocadosmasher.github.io`), `OAUTH_CALLBACK_URL`, `GITHUB_SCOPE`(`public_repo`).
- 비밀값: `GITHUB_CLIENT_SECRET`, `OAUTH_STATE_SECRET`. 저장소·정적 산출물·대화에 넣지 않는다.
- 로그인 요청은 PKCE(S256)와 서명된 state를 쓰고, `__Host-` 접두사의 HttpOnly·Secure·SameSite=Lax 쿠키로 브라우저를 묶는다. 로그인 세션은 Durable Object에 10분만 살고 한 번만 소비된다.
- Worker는 `CMS_ORIGIN` 하나만 허용한다. 그래서 로컬(`127.0.0.1`)에서는 운영 로그인을 할 수 없다.

### 2-3. 토큰 보관

- 발급된 토큰은 그 탭의 `sessionStorage`에만 둔다. 키는 `fragment-writer:<저장소>:<브랜치>`다.
- 페이지가 열리면 저장된 토큰으로 저장소 쓰기 권한을 **한 번 확인한 뒤에만** 로그인 상태로 복원한다.
- 로그아웃, 인증·권한 실패, 탭 종료 시 지워진다. `localStorage`에는 절대 쓰지 않는다.

### 2-4. 카드 읽기

- 화면의 카드 목록은 두 겹이다. **빌드 시점의 스냅샷**(HTML에 포함)과 **실시간 조회**다.
- 실시간 조회는 브랜치의 Git 트리를 한 번 읽고, 카드 파일의 blob을 4개씩 묶어 읽는다. 모두 같은 리비전이라 중간 상태가 섞이지 않는다.
- 비로그인 방문자는 `main`을, 로그인한 작성자는 `fragments-draft`를 읽는다.
- 로그인 상태면 조회에도 토큰을 쓴다. 익명 조회는 IP당 시간당 60회 한도라 금방 소진되기 때문이다.
- 조회가 실패하면 빌드 스냅샷을 유지하고 안내를 띄운다. **↻ 새로고침**으로 다시 시도한다.

### 2-5. 저장·수정·삭제

- 새 카드와 단순 수정은 Contents API(`PUT`)로 커밋한다. 파일 경로는 `src/content/fragments/<id>.md`이고 **ID는 파일명과 프론트매터에 고정**된다. 제목을 바꿔도 파일은 그대로다.
- 관계가 바뀌는 저장과 삭제는 트리 전체를 한 리비전으로 읽어 검증한 뒤 커밋한다. 없어진 대상이나 자기 참조, 같은 두 카드 사이의 중복 관계를 막는다.
- 수정·삭제는 읽어 둔 파일 버전(SHA)과 현재 버전을 비교한다. 다르면 덮어쓰지 않고 충돌로 알린다.
- 다른 카드가 참조하는 카드는 삭제를 막고 참조 카드 제목을 안내한다.
- 응답이 유실된 경우(네트워크 끊김 등)에는 같은 내용인지 확인하고, 이미 저장돼 있으면 두 번 쓰지 않는다.

### 2-6. 발행 대기 목록과 제거

- 대기 여부는 `compare main...fragments-draft`의 **카드 파일 변경**으로만 판단한다. 커밋 수는 쓰지 않는다.
- 목록의 각 줄은 카드 제목, 변경 종류(새 카드·수정·삭제), 제거 버튼이다.
- **제거**는 그 카드만 공개본 상태로 되돌린다. 새 카드면 초안에서 지우고, 수정이면 공개본 내용으로 덮고, 삭제였다면 공개본 카드를 되살린다. 다른 초안은 건드리지 않는다.

### 2-7. 배포 상태

- `main`의 `deploy.yml` 최신 실행을 읽어 배포 중·완료·실패·취소를 보여 준다.
- 발행하면 **그 병합 커밋의 실행**을 지목한다. 실행이 나타날 때까지 5초 간격으로 기다리고, 시작되면 15초 간격으로 완료까지 따라간다. 직전 실행을 보고 끝났다고 오해하지 않는다.
- 완료되면 카드 목록과 대기 목록을 자동으로 다시 불러온다.
- 연속으로 발행하면 대기 중이던 실행이 취소될 수 있다. 실패가 아니라 다음 실행이 대신한다는 뜻이다.
- 상태를 읽지 못하면 숨기지 않고 사유와 배포 기록 링크를 남긴다.

### 2-8. 빌드와 배포 게이트

- 저장 기능은 빌드할 때 `FRAGMENT_WRITER_OAUTH_ORIGIN`이 있을 때만 켜진다. 이 값은 `deploy.yml`(= `main` 배포 경로)에서만 전달한다. 로컬 빌드나 PR 검사 빌드에서는 작성 창이 미리보기로만 동작한다.
- 배포 경로는 검사를 모두 통과한 `dist/`를 그대로 올린다. 검사가 실패하면 배포 job이 실행되지 않고 **이전 사이트가 유지된다.**
- "Check production writer" 단계가 운영 산출물에 저장 설정이 실제로 들어갔는지 확인한다.
- `fragments-draft` push는 CI를 돌리지 않는다. 카드 저장마다 전체 검사를 돌리지 않기 위해서다. 검사는 발행 시점의 배포 경로에서 수행한다.

### 2-9. 검사 모음

| 명령 | 범위 |
| --- | --- |
| `npm test` | 단위·통합(스키마, 저장, 관계, 삭제, 세션, 발행, 배포 상태) |
| `npm run test:e2e` / `test:e2e:preview` | 개발 서버 / 빌드 산출물에서의 조회·검색·팝업·그래프 |
| `npm run test:h01` | 모바일·테마·접근성(25개 fixture) |
| `npm run test:h02` | 500개 카드·1,500개 관계 성능 |
| `npm run test:oauth` | 로그인·저장·수정·삭제·관계(모의 GitHub) |
| `npm run test:draft` | 초안 브랜치·발행·배포 상태(운영 모드 빌드) |

## 3. 시행착오와 선택

### 3-1. 편집 화면을 직접 만들기로 한 것

외부 CMS(Decap) 화면을 먼저 붙였지만, 권한 오류 상황에서 버튼이 비활성으로 굳는 등 우리가 손댈 수 없는 부분이 많았다. 블로그와 같은 디자인·문구를 쓰기도 어려웠다. 그래서 카드 작성·수정·관계·삭제를 블로그 전용 폼으로 다시 만들었다. 대신 GitHub API 호출과 충돌 처리를 직접 책임지게 됐고, 그만큼 테스트를 두껍게 깔았다. Decap 화면(`/admin/`)은 한동안 꺼진 채 남아 있다가 2026-09-24에 완전히 걷어냈다(K01).

### 3-2. 운영 저장소에 실수로 쓰지 않도록 막아 둔 것

개발 중에는 설정 검사가 운영 저장소와 `main`을 **거부**하도록 만들었다. 덕분에 테스트가 운영 콘텐츠를 건드릴 위험이 없었다. 운영 연결 단계에서 이 벽을 없애는 대신, `production: true`를 **명시**해야만 통과하도록 바꿨다. 지금은 여기에 "초안 브랜치에만 쓴다"는 조건이 더해져 있다.

### 3-3. 테스트 관리 화면 업로드 실패 두 번

ZIP을 올렸는데 사이트가 404였다. PowerShell이 ZIP 항목을 역슬래시 경로로 기록해 파일이 폴더로 인식되지 않은 것이 원인이었다. POSIX 경로로 다시 묶었더니 이번엔 화면이 로딩에서 멈췄다. 진입 스크립트가 부르는 청크 하나가 ZIP에 빠져 있었다. 이후로는 **ZIP 안의 정적 import가 모두 해소되는지 검사**하고 올린다.

### 3-4. 서명 키 생성 실패를 지나칠 뻔한 것

`OAUTH_STATE_SECRET`을 만들 때 첫 난수 API가 실패했는데도 파이프라인이 계속 진행돼 임시 값이 등록됐다. 바로 호환되는 API로 새 32바이트 난수를 만들어 교체했다. 그 값은 OAuth 코드 배포 전에 교체돼 실제 인증에 쓰이지 않았다. 이후 비밀값 생성은 **실패하면 즉시 멈추는 방식**으로 다룬다.

### 3-5. 그래프 성능: 보기 좋은 배치를 지키기로 한 것

CI 러너에서 그래프 렌더가 2.2초로 목표(2초)를 넘겼다. 원인을 측정하니 배치 계산이 절반 이상이었다. 빠른 배치 옵션(`quality: 'draft'`)을 캡처로 비교했더니 카테고리 구분이 사라지고 허브가 가장자리에 몰려 이름이 겹쳤다. **읽기 쉬운 배치를 성능보다 우선**해 이 옵션은 버렸다. 대신 간격 보정 계산을 337ms → 145ms로 줄이고(결과 좌표는 동일함을 확인), CI 한도만 3초로 두었다. 개발 PC 기준 실측은 검색 p95 2.7~2.9ms, 그래프 881~1,077ms다.

### 3-6. 그래프가 계산되는 동안의 키보드 이동

노드 목록 버튼은 그래프 계산 전에 만들어지므로, 계산 중에 포커스를 옮기면 강조와 안내가 나오지 않았다. 느린 러너에서 드러난 실제 접근성 결함이라, 그래프가 준비되면 **그때 포커스가 있는 노드를 다시 강조**하도록 고쳤다.

### 3-7. 테스트가 운영 카드에 매달려 있던 문제 (가장 컸던 사고)

운영에서 카드(HPA)를 삭제하자 이후 **모든 배포가 실패**했다. 테스트가 운영 카드 파일과 그 내용을 고정 데이터로 쓰고 있었기 때문이다. 웹 작성 기능은 작성자가 카드를 마음대로 고치라고 만든 것인데, 고칠수록 배포가 막히는 구조였다.

선택지는 두 가지였다. (A) 씨앗 카드를 지우지 못하게 운영 규칙으로 막기, (B) 테스트가 카드 이름을 박아 넣지 않게 고치기. **B를 골랐다.** 규칙으로 사람을 묶으면 언젠가 다시 깨지고, 그 대가로 배포 전체가 멈추기 때문이다. 지금 미리보기 테스트는 배포될 산출물의 카드 데이터에서 검색어·관계·대상 카드를 **읽어서** 검사하고, 카드가 없거나 관계가 없으면 해당 검사를 건너뛴다. OAuth 테스트는 자체 고정 데이터를 쓴다. 세 가지 콘텐츠 상태(현재 카드, 씨앗 카드 없음, 카드 0개)로 검증했다.

### 3-8. 배포 타이밍: 초안 브랜치를 고른 이유

저장할 때마다 배포가 돌아 연속 작업이 불편했다. 세 가지를 검토했다.

| 안 | 내용 | 판단 |
| --- | --- | --- |
| 초안 브랜치 + 발행 버튼 | 저장은 별도 브랜치, 발행 시 한 번 배포 | **채택.** 새로고침해도 초안이 남고, 실수로 공개될 일이 없다 |
| main에 저장 + 수동 배포 | 자동 배포만 끄고 버튼으로 배포 | 저장 내용이 배포 전에도 저장소에 공개되고, 다른 이유로 main이 갱신되면 함께 나간다 |
| 브라우저에 모았다 한 번에 커밋 | 여러 변경을 한 커밋으로 | 새로고침·기기 변경 시 작업이 날아가고 카드별 이력이 남지 않는다 |

### 3-9. 로그인 유지 범위

새로고침하면 로그인이 풀려 불편했다. 탭 세션(`sessionStorage`), 브라우저 영구(`localStorage`), 시간 제한 중에서 **탭 세션**을 골랐다. 쓰기 권한이 있는 토큰이 기기에 오래 남지 않으면서, 실제 불편(새로고침)은 해결되기 때문이다. 이때 "토큰을 어떤 저장소에도 두지 않는다"던 기존 테스트를 "`localStorage`에는 두지 않고 로그아웃하면 지운다"로 바꿨다. **규칙이 바뀌었으면 테스트도 그 의도에 맞게 고치고 기록한다.**

### 3-10. 발행 대기 개수가 틀렸던 것

카드를 만들었다 제거하면 커밋은 2개 남지만 내용 차이는 없다. 그런데 커밋 수를 대기 건수로 표시해 "발행 대기 2건"이 떴고, 목록 버튼은 카드 변경 기준이라 숨어서 서로 어긋났다. **사용자에게 의미 있는 단위는 커밋이 아니라 카드**라는 판단으로, 대기 여부와 개수를 카드 파일 변경만으로 계산하게 고쳤다.

### 3-11. 배포 상태가 안 보이던 것과 안 바뀌던 것

- 조회에 실패하면 줄을 **숨기도록** 해 두어 화면에 아무 흔적이 없었다. 원인 파악도 불가능했다. 지금은 사유와 배포 기록 링크를 남긴다.
- 발행 직후 상태를 읽으면 새 실행이 아직 큐에 없어 **직전 실행**이 잡혔다. 그게 완료 상태면 추적을 멈춰 버렸다. 지금은 발행한 병합 커밋을 기억해 그 실행이 나타날 때까지 기다린다.

### 3-12. 새로고침하면 초안 카드가 사라지던 것

카드 조회가 로그인 토큰 없이 익명으로 나가고 있었다. 익명 한도(IP당 시간당 60회)를 소진하면 조회가 실패하고 화면이 빌드 시점의 공개본으로 돌아갔다. 발행 대기 목록은 토큰을 써서 정상이었기에 둘이 어긋나 보였다. 로그인 상태에서는 **조회에도 토큰을 쓰도록** 고쳤다.

### 3-13. 한국어 줄바꿈

모바일에서 "발행 / 대기 카드", "반영 / 됩니다", "배포 기록 보 / 기"처럼 끊겼다. 글자 크기를 줄이는 대신 줄바꿈 규칙을 고쳤다. 어절 단위 줄바꿈(`word-break: keep-all`), 링크·버튼 글자 줄바꿈 금지, 안내 문구를 문장 단위로 묶기까지 적용했다. 문장 사이 공백은 요소 바깥의 **텍스트 노드**로 둬야 한다. 요소 안에 넣으면 데스크톱에서 공백이 사라지고, 여백(`margin`)으로 주면 줄이 바뀔 때 다음 줄이 들여쓰기된다. 두 번 헛짚고 나서 정리한 결과다.

### 3-14. 다시 불러오기 버튼

실패했을 때만 나타났다 사라지는 문구 버튼이 어색했다. 아이콘만·아이콘+글자·전환 버튼 안쪽 세 시안을 캡처로 비교해 **아이콘 + "새로고침" 글자**를 골랐다. 무슨 버튼인지 바로 읽히고, 뷰 전환과는 다른 기능임이 구분되기 때문이다. 이제 항상 같은 자리에 있고, 읽는 동안 아이콘이 돌며, 실패해도 사라지지 않는다.

### 3-15. 검증 절차 자체의 조정

처음에는 모든 작업마다 사용자가 자동 검사까지 직접 돌려 확인했다. 반복해도 결과가 같은 검사와 코드 확인은 에이전트가 맡고, **사람은 화면의 심미적 판단과 실제 동작 확인에 집중**하도록 절차를 바꿨다(`AGENTS.md`). 화면이 바뀌면 캡처를 먼저 보여 주고 고르게 한다.

## 4. 한계와 주의

- **초안은 비공개가 아니다.** 사이트에는 안 보이지만 공개 저장소의 브랜치에 있다.
- **토큰이 탭 세션 동안 브라우저에 있다.** 공개 저장소 쓰기 권한 범위이며, 공용 PC에서는 로그아웃한다.
- **GitHub API 한도.** 비로그인 조회는 IP당 시간당 60회라 쉽게 소진된다. 자세한 셈은 아래 **4-1**에 있다.
- **발행에서 배포 반영까지 3~4분**이 걸린다. 즉시 반영이 아니다.
- **연속 발행 시 중간 배포가 취소**될 수 있다. 마지막 발행이 반영되면 정상이다.
- **로컬에서는 운영 로그인을 할 수 없다.** Worker가 운영 도메인만 허용한다. 로컬 확인은 빌드 산출물과 테스트로 한다.
- 대기 목록은 GitHub 비교 API를 쓰며, 변경 파일이 아주 많은 경우(수백 개) 목록이 잘릴 수 있다. 카드 단위 작업에서는 문제가 되지 않는다.

### 4-1. GitHub API 한도 자세히

**한도는 두 종류다.**

| 구분 | 한도 | 적용 대상 |
| --- | --- | --- |
| 기본(비로그인) | **IP당 시간당 60회** | 로그인 전 방문자의 카드 조회 |
| 기본(로그인) | **계정당 시간당 5,000회** | 로그인한 작성자의 모든 호출 |
| 부가 한도(secondary) | 쓰기 요청 분당 약 80회·시간당 약 500회, 동시 요청 100건 | 저장·삭제·발행 |

부가 한도는 문서화된 정확한 값이 아니라 GitHub이 상황에 따라 적용하는 보호 장치다. 사람이 손으로 카드를 쓰는 속도로는 닿지 않는다.

**작업 하나가 요청 몇 회를 쓰는가.** `N`은 카드 개수다(현재 3장).

| 작업 | 요청 수 | 내역 |
| --- | --- | --- |
| 카드 목록 한 번 불러오기 | **1 + N** | 트리 1회 + 카드마다 blob 1회 |
| 새 카드·단순 수정 저장 | **3** | 권한 확인 + 기존 파일 확인 + 커밋 |
| 관계가 바뀌는 저장·삭제 | **7 + N** | 권한 확인, 브랜치·커밋 조회, 검증용 트리 조회(1+N), 트리·커밋 생성, 브랜치 이동 |
| 발행 대기 확인 | **1** | `compare` 1회 |
| 발행 | **1** | `merges` 1회 |
| 배포 상태 확인 | **회당 1** | 실행이 잡히기 전 5초 간격, 진행 중 15초 간격 |

**그래서 이런 결과가 된다.**

- **비로그인 방문자**는 카드 30장이면 목록 한 번에 31회를 쓴다. 같은 IP에서 두 번 열면 한도의 대부분이 사라진다. 이것이 로그인 상태에서 조회에도 토큰을 쓰도록 고친 이유다(3-12).
- **로그인한 작성자**는 5,000회를 쓴다. 발행 한 번을 끝까지 지켜보면 배포 상태 확인에만 15~20회가 들지만, 하루 작업량으로 한도에 닿기 어렵다.
- **카드가 늘수록 조회 비용이 선형으로 는다.** 500장이면 목록 한 번에 501회다. 로그인 상태에서는 여유가 있지만, 비로그인 방문자에게는 빌드 시점 스냅샷이 사실상의 기본 화면이 된다.

**한도에 걸리면 무엇이 보이는가.**

- 쓰기 중이면 "GitHub 요청 한도에 도달했습니다. 입력은 유지됩니다."가 뜬다. **작성 중인 내용은 지워지지 않는다.** 잠시 기다렸다 같은 작업을 다시 누르면 된다.
- 조회 중이면 "최신 카드를 확인하지 못했습니다."가 뜨고 화면은 **마지막 배포본**을 유지한다. 빈 화면이 되지는 않는다.
- 한도는 시간 창이 지나면 저절로 회복된다. 응답이 429이거나, 403이면서 남은 횟수가 0인 경우를 한도로 판별한다.

**한도 외의 크기 제한.**

- 카드 조회는 저장소 트리를 한 번에 읽는다. 트리가 잘려서 오면(`truncated`) 저장·삭제를 **보내지 않고** 중단한다. 일부만 보고 관계를 판단하지 않기 위해서다.
- 발행 대기 비교(`compare`)는 변경 파일을 최대 300개까지만 돌려준다. 카드 단위 작업에서는 닿지 않는다.

## 5. 설정이 필요할 때

| 대상 | 위치 | 값 |
| --- | --- | --- |
| 운영 OAuth App | GitHub → Settings → Developer settings | Homepage `https://avocadosmasher.github.io`, Callback `https://fragment-oauth.rdd0426.workers.dev/callback` |
| 운영 Worker | Cloudflare `fragment-oauth` | 공개 변수 4개, 비밀값 `GITHUB_CLIENT_SECRET`·`OAUTH_STATE_SECRET` |
| 빌드 연결 | `.github/workflows/deploy.yml` | `writer_oauth_origin: https://fragment-oauth.rdd0426.workers.dev` |
| Worker 배포 | 저장소에서 | `npx wrangler deploy --config workers/fragment-oauth/wrangler.jsonc --env production` |

비밀값은 대시보드나 `wrangler secret put`으로만 넣는다. 저장소·문서·대화에 남기지 않는다.
