1한 태스크의 사이클

판정 가능한 작은 작업 단위로 구현·테스트·기록을 묶는다. 가이드를 제시한 뒤 판정을 기다리며, 다음 작업으로 알아서 넘어가지 않는다. 작업 ID와 커밋 수가 항상 같은 것은 아니다(D06·D07은 함께 판정받고 같은 커밋으로 반영).

에이전트사람게이트
Red
기대 동작을 테스트로 먼저 쓰고 실패를 확인한다
Green
테스트를 통과시키는 최소 구현
Refactor
정리 후 해당 테스트와 영향받는 회귀 테스트 재실행
자동 검사
타입·단위·통합·빌드·E2E. 결과를 요약
기록·스테이징
로그 1항목 작성, 이 작업의 파일만 스테이징
수동 테스트 가이드
사람이 봐야 아는 것만, 조작과 예상 결과를 짝지어 제시
판정
“통과” 또는 “수정: 문제와 재현 방법”
승인 기록 → 커밋·push
manual-review.mjs approve 후 개발 브랜치에 push

수정 판정이면 수정 → 자동 검사 → 새 가이드 → 판정을 반복한다. 승인 이후 변경한 내용은 다시 판정받는다. 훅은 승인받은 스테이징 트리와 다른 내용을 커밋하려 하면 차단한다. 미스테이징·미추적 파일의 변경까지 감지하는 장치는 아니다.

2원칙 10가지

01

판정 가능한 작은 작업을 함께 커밋

코드·테스트·작업 기록이 같은 커밋에 들어간다. 되돌리거나 추적할 단위가 곧 판정 단위다.

왜 큰 덩어리는 판정도 어렵고, 어디서 틀렸는지 찾기도 어렵다.
02

Red는 진짜 실패여야 한다

의존성 설치 실패·서버 미실행은 Red가 아니다. 모듈이 없어서 난 실패와 assertion 실패를 구분해 기록한다. 설정 조사·문서 작업에는 억지 테스트를 만들지 않고 완료 기준으로 판정한다.

근거 로그 13 “TDD 증거 기록” — 전체 E2E 통과를 엄격한 TDD의 증거로 쓰지 않는다.
03

사람의 “통과”가 커밋 게이트

승인 시점의 HEAD와 스테이징 트리를 기록하고, pre-commit·pre-push 훅이 대조한다. --no-verify, 훅 비활성화, 승인 파일 조작, 대신 “통과”라고 쓰기는 금지.

왜 자동 테스트 통과는 “원하던 것”을 보장하지 않는다.
04

사람은 사람만 아는 것만

사람에게는 심미적 판단(배치·색·문구)과 실제 동작(외부 계정이 얽힌 흐름) 확인만 요청한다. 반복해도 같은 결과인 검사와 diff 확인은 에이전트가 하고 결과만 보고한다.

근거 2026-09-21 절차 조정(운영가이드 3-15).
05

시각 결정은 캡처 비교가 먼저

말로 설명하기 어려운 결정은 코드를 고치기 전에 2~8개 시안을 같은 조건에서 캡처해 고르게 한다.

근거 그래프 배치 8종·관계 선 모양 4종·새로고침 버튼 3종을 캡처로 결정. 설명만으로는 몇 차례 돌았던 것이 한 번에 정해졌다.
06

추측하지 말고 잰다

“느려서 그렇겠지”를 측정으로 확인한다. 측정하면 문제의 정의가 바뀌기도 한다.

근거 그래프가 원형이던 이유를 재 보니 “느림”이 아니라 “화면 멈춤”이 핵심이었다(설계 결정기록 1).
07

결정은 선택지와 함께 남긴다

docs/decision/에 검토한 선택지, 고른 것, 근거를 적는다. 틀렸던 가정과 방향을 바꾼 지점도 그대로 남긴다.

왜 나중에 “왜 이렇게 했지?”를 다시 조사하지 않기 위해.
08

기록은 다시 시작하기 좋게

STATUS.md(지금·다음 할 일) → 메뉴판(항목당 결론 한 줄) → 항목 파일 하나. 세션은 STATUS만 읽고 시작한다. 결론 한 줄에는 “무엇이 문제였고 어떻게 정했는지”를 적는다.

근거 J01: 76,519자 1파일 로그를 나눠 세션 시작 비용을 줄였다.
09

운영은 구조로 보호한다

테스트는 운영 데이터를 고정값으로 쓰지 않는다. 운영 쓰기는 명시적 opt-in(production: true)이 있어야만 열린다. 사람에게 규칙을 지키라고 하지 말고, 깨질 수 없게 만든다.

근거 운영 카드 하나를 지우자 모든 배포가 실패한 사고(운영가이드 3-7).
10

실패는 숨기지 않는다

조회 실패 시 화면을 비우지 말고 사유와 링크를 남긴다. 비밀값 생성처럼 중요한 단계는 실패하면 즉시 멈춘다. 규칙이 바뀌면 테스트도 새 의도에 맞게 고치고 기록한다.

근거 배포 상태가 안 보이던 문제(3-11), 서명 키 생성 실패(3-4), 로그인 유지 범위 변경(3-9).

3계획 세우기

계획 문서(docs/plan/<기능>-개발계획.md)는 구현 전에 사용자와 합의한다. 네 가지가 들어가야 한다.

3.1 끝의 정의와 제외 범위

“구현·테스트·운영 배포 검증·운영 가이드·최종 보고서까지 끝나야 종료”처럼 끝을 먼저 정한다. 중간 버전에서 핵심 기능을 빼고 완료로 처리하지 않는다. 이번에 하지 않는 것도 명시한다(Fragments: AI 관계 추론, 별도 DB, 비공개 카드, 이미지 업로드).

3.2 작업 표

한 행은 혼자서 통과/실패를 판단할 수 있는 크기다. 행마다 먼저 작성할 실패 테스트를 적는다.

ID작업선행먼저 작성할 실패 테스트 / 완료 기준
B01필수·선택 필드 정의A02id/title/summary/category 누락·공백을 거부하고 aliases/tags/relations 기본값 적용
B02안정적인 ID와 고유성B01제목이 바뀌어도 ID 유지, 중복 ID와 URL에 부적합한 ID 거부
B04관계 참조 검증B03없는 대상·자기 참조·모르는 관계 유형을 파일/ID가 포함된 오류로 거부

Fragments 개발계획에서 발췌. 영역별 알파벳(A 기준선, B 데이터, C 화면 …) + 번호로 ID를 붙이면 로그·커밋·보고서가 같은 이름으로 서로를 가리킨다.

3.3 테스트 계층

계층도구 예책임
단위Vitest스키마, 검증 규칙, 검색·정렬·페이지 계산, URL 상태
통합Vitest + 격리 fixture + 실제 빌드실제 파일 수집·렌더링, 잘못된 콘텐츠 차단
브라우저Playwright탐색·팝업·키보드·반응형. 최종 검증은 개발 서버가 아닌 빌드 산출물 preview로
실제 연동테스트 저장소 + 수동 인수OAuth, 실제 커밋, Actions, 여러 세션
배포 인수운영 사이트정적 산출물·경로·전체 흐름을 사람이 확인

테스트는 구현 코드의 내부 호출 순서나 CSS 클래스 문자열을 복제하지 말고, 사용자가 보는 결과와 데이터 계약을 검증한다. fixture는 실제 콘텐츠 밖에 두고 경계값(0·1·12·13·25개, 한글 조합형/분해형, HTML처럼 보이는 문자열)을 포함한다.

3.4 위험한 것부터

외부 연동처럼 실패하면 계획 전체가 흔들리는 작업은 앞쪽에 “최소 실험”으로 둔다(Fragments A04: 로그인 → 샘플 커밋 → 다른 세션에서 읽기). 실패하면 원인을 분류하고 대안을 먼저 제시한다.

로그 상태 표기: 판정 전에는 판정 대기로 둔다. 통과 후에는 승인받은 파일 그대로 커밋하고, 상태·해시 갱신은 다음 작업의 검토 범위에 포함한다. 다음 세션에서 판정 대기 문구가 남아 있더라도 실제 사용자 판정 기록과 해당 커밋을 확인해 갱신 지연인지 구분한다. 같은 변경의 재승인을 요구하지 않으며, 증거가 없으면 통과로 추정하지 않는다. 자기 해시를 넣으려고 amend를 반복하지 않는다.

코드 탐색에는 이 저장소의 graft 그래프를 먼저 사용했다. 위치·설명은 graft ask "작업" --source, 전체 출현 위치는 graft grep "식별자", 변경 전 호출 영향은 graft callers 식별자 --depth all로 확인한다. 필요한 소스 범위만 읽고, 큰 코드 변경 후 그래프를 갱신한다. 다른 저장소에서는 도구와 인덱스가 있을 때 적용한다.

상단 실적은 당시 기록이다. I02의 167개는 2026-09-24 검사 결과이며, K01에서 Decap을 제거한 뒤 보고된 수는 159개다. 현재 테스트 개수를 뜻하지 않는다. 로그 57건에는 M01과 이후 보완 기록을 포함하지 않는다.

6브랜치와 배포

  • 개발 브랜치(feat/<기능>)에서 태스크마다 커밋·push. main push가 곧 배포이므로 개발은 거기서 하지 않는다.
  • 개발 브랜치 push ≠ 배포. main 병합은 그 배포 범위의 인수 조건, build·preview 검증, 사용자 판정을 모두 거친 뒤 PR로.
  • CI와 배포는 같은 검사를 쓰고, 배포에는 검사를 통과한 그 산출물을 그대로 올린다. 운영 설정이 빠진 산출물은 게이트로 막는다.
  • 반쪽짜리를 main에 넣지 않는다. Fragments D01(초안 저장)은 D02(발행 버튼)가 끝날 때까지 병합하지 않았다 — 저장만 되고 공개할 방법이 없기 때문.
  • push가 실패하면 로컬 커밋을 보존하고 원인을 기록한다. 성공을 확인하기 전에는 원격 백업 완료라고 쓰지 않는다.

커밋 메시지 예: feat(fragments): let either card remove the relation between them · docs(log): mark the relation work as passed

7Fragments의 교훈

일어난 일배운 것출처
