- 선행: ACTF01 사용자 통과, `7841802` 커밋·개발 브랜치 push 완료.
- 위치: C3 중 카테고리 처리 검증·판정 완료. 프로젝트는 [별도 가이드](./AI-콘텐츠-프로젝트-CLI.md), 잠금/복구는 [복구 가이드](./AI-콘텐츠-잠금-복구-CLI.md)로 연결함. 최신 저장 차단·공통 CI는 [Git 훅 안내](./AI-콘텐츠-Git-검사-CLI.md)를 따름. 최종 인수는 남은 작업임.

## 무엇이 가능해졌는가

확정한 카테고리 키와 색으로 CATEGORIES에 한 항목을 등록하거나, 기존 키의 색만 수정할 수 있다. 같은 키·같은 색이면 쓰기 없이 끝내고, 같은 키·다른 색의 생성 요청은 충돌로 처리한다. 기존 카테고리와 프로필·프로젝트 등 다른 설정을 통째로 재작성하지 않는다.

현재 [글 CLI](./AI-콘텐츠-글-생성-CLI.md)·[Fragment CLI](./AI-콘텐츠-Fragment-CLI.md)와 같은 plan/apply 명령을 사용한다. 요청의 resource가 category이면 카테고리 어댑터를 선택한다. 도구는 로컬 설정과 최소 완료 기록을 준비하며 Git 승인·커밋·push·운영 발행을 수행하지 않는다. 이번 개발에서는 실제 운영 CATEGORIES와 색을 바꾸지 않았다.

## 입력과 실행

[JSON 요청 계약](./AI-콘텐츠-요청-계약.md)을 따른다. 색을 매번 새로 고르지 않고 처음 확정한 값을 같은 요청에서 재사용한다. 키 이름은 정확한 문자열로 식별하며 카테고리 ID를 새로 도입하지 않는다.

| 항목 | 생성 | 기존 색 수정 |
| --- | --- | --- |
| resource / operation | category / create | category / update |
| target.path | src/consts.ts | src/consts.ts |
| target.key | 등록할 확정 키 | 실제 기존 키 |
| baseline.sha256 | 읽어 둔 설정 파일 전체 바이트의 SHA-256 | 동일 |
| 값 | content.color | changes.color |

신규 카테고리도 이미 있는 설정 파일을 편집하므로 기준 지문은 null이 아니다. Git 커밋 SHA나 GitHub 파일 SHA와 구별한다. 설정 파일이 없으면 새 파일을 만들지 않는다. 키 변경·삭제·기존 콘텐츠의 카테고리 일괄 이관은 지원하지 않는다.

```powershell
node scripts/content-ops.mjs plan --request 'input/category-request.json' --root 'C:\작업폴더' --out '.content-ops/local/category-plan.json'
node scripts/content-ops.mjs apply --request 'input/category-request.json' --root 'C:\작업폴더' --plan '.content-ops/local/category-plan.json' --expect-plan '<plan에서 확인한 64자리 지문>'
```

요청 상대 경로는 터미널 작업 폴더, 대상·계획 경로는 지정 root를 기준으로 한다. root를 생략하면 스크립트 소속 저장소다. plan은 수정 전후 TypeScript를 `-`와 `+`로 표시하고 로컬 계획 파일만 저장한다. 같은 계획 파일은 다시 쓰지 않는다. `--json`과 종료 코드 0 성공/변경 없음·1 입력/충돌/적용 실패·2 명령 사용 오류도 기존과 같다.

## 설정 원문을 보존하는 방식

검사기와 편집기가 같은 TypeScript AST 해석기로 CATEGORIES 선언과 키·문자열 값의 정확한 위치를 확인한다. AST는 코드를 실행하지 않고 구문 구조와 위치를 읽는 자료다. 다른 설정의 실행문이나 함수 호출을 평가하지 않는다.

색 수정은 해당 문자열 값의 범위만 교체한다. 기존 키의 인용 방식·다른 색·주석·BOM·줄바꿈·PROFILE·PROJECTS 등 나머지 원문은 보존한다. 신규 등록은 객체 끝에 한 쌍만 추가한다. 필요한 마지막 쉼표만 보충하며 한 줄 객체·여러 줄 객체·빈 객체·주석·탭 들여쓰기도 처리한다. 새 키와 변경한 값은 안전하게 인코딩한 문자열 표기를 사용한다.

| 상황 | 결과 |
| --- | --- |
| AI 키가 같은 색으로 이미 등록됨 | 변경 없음. 인용·이스케이프 표현도 그대로 보존 |
| AI가 다른 색인데 create로 요청 | target.conflict. 기존 색 덮어쓰기 없음 |
| AI가 다른 색이고 update로 요청 | AI의 색 값만 수정 |
| 수정할 키가 없음 | target.missing. 생성으로 자동 전환하지 않음 |
| 새 키 등록 | 해당 한 쌍만 추가. 다른 키·설정 보존 |

비교는 확정한 문자열 값 기준이다. 예를 들어 #fff와 #FFF를 브라우저에서 비슷하게 보인다는 이유로 같은 입력으로 바꾸지 않는다. 현행 입력 계약은 비어 있지 않은 색 문자열을 받으며 모든 CSS 색 문법이나 디자인 적합성을 판정하는 엔진은 아니다.

## 지원하지 않는 설정을 추측하지 않는다

export const CATEGORIES에 정적 객체를 직접 지정한 형태만 지원한다. 계산식·spread·별칭 값·getter·동적 키·숫자 값·중복 키/선언·지원 밖 타입 단언·구문 오류는 registry.invalid로 중단한다. 선언 밖에 CATEGORIES 참조가 있으면 별칭이나 후속 수정의 영향을 추측하지 않고 patch.unsupported로 거절한다. 읽기 전용 검사기는 정적 선언을 해석하고, 실제 편집기는 쓰기 대상을 확정하기 위해 이 추가 제한을 적용한다.

설정 전체를 실행하거나 정규식으로 객체 전체를 덮어쓰는 우회는 하지 않는다. 지원 밖 형태를 정리하는 작업은 별도로 검토해야 한다. 선언 밖 다른 파일의 런타임 수정까지 분석하는 기능은 포함하지 않는다.

## 전체 정책·재실행·충돌

제안된 CATEGORIES 원문을 메모리에서 현재 글·Fragment와 대조한다. 예를 들어 아직 등록되지 않은 새 키를 쓴 글이 있으면 그 키를 등록한 제안으로 전체 정책이 통과하는지 먼저 확인할 수 있다. 반대로 기존 관계 오류·잘못된 문서가 있으면 카테고리 계획도 실패한다. 설정을 먼저 쓴 뒤 검사하는 방식이 아니다.

이 제안 검사는 전체 TypeScript 타입 검사나 실제 Astro 빌드를 대체하지 않는다. 실제 콘텐츠 작업에서는 적용 뒤 저장소의 자동 검사·타입 검사·빌드도 수행한다. 설정의 별도 타입 제약과 실제 색 출력까지 그 단계에서 확인한다.

기존 Infra 예외 목록은 자동으로 늘리거나 삭제하지 않는다. 새 키를 등록했다는 이유로 기존 콘텐츠의 문자열을 바꾸지 않는다. 명시적 등록으로 예외가 더는 필요하지 않게 된 경우도 미사용 예외로 보고할 뿐 자동 정리하지 않는다.

계획 이후 다른 사람이 PROJECTS만 편집했더라도 설정 파일 전체 지문이 달라지므로 아직 색 수정이 필요하면 baseline.conflict로 중단한다. 오래된 설정 전체로 그 프로젝트 편집을 덮어쓰지 않는다. 기록 없이 요청한 키·색이 이미 같은 경우에는 변경 없음으로 끝내고 최신 설정을 보존한다.

완료 기록이 있으면 실제 consts.ts 전체의 최종 지문을 대조한다. 이후 다른 설정만 바뀌어도 receipt.state-mismatch이며 이전 요청이 완전히 같은 결과라고 보고하지 않는다. 새 편집은 최신 기준으로 별도 요청을 준비한다. 같은 요청 ID의 내용 변경·다른 계획 지문·변조한 결과 계획도 거절한다.

설정은 기준 재확인 뒤 완성된 임시 파일로 교체하고, 결과 지문을 확인한 다음 `.content-ops/receipts/<request_id>.json`에 최소 기록을 마지막으로 추가한다. 기록은 요청/계획·전후 파일 지문·결과만 담으며 설정 원문·채팅·토큰·승인을 보관하지 않는다. 재실행이 변경 없음이면 기록과 파일 수정 시각도 바꾸지 않는다.

## 검증과 남은 범위

카테고리 통합 55개를 추가해 전체 484개·29파일을 통과했다. 한 줄 객체의 쉼표 삽입과 정적 속성 이름을 변수 참조로 오인하는 경계를 실패 재현 후 보완했다. 타입 검사 114파일에서 오류·경고 0건과 기존 힌트 5건을 확인했다. 일반 빌드는 11페이지·18이미지로 성공했다. 현재 수집 콘텐츠 검사도 오류 0·기존 Infra 예외 4·미사용 예외 0이다.

`npm run test:content-ops:build`는 격리 사본에서 실제 CLI로 새 카테고리 등록·색 수정·각 재실행과 해당 키를 쓰는 글 수정을 실행한다. 실제 Astro 산출물에서 새 키·수정한 색·검색 포함을 확인한다. 기존 글의 본문·이미지와 Fragment ID·제목·관계도 함께 회귀 검사한다. 이 별도 빌드의 공통 CI 연결은 ACTH01 범위다.

ACTK01 당시 파일 교체 권한 오류 1건이 있었으나 분리 재실행과 이후 전체 검사에서는 재현되지 않았다. 원인은 확정하지 않았으며 이 오류를 정상 결과로 바꾸거나 파일 교체 방식을 우회하지 않았다. ACTS01에서 저장소 적용 잠금·교체 실패 자료 보존·명시적 복구를 추가했다. EBUSY/EACCES 주입의 보존·재시도 검증이며 기존 오류의 원인을 확정하거나 모든 OS 파일 점유를 재현한 것은 아니다. 최종 기준 확인/rename 사이 외부 쓰기와 다중 파일 원자성은 계속 미보장이다.

ACTK01은 화면·운영 색·외부 계정 흐름을 바꾸지 않았고 파일 결과·종료 코드·실제 빌드로 자동 확인했다. 사용자 직접 실행 없이 통과 판정을 받았다. 이후 ACTJ01에서 카테고리와 프로젝트의 원문 범위 편집을 공유했으며 카테고리 55개 회귀 사례를 유지했다. 프로젝트 적용은 프로젝트 가이드, 잠금·복구의 제한은 복구 가이드를 따른다. 최신 저장 차단과 공통 CI 검증은 위 Git 훅 안내를 따른다.
