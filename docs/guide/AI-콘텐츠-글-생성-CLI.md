# AI 콘텐츠 글 생성 CLI

- 개발 건: AI-CONTENT-TOOLS / ACTB01, 2026-10-18, 사용자 판정 대기.
- 선행: ACTC02 사용자 통과, `e13f72c` 커밋·개발 브랜치 push 완료.
- 위치: C2 글 작성·재실행 중 신규 생성 구현. 제목 수정·동시 수정 확인은 ACTB02에 남아 있음.

## 무엇이 가능해졌는가

확정한 글·자산으로 변경계획을 만들고, 확인한 계획의 지문을 지정해 로컬 파일에 반영할 수 있다. 같은 요청을 다시 실행하면 이미 반영된 실제 결과를 확인하고 추가 쓰기 없이 끝낸다. 기존 글을 임의로 덮어쓰거나 경로에 접미사를 붙여 새 글을 만들지 않는다.

현재 지원은 **blog/create**다. 수정·Fragment·카테고리·프로젝트는 입력 계약만 있으며 각 적용 어댑터는 후속 작업이다. CLI는 콘텐츠와 최소 완료 기록을 로컬에 준비한다. Git 승인·커밋·push·운영 발행은 수행하지 않는다.

## 준비와 명령

프로젝트의 Node.js·의존성이 설치된 환경에서 [확정 요청 계약](./AI-콘텐츠-요청-계약.md)에 맞는 JSON을 준비한다. 글의 날짜·초안 여부·본문·대상 경로와 자산 지문을 먼저 확정한다. 도구가 날짜나 ID를 자동으로 채우지 않는다.

다음은 경로를 자신의 작업 폴더로 바꾸어 사용하는 명령 형식이다. 이번 사용자 확인용 실제 경로와 지문은 별도로 열어 둔 임시 안내에 준비했다.

```powershell
node scripts/content-ops.mjs plan --request 'input/request.json' --root 'C:\작업폴더' --out '.content-ops/local/plan.json'
node scripts/content-ops.mjs apply --request 'input/request.json' --root 'C:\작업폴더' --plan '.content-ops/local/plan.json' --expect-plan '<확인한 계획 지문>'
```

`--expect-plan`에는 plan이 보여 준 64자리 지문을 지정한다. `--request`의 상대 경로는 현재 터미널 작업 폴더, 대상 파일·자산·계획 경로는 `--root`를 기준으로 한다. root를 생략하면 스크립트 소속 저장소를 사용하므로 다른 사본을 다룰 때는 명시한다.

```powershell
node scripts/content-ops.mjs --help
npm run content:ops -- plan --request 'input/request.json' --root 'C:\작업폴더' --out '.content-ops/local/plan.json'
```

기계용 결과는 명령 끝에 `--json`을 붙인다. 순수 JSON이 필요하면 npm 안내가 섞이지 않는 Node 직접 명령을 사용한다. 성공·변경 없음은 종료 0, 입력/충돌/적용 실패는 1, 명령 사용 오류는 2다. 승인 플래그·강제 덮어쓰기 옵션은 없다.

## plan과 apply의 차이

| 단계 | 읽고 확인하는 것 | 실제 쓰기 |
| --- | --- | --- |
| plan | 현재 대상·자산 바이트·기존 기록·제안 원문을 포함한 전체 콘텐츠 정책 | 지정한 로컬 계획 파일만 추가 |
| 같은 plan 재실행 | 기존 계획과 요청·지문 일치 확인 | 계획까지 같은 경우 쓰기 없음 |
| apply | 요청·기대 계획 지문·현재 상태·정책을 다시 확인 | 새 글·명시한 새 자산·최소 완료 기록 |
| 같은 적용 재실행 | 완료 기록과 실제 파일의 지문을 대조 | 모두 일치하면 쓰기 없음 |

plan은 추가할 경로와 글 원문, 자산 지문을 보여 준다. 본문 제어 문자는 화면에서 보이는 이스케이프로 표시하지만 실제 파일에는 확정 입력의 바이트를 보존한다. 계획 파일은 해시 중심 자료이며 `.content-ops/local/`에 둔다. 같은 출력 경로에 다른 계획이 있으면 조용히 교체하지 않는다.

apply는 준비한 글·자산의 실제 바이트로 계획을 다시 만들고 기대 지문과 비교한다. 계획 파일의 지문만 다시 계산해 결과 파일을 바꾸어도 요청의 원문·자산과 다르면 거절한다. 각 파일은 새 파일 전용 생성으로 추가하며 이미 있는 파일을 덮어쓰지 않는다.

콘텐츠의 최종 바이트 확인 뒤 `.content-ops/receipts/<request_id>.json`에 완료 기록을 마지막으로 추가한다. 글 1개·자산 1개 요청이라면 콘텐츠 2개와 기록 1개가 추가된다. 실제 작업에서는 이 기록도 콘텐츠와 같은 Git 검토 범위에 포함한다.

## 변경 없음과 충돌의 구별

| 현재 상태 | 결과 |
| --- | --- |
| 대상과 자산이 모두 없고 입력이 유효함 | 생성 계획 준비 |
| 기록 없이 이미 같은 글·자산이 있음 | 변경 없음, 새 기록도 만들지 않음 |
| YAML 순서·선택 필드 기본값 표현만 다르고 해석된 정보·본문이 같음 | 기존 원문 보존, 재직렬화 없음 |
| 같은 경로에 다른 본문·메타데이터가 있음 | target.conflict |
| 본문만 있고 요청한 자산 일부가 없음 | 부분 상태로 충돌, 임의 복구 없음 |
| 같은 ID의 기록과 확정 입력이 다름 | request.conflict |
| 기록은 있으나 최종 파일이 수정·삭제됨 | receipt.state-mismatch |
| 계획 후 자산 입력이나 등록 정책이 바뀜 | asset.changed 또는 content.invalid |
| 기대 지문과 계획·실제 생성 결과가 다름 | plan.changed |

태그 순서·본문 줄바꿈·이미지 바이트처럼 결과에 영향을 주는 차이는 임의로 무시하지 않는다. BOM·CRLF·발행일·draft 값도 확정 입력대로 보존한다. 같은 제목의 다른 경로에 있는 글까지 의미 중복을 자동 판정하는 기능은 아니므로 요청 전에 기존 후보를 확인해야 한다.

## 정책 검사와 실패 범위

제안 글을 메모리에서 현재 문서 집합에 합쳐 검사한다. 미등록 카테고리뿐 아니라 기존 Fragment의 끊어진 관계 등 전체 정책 오류도 계획을 막는다. 실제 콘텐츠를 먼저 써 놓고 검사하는 방식이 아니다. 기존 Infra 예외는 정확한 경로·규칙·값의 기존 기준을 유지한다.

본문·자산·기록 경로는 저장소 경계와 링크/junction을 검사한다. 자산 source는 선택한 저장소 안에 미리 준비한 파일이며 target은 새 글 폴더 안의 새 경로다. 이 검사는 Astro의 이미지 해석·실제 빌드를 대체하지 않으므로 실제 글 작업에서는 로컬 적용 뒤 저장소의 자동 검사도 수행한다.

여러 파일이 하나의 데이터베이스 트랜잭션처럼 동시에 생성되는 것은 아니다. 디스크 오류나 외부 변경으로 도중 실패하면 이미 추가한 파일 목록을 보고하고 자동 삭제하지 않는다. 파일 일부가 남으면 성공으로 보고하지 않으며 상태 확인이 필요하다. 잠금·실패 주입·복구 저널·복구 흐름은 ACTS01에서 검증하고 보완한다. 현재 단계에서 다중 파일 원자성이나 모든 외부 편집기 통제를 보장하지 않는다.

계획 지문은 내용 일치 확인값이며 사람의 통과 판정이 아니다. 로컬 적용은 검토할 결과물을 준비하는 단계다. 적용 뒤 Git 저장은 기존 AGENTS 절차의 사용자 통과를 따라야 한다.
