## 무엇이 가능해졌는가

확정한 글·자산으로 변경계획을 만들고, 확인한 계획의 지문을 지정해 로컬 파일에 반영할 수 있다. 같은 요청을 다시 실행하면 이미 반영된 실제 결과를 확인하고 추가 쓰기 없이 끝낸다. 기존 글을 임의로 덮어쓰거나 경로에 접미사를 붙여 새 글을 만들지 않는다.

이 가이드의 대상은 **blog/create와 blog/update**다. 기존 글 수정은 확정한 실제 경로에서 요청 필드만 바꾼다. 같은 CLI에 연결한 Fragment 생성·부분 수정·관계 처리는 [Fragment 가이드](./AI-콘텐츠-Fragment-CLI.md)를 따른다. 카테고리·프로젝트 적용은 후속 작업이다. CLI는 콘텐츠와 최소 완료 기록을 로컬에 준비한다. Git 승인·커밋·push·운영 발행은 수행하지 않는다.

## 준비와 명령

프로젝트의 Node.js·의존성이 설치된 환경에서 [확정 요청 계약](./AI-콘텐츠-요청-계약.md)에 맞는 JSON을 준비한다. 글의 날짜·초안 여부·본문·대상 경로와 자산 지문을 먼저 확정한다. 도구가 날짜나 ID를 자동으로 채우지 않는다.

다음은 경로를 자신의 작업 폴더로 바꾸어 사용하는 명령 형식이다. 생성과 수정은 같은 명령을 쓰며 요청의 operation으로 구별한다. AI가 실행할 때도 대상 저장소와 요청을 먼저 확인해야 한다.

```powershell
node scripts/content-ops.mjs plan --request 'input/request.json' --root 'C:\작업폴더' --out '.content-ops/local/plan.json'
node scripts/content-ops.mjs apply --request 'input/request.json' --root 'C:\작업폴더' --plan '.content-ops/local/plan.json' --expect-plan '<확인한 계획 지문>'
```

`--expect-plan`에는 plan이 보여 준 64자리 지문을 지정한다. `--request`의 상대 경로는 현재 터미널 작업 폴더, 대상 파일·자산·계획 경로는 `--root`를 기준으로 한다. root를 생략하면 스크립트 소속 저장소를 사용하므로 다른 사본을 다룰 때는 명시한다.

```powershell
node scripts/content-ops.mjs --help
npm run content:ops -- plan --request 'input/request.json' --root 'C:\작업폴더' --out '.content-ops/local/plan.json'
```

기계용 결과는 명령 끝에 `--json`을 붙인다. 순수 JSON이 필요하면 npm 안내가 섞이지 않는 Node 직접 명령을 사용한다. 성공·변경 없음은 종료 0, 입력/충돌/적용 실패는 1, 명령 사용 오류는 2다. 승인 플래그·강제 덮어쓰기 옵션은 없다.

## plan과 apply의 차이

| 단계 | 읽고 확인하는 것 | 실제 쓰기 |
| --- | --- | --- |
| plan | 현재 대상·자산 바이트·기존 기록·제안 원문을 포함한 전체 콘텐츠 정책 | 지정한 로컬 계획 파일만 추가 |
| 같은 plan 재실행 | 기존 계획과 요청·지문 일치 확인 | 계획까지 같은 경우 쓰기 없음 |
| apply | 요청·기대 계획 지문·현재 상태·정책을 다시 확인 | 글 생성 또는 요청 필드 수정·명시한 새 자산·최소 완료 기록 |
| 같은 적용 재실행 | 완료 기록과 실제 파일의 지문을 대조 | 모두 일치하면 쓰기 없음 |

plan은 대상 경로와 글 원문, 자산 지문을 보여 준다. 수정은 기존 원문을 `-`, 수정 결과를 `+`로 구별한다. JSON 결과는 before와 source를 제공한다. 본문 제어 문자는 화면에서 보이는 이스케이프로 표시하지만 실제 파일에는 확정 입력의 바이트를 보존한다. 계획 파일은 해시 중심 자료이며 `.content-ops/local/`에 둔다. 같은 출력 경로에 다른 계획이 있으면 조용히 교체하지 않는다.

apply는 준비한 글·자산의 실제 바이트로 계획을 다시 만들고 기대 지문과 비교한다. 계획 파일의 지문만 다시 계산해 결과 파일을 바꾸어도 요청의 원문·수정 값·자산과 다르면 거절한다. 새 글·자산·기록은 새 파일 전용으로 추가한다. 기존 글의 수정만 기준을 재확인하고 완성된 임시 파일로 교체한다. 기존 자산의 덮어쓰기·삭제는 지원하지 않는다.

콘텐츠의 최종 바이트 확인 뒤 `.content-ops/receipts/<request_id>.json`에 완료 기록을 마지막으로 추가한다. 글 1개·자산 1개 요청이라면 콘텐츠 2개와 기록 1개가 추가된다. 실제 작업에서는 이 기록도 콘텐츠와 같은 Git 검토 범위에 포함한다.

## 변경 없음과 충돌의 구별

| 현재 상태 | 결과 |
| --- | --- |
| 대상과 자산이 모두 없고 입력이 유효함 | 생성 계획 준비 |
| 기록 없이 이미 같은 글·자산이 있음 | 변경 없음, 새 기록도 만들지 않음 |
| YAML 순서·선택 필드 기본값 표현만 다르고 해석된 정보·본문이 같음 | 기존 원문 보존, 재직렬화 없음 |
| 같은 경로에 다른 본문·메타데이터가 있음 | target.conflict |
| 본문만 있고 요청한 자산 일부가 없음 | 부분 상태로 충돌, 임의 복구 없음 |
| 같은 ID의 기록과 확정 입력이 다름 | request.conflict |
| 기록은 있으나 최종 파일이 수정·삭제됨 | receipt.state-mismatch |
| 계획 후 자산 입력이나 등록 정책이 바뀜 | asset.changed 또는 content.invalid |
| 기대 지문과 계획·실제 생성 결과가 다름 | plan.changed |

태그 순서·본문 줄바꿈·이미지 바이트처럼 결과에 영향을 주는 차이는 임의로 무시하지 않는다. BOM·CRLF·발행일·draft 값도 확정 입력대로 보존한다. 같은 제목의 다른 경로에 있는 글까지 의미 중복을 자동 판정하는 기능은 아니므로 요청 전에 기존 후보를 확인해야 한다.

## 기존 글을 부분 수정하는 방식

수정 요청은 `operation: "update"`, 기존 글의 `target.path`, 읽어 둔 원문 바이트의 SHA-256인 `baseline.sha256`, 변경할 값인 `changes`를 사용한다. 예를 들어 `changes: { "title": "새 제목" }`이면 title 값만 바꾼다. 파일 경로와 ID를 새로 만들지 않는다. 날짜·본문 등 생략한 값은 현재 파일에서 보존하며 요청에 보충하지 않는다.

전체 YAML을 객체로 바꿔 다시 저장하면 제목만 수정해도 주석·따옴표·필드 순서·줄바꿈이 바뀔 수 있다. 이 도구는 YAML이 알려 준 값의 정확한 위치만 교체한다. 바뀌지 않은 영역의 BOM·CRLF·주석·모르는 기존 필드·Markdown 바이트를 그대로 둔다. 변경한 문자열은 JSON 문자열 표기로 안전하게 인코딩하며, 변경한 배열은 원래 값의 위치에 흐름 배열로 쓴다. 해당 필드의 표현은 바뀔 수 있다.

| 요청 | 결과 |
| --- | --- |
| title만 지정 | 제목 값만 수정, 날짜·초안 여부·태그·본문·기존 이미지 보존 |
| tags: [] 또는 body: "" 지정 | 그 배열 또는 본문을 명시적으로 비움 |
| tags·body 생략 | 원래 배열 순서와 본문 바이트 유지 |
| 없는 선택 필드에 기본값 지정 | 해석한 값이 같으면 필드를 삽입하지 않음 |
| readingTime 등 없는 선택 필드의 실제 새 값 지정 | 기존 필드를 건드리지 않고 헤더 끝에 한 필드 추가 |
| 자산만 새로 추가되고 글은 같은 값 | 글은 다시 쓰지 않아 원래 수정 시각 보존 |
| 다른 글 경로로 이동·기존 자산 덮어쓰기 요청 | 지원하지 않음 |

기존 원문이 유효하지 않으면 임의로 고치지 않는다. 메타데이터의 흐름 매핑이나 수정할 값에 앵커가 포함된 경우에는 요청 밖 값에 영향을 줄 수 있어 `patch.unsupported`로 중단한다. 흐름 매핑의 본문 수정, 앵커가 없는 다른 필드의 수정, 별칭을 참조하는 필드 자체 교체는 지원한다. 편집 결과의 스키마 해석과 요청 밖 필드·본문 보존도 쓰기 전에 재확인한다.

## 동시 편집과 이미 반영된 수정의 구별

예를 들어 AI A가 제목 수정 계획을 만들고, 그 뒤 AI B나 편집기가 본문을 바꾸면 원문 지문이 달라진다. A가 적용할 때 `baseline.conflict`로 멈추며 B의 본문을 옛 내용으로 되돌리지 않는다. 여기서 AI는 별도 채팅 세션이나 별도 프로세스의 작업자다. 블로그 방문자의 웹 세션을 뜻하지 않는다.

완료 기록이 없고 요청한 필드와 자산이 이미 원하는 값이면 변경 없음이다. 오래된 기준 지문이더라도 다른 본문 편집을 보존하고 새 기록을 만들지 않는다. 예를 들어 title만 요청했고 현재 제목이 같은 값이면 현재 본문에는 쓰지 않는다. 요청 자산이 일부 빠졌다면 이 조건을 충족하지 않으며, 기준도 달라졌으면 충돌로 보고한다.

완료 기록이 있는 경우는 더 엄격하다. 기록에 묶인 모든 파일의 최종 지문과 현재 파일을 대조한다. 이후 본문만 바뀌었더라도 `receipt.state-mismatch`이며 예전 작업이 완전히 같은 상태라고 보고하지 않는다. 새 편집은 최신 원문을 기준으로 새로운 요청을 준비한다.

기존 글 교체는 `.content-ops/local/writes/`의 고유한 임시 파일을 완성한 다음 원문 지문을 재확인하고 rename으로 수행한다. 파일을 먼저 비우고 쓰는 방식은 사용하지 않는다. 다만 최종 지문 확인과 rename 사이의 외부 쓰기를 원자적으로 막는 비교·교체는 아니다. 현재 단계의 두 계획 순차 적용 검증을 모든 프로세스의 동시 쓰기 차단으로 확대 해석하지 않는다. 도구 간 잠금·중단 저널·실패 주입·복구는 ACTS01에서 다룬다.

## 정책 검사와 실패 범위

제안 글을 메모리에서 현재 문서 집합에 합쳐 검사한다. 미등록 카테고리뿐 아니라 기존 Fragment의 끊어진 관계 등 전체 정책 오류도 계획을 막는다. 실제 콘텐츠를 먼저 써 놓고 검사하는 방식이 아니다. 기존 Infra 예외는 정확한 경로·규칙·값의 기존 기준을 유지한다.

본문·자산·기록 경로는 저장소 경계와 링크/junction을 검사한다. 자산 source는 선택한 저장소 안에 미리 준비한 파일이며 target은 새 글 폴더 안의 새 경로다. 이 검사는 Astro의 이미지 해석·실제 빌드를 대체하지 않으므로 실제 글 작업에서는 로컬 적용 뒤 저장소의 자동 검사도 수행한다.

여러 파일이 하나의 데이터베이스 트랜잭션처럼 동시에 반영되는 것은 아니다. 디스크 오류나 외부 변경으로 도중 실패하면 이미 반영한 파일 목록을 보고하고 사용자 파일을 자동으로 되돌리지 않는다. 파일 일부가 남으면 성공으로 보고하지 않으며 상태 확인이 필요하다. 잠금·실패 주입·복구 저널·복구 흐름은 ACTS01에서 검증하고 보완한다. 현재 단계에서 다중 파일 원자성이나 모든 외부 편집기 통제를 보장하지 않는다.

계획 지문은 내용 일치 확인값이며 사람의 통과 판정이 아니다. 로컬 적용은 검토할 결과물을 준비하는 단계다. 적용 뒤 Git 저장은 기존 AGENTS 절차의 사용자 통과를 따라야 한다.
