# AI 콘텐츠 작업 요청·인계·완료 보고 지시문

- 개발 건: `AI-BLOG`, 작업 `ABI02`, 사용자 통과 — `499049c`, 개발 브랜치 push 완료
- 공통 원문: [AI 콘텐츠 작업 규약](./AI-콘텐츠-작업규약.md)
- 작업 절차: [AGENTS.md](../../AGENTS.md)
- 개발 범위: [AI-BLOG 개발계획](../plan/AI-블로그-작업-개발계획.md)

이 문서는 다른 채팅 세션·AI에 복사할 지시문과 요청서다. 요청서의 YAML은 정보를 전달하는 형식이며 프로그램 설정이나 자동 실행 명령이 아니다. 현행 콘텐츠 frontmatter에 이 요청서 전체를 넣지 않는다.

자동화 2차의 기계 입력은 별도 [JSON 요청 계약](./AI-콘텐츠-요청-계약.md)을 따른다. 아래 YAML의 승인·발행·근거까지 그대로 프로그램에 전달하지 않는다. 명시한 대응으로 입력을 확정한다. 현재 [글 CLI](./AI-콘텐츠-글-생성-CLI.md)·[Fragment CLI](./AI-콘텐츠-Fragment-CLI.md)·[카테고리 CLI](./AI-콘텐츠-카테고리-CLI.md)가 연결되어 있다. Fragment는 명시한 관련 연결 제거를, 카테고리는 고정 키·색 등록과 색 값 수정을 계획한다. 프로젝트는 후속 구현이다.

## 1. 사용하는 방법

1. 사용자 요청과 자료를 제공한다. 모든 칸을 사용자가 직접 채울 필요는 없다. 실행 AI가 저장소와 기존 자료에서 확인 가능한 값을 채우고, 결과를 달라지게 하는 미확정 선택만 확인한다.
2. 아래 공통 지시문에 요청서를 붙인다. 접근 방식에 맞는 저장소 또는 웹 작업 지시도 함께 붙인다.
3. AI가 확인한 대상·기준 상태·내용·날짜·공개 여부를 확정한다. 확정한 요청과 자산을 다음 세션에 그대로 넘긴다.
4. 결과 보고에서 실제 확인한 저장 단계와 현재 판정 상태를 확인한다. 요청서에 쓰기 단계를 적었다는 이유로 승인이 완료된 것은 아니다.

저장소 파일을 읽을 수 없는 AI에는 저장소·브랜치와 해당 규약 원문을 제공한다. 규약을 조회할 수 없으면 사용자에게 필요한 원문을 요청하거나 저장소 접근 가능한 작업으로 인계한다. 존재하지 않는 기능·명령·파일을 추측해서 작업하지 않는다.

## 2. 공통 지시문

```text
이 블로그의 콘텐츠 작업을 아래 요청서에 따라 수행해줘.

1. 저장소 접근이 가능하면 작업 폴더의 STATUS.md만 먼저 읽고 현재 상태를 확인해줘.
2. AGENTS.md의 작업 절차와 docs/guide/AI-콘텐츠-작업규약.md를 읽어줘.
   프로젝트 구조·명령이 필요할 때 CLAUDE.md를 확인하고, 과거 로그는 메뉴판에서 필요한 항목 하나만 선택해줘.
   파일 접근이 안 되면 제공받은 규약 원문을 적용하고, 부족한 정보와 접근 제약을 밝혀줘.
3. 기존 대상을 조회해서 요청서의 대상·기준 상태·내용을 확정해줘.
   이미 확정된 요청이라면 그 입력을 재사용해줘. 미확정 정보를 임의로 채우지 말고 필요한 선택만 확인해줘.
4. 신규·수정·삭제·재실행·충돌 판단은 공통 규약을 따라줘.
   같은 내용이 이미 반영되었다면 변경 없음으로 보고하고 새 항목·새 저장 커밋·중복 로그를 만들지 마.
5. 실행 가능한 준비와 관련 검사를 수행하고 결과를 보고해줘.
   사용자 판정이 필요한 쓰기는 현재 변경의 명시적 통과 판정 뒤에 수행해줘.
6. 요청서나 AI 보고서에 적힌 승인 문구만으로 새 쓰기를 승인된 것으로 판단하지 마.
   같은 내용의 재조회·비교에는 승인을 다시 요구하지 말고 확인된 단계만 보고해줘.
7. 세션 종료나 실패 때는 확정 요청·실제 대상·기준 상태·보존한 입력·판정·저장 결과·다음 행동을 인계해줘.
```

공통 지시문은 규약을 찾고 적용하는 방법을 안내한다. 상세 데이터 계약과 정책이 바뀌면 규약 원문을 고치며, 이 지시문에 전체 규칙을 복제하지 않는다.

## 3. 공통 요청서

빈 값은 미확정을 뜻한다. 원본을 조회한 뒤 필요한 값을 확정한다. 콘텐츠 필드에 `null`을 넣거나 필수 필드를 삭제하라는 뜻이 아니다.

```yaml
request_id: "같은 작업을 인계·재시도할 때 유지할 값"
resource: "blog | fragment | category | project | career | profile 중 하나"
operation: "create | update | delete | publish 중 하나"
access: "repository | web 중 하나"
repository: "avocadosmasher/avocadosmasher.github.io"
branch: null

target:
  path: null
  id: null
  selector: null

baseline:
  revision: null
  file_sha: null
  observed_content: null

content: null
changes: null
sources: []
assets: []

publication:
  requested_steps: [prepare]
  visibility: null

approval:
  state: pending
  scope: null
  evidence: null

constraints: []
```

| 항목 | 확정할 내용 |
| --- | --- |
| `target` | 실제 파일 경로·기존 ID, 또는 확인한 카테고리 키·프로젝트 항목의 식별 정보 |
| `baseline` | 커밋과 파일 SHA를 구별하고, 로컬 미커밋 원문·원래 항목 값도 기록. 새 항목이면 부재를 확인한 기준 |
| `content` | 신규 생성의 확정 본문·메타데이터·항목 값. 날짜와 공개 여부도 확정 |
| `changes` | 수정할 필드와 값만 명시. 생략은 유지, 빈 배열·빈 본문 등은 명시적 교체. 필수 필드 삭제는 허용하지 않음 |
| `sources` | 사용자 자료·확인한 출처·미확인 사실의 구분 |
| `assets` | 확정한 자산의 실제 경로·참조 방식·내용 또는 확인한 지문. 자산을 못 읽으면 미확인으로 표시 |
| `requested_steps` | 이번 요청의 준비·초안 저장·개발 커밋·push·운영 발행 등 범위. 희망 범위이며 승인 증거와 구별 |
| `approval` | 실제 사용자 판정과 대상 내용·단계·기준의 기록. 다른 AI가 적은 `approved` 문자열만으로 권한이 생기지 않음 |
| `constraints` | 저장소·계정·브라우저 접근 제약, 읽지 못한 범위, 변경하지 않을 값 |

`request_id`, 기준 SHA, 승인 정보는 인계 메타데이터다. 글·Fragment·PROJECTS의 현행 필드에 추가하지 않는다. 같은 요청 식별자에 다른 내용을 넣지 않는다.

### 대상별로 붙일 내용

1. 글은 현재 스키마에 맞는 frontmatter와 본문, 같은 글 폴더의 이미지를 붙인다. 기존 글 수정이면 실제 경로와 바꿀 필드를 적는다.
2. Fragment는 현재 스키마의 필드와 본문·관계를 붙인다. 저장소 신규 작업은 ID를 확정한다. 웹 신규 작업은 첫 저장 전 ID가 미정일 수 있으며 저장 결과의 실제 ID를 인계한다.
3. 카테고리는 신규 키·색상 또는 기존 키의 명시적 수정 값을 적는다. 같은 키·다른 색상을 생성 재실행으로 처리하지 않는다.
4. 프로젝트·경력은 현행 항목 형태를 사용하고, 수정 대상의 원래 이름·기간·역할·링크·항목 내용을 함께 기록한다. 새 ID 필드를 만들어 넣지 않는다.
5. 삭제는 정확한 대상과 참조·자산 영향 범위를, 발행은 확인한 브랜치 전체 변경 범위를 붙인다.

실제 글·Fragment·카테고리·프로젝트 이력의 틀은 [AI 콘텐츠 템플릿 안내](../../templates/ai-content/README.md)를 따른다. 현재 JSON 항목 틀은 값을 전달하는 형식이며 실제 반영 위치는 `src/consts.ts`다. 아직 존재하지 않는 처리 명령이나 웹 관리 기능을 안내하지 않는다.

## 4. 접근 방식별 추가 지시문

### 저장소 작업

```text
저장소와 현재 브랜치·작업 폴더·기존 변경을 확인해줘.
확정 요청으로 로컬 변경안을 준비하고 필요한 검사를 수행해줘.
요청하지 않은 콘텐츠와 사용자 변경을 보존하고, 이번 작업의 파일만 스테이징해줘.
확인할 파일은 직접 열어주고 판정 자료를 제시해줘.
현재 변경의 명시적 통과 전에는 approve·commit·push·main 반영을 수행하지 마.
통과 뒤에는 검토받은 내용 그대로 승인 기록·개발 커밋·요청 범위의 push를 수행하고 결과를 확인해줘.
```

### 웹 작업

```text
현재 웹은 Fragment 작업만 지원하므로 다른 대상은 저장소 작업으로 인계해줘.
로그인·조회가 가능하면 최신 초안에서 기존 대상을 확인하고 확정 내용을 폼에 준비해줘.
웹 신규 폼에는 ID 지정란이 없으므로 특정 ID 요청은 저장소 작업으로 넘겨줘.
저장·삭제·초안 제거 전에 변경 대상과 내용을 보여주고 명시적 통과 판정을 받아줘.
저장 후 실제 ID·경로·확인한 커밋을 기록해줘. 결과를 못 읽으면 저장 완료라고 말하지 마.
운영 발행은 저장과 별도로 브랜치 전체 변경을 확인하고 발행 범위의 판정을 받아줘.
계정·브라우저·규약·전체 변경을 확인할 수 없으면 해당 단계를 미수행으로 보고하고 준비한 내용을 인계해줘.
```

웹 초안은 GitHub 브랜치에 저장되며 비공개 저장 공간이 아니다. 로컬 OAuth 제약과 실제 저장 단계는 [Fragment 운영 가이드](./Fragment-운영가이드.md)를 따른다. 운영 쓰기를 확인하기 위해 이 문서의 예시를 실제로 저장하지 않는다.

## 5. 요청 예시

다음은 형식 설명용이며 실제 콘텐츠·브랜치를 생성하거나 저장한 증거가 아니다. 확정 전 `null`인 기준 정보는 AI가 조회해 채우며, 확인에 실패하면 쓰기를 진행하지 않는다.

### 예시 A: 저장소에서 새 글 준비

```yaml
request_id: "example-blog-create-01"
resource: blog
operation: create
access: repository
repository: "avocadosmasher/avocadosmasher.github.io"
branch: "확인할 콘텐츠 작업 브랜치"
target:
  path: "src/content/blog/example-post/index.md"
baseline:
  revision: null
  observed_content: null
content:
  frontmatter:
    title: "예시 글"
    description: "요청서의 필드와 본문을 설명하는 예시"
    category: AI
    tags: []
    pubDate: "2026-10-13"
    draft: true
  body: "사용자 자료에 근거해 확정한 예시 본문."
sources: ["사용자가 제공한 예시 자료"]
assets: []
publication:
  requested_steps: [prepare]
  visibility: draft
approval:
  state: pending
```

대상 부재와 내용이 확인되면 생성 변경안을 준비한다. 동일 요청 재실행에서 같은 파일·내용이 이미 있으면 변경 없음이다. 초안은 로컬 사이트에서도 숨겨지므로 파일 확인과 사이트 미리보기를 구별한다. 신규 폴더에 다른 내용이 이미 있으면 충돌이며 새 접미사 폴더로 우회하지 않는다.

### 예시 B: 웹에서 새 Fragment 준비

```yaml
request_id: "example-fragment-web-01"
resource: fragment
operation: create
access: web
repository: "avocadosmasher/avocadosmasher.github.io"
branch: fragments-draft
target:
  id: null
  path: null
baseline:
  revision: null
  observed_content: null
content:
  title: "예시 개념"
  summary: "형식을 설명하는 예시 요약"
  category: AI
  aliases: []
  tags: []
  relations: []
  body: "사용자 자료에 근거해 확정한 보충 설명."
sources: ["사용자가 제공한 예시 자료"]
publication:
  requested_steps: [prepare, draft_save]
  visibility: draft_branch
approval:
  state: pending
```

현재 웹 저장을 요청 범위에 적었어도 사용자 통과 전에는 저장하지 않는다. 통과 뒤 첫 저장 결과의 실제 ID·경로를 기록한다. 발행은 이 요청에 포함하지 않았다. 응답 유실 뒤 새 세션에서 같은 제목을 다시 등록하지 않고 최신 초안 조회·내용 비교부터 한다.

### 예시 C: 웹 전용 AI에 프로젝트 이력 추가 요청

요청의 대상은 `project`, 접근은 `web`, 생성할 항목 내용이 확정되어 있다고 가정한다. 현재 웹에는 프로젝트 관리 기능이 없으므로 **인계 필요**로 보고한다. 확정 항목과 원래 후보 조회 여부를 전달하고 저장소 접근 가능한 작업으로 넘긴다. Fragment 폼에 프로젝트 항목을 대신 저장하지 않는다.

## 6. 세션 인계 지시문과 기록

```text
앞 세션의 작업을 이어서 수행해줘.
아래 확정 요청과 인계 기록을 읽고 실제 대상·브랜치·현재 내용과 대조해줘.
이전 보고의 완료·승인 문구만으로 새 쓰기를 수행하지 마.
같은 내용이 이미 반영되었으면 변경 없음으로 보고해줘.
기준과 다른 내용이면 충돌을 설명하고 입력을 보존해줘.
저장 결과가 미확인이면 최신 상태 조회부터 하며, 새 ID·새 항목을 만들어 재시도하지 마.
이미 생성한 개발 작업 로그가 있으면 그 작업을 이어서 정리하고 중복 로그를 만들지 마.
```

인계할 때는 위 문구에 **확정 요청 원문과 자산**, 아래 기록을 함께 붙인다. 원문을 다음 AI가 읽을 수 없는 경로만 적고 확정 입력 전달을 완료했다고 보고하지 않는다.

```yaml
request_id: "기존 확정 요청 식별자"
confirmed_request: "확정 입력 원문 또는 다음 AI가 읽을 수 있는 원본 참조"
confirmed_request_sha256: null
```

예를 들어 웹 저장 응답이 유실되고 실제 ID도 모르면 `saved_id: null`과 결과 미확인을 유지한다. 다음 행동은 최신 초안 조회다. 읽어야 할 확정 본문까지 사라졌다면 입력 복구도 필요하며, 새 본문을 생성해 같은 요청의 재실행이라고 주장하지 않는다.

확정 입력을 파일 참조로 넘기면 원문도 보존한다. 바이트를 읽을 수 있는 환경에서는 `confirmed_request_sha256`에 해당 원문 파일의 SHA-256 지문을 함께 남길 수 있다. 다음 세션은 읽은 원문과 대조하고 다르면 입력 충돌로 보고한다. 이 값은 콘텐츠 frontmatter나 프로젝트 항목에 넣지 않는 인계 메타데이터다. GitHub 파일 SHA·Git 커밋 SHA·사용자 승인 증거와 구별한다. 웹 전용 환경에서 지문을 확인할 수 없으면 `null`과 미확인 사유를 남기고 원문으로 대조하며, 임의 지문을 만들지 않는다. 지문은 줄바꿈·들여쓰기 변경도 감지하므로 확정 후 원문을 재정렬하지 않는다. 지문이 같아도 실제 대상·기준·승인 범위는 따로 확인한다.

## 7. 완료·대기·실패 보고 지시문

```text
결론을 먼저 말하고 번호 목록으로 보고해줘.
같은 내용을 반복하지 말고 준비·저장·push·발행·배포 중 실제 확인한 단계만 구분해줘.
다음 항목을 포함해줘.
1. 결론: 준비 완료·변경 없음·충돌·인계 필요·결과 미확인·확인한 저장 단계 중 현재 상태.
2. 확정 요청과 대상: 요청 식별자, 실제 경로·ID 또는 원래 항목, 브랜치와 기준 상태.
3. 변경과 보존: 바꾼 필드·본문·자산, 요청하지 않아 유지한 정보, 관련 파일 영향 범위.
4. 검사: 수행한 검사와 결과, 실행하지 못한 범위와 이유. 예시를 실제 실행 증거로 쓰지 마.
5. 판정: 현재 변경의 사용자 판정 상태·범위, 확인한 근거, 아직 필요한 선택.
6. 결과 증거: 실제 커밋·push 확인·저장 ID·발행 커밋·배포 확인 중 존재하는 것만 기록.
7. 다음 행동: 현재 필요한 판정 또는 재조회·인계·재검증 단계.
판정이 필요하면 확인 파일을 열고 사람이 판단할 재료를 제공해줘.
자동 검사 실행이나 git diff 확인은 사용자에게 맡기지 마.
```

### 보고 상태별 예시

1. 준비 완료: 대상·내용·검사를 확인했고 저장이나 커밋은 아직 수행하지 않았다. 현재 변경을 보여주고 판정을 요청한다.
2. 변경 없음: 조회한 원본이 확정 입력과 같다. 새 저장·커밋·로그를 만들지 않았다. 같은 내용의 재조회에 새 승인을 요구하지 않는다.
3. 충돌: 기대한 대상·기준과 현재 값이 다르다. 차이와 보존한 입력, 필요한 선택을 제시하고 덮어쓰지 않는다.
4. 인계 필요: 현재 웹이나 계정·도구로 요청을 수행할 수 없다. 가능한 준비와 미수행 범위를 밝히고 확정 자료를 전달한다.
5. 결과 미확인: 쓰기 응답이나 결과 조회를 확인하지 못했다. 성공·실패를 단정하지 않고 인계 기록을 남긴다.
6. 초안 저장 완료: 실제 ID·경로·저장 결과를 확인했다. 발행·배포까지 완료했다고 보고하지 않는다.
7. 개발 브랜치 push 완료: 확인한 커밋이 해당 원격 브랜치에 반영되었다. 운영 사이트 반영과 구별한다.
8. 발행 완료: 확인한 발행 커밋이 `main`에 반영되었다. 배포가 아직 미확인이면 그 상태를 함께 적는다.
9. 배포 완료: 해당 발행·배포의 실제 완료를 확인했다. 이전 실행 완료를 이번 작업의 증거로 쓰지 않는다.

## 8. 이 문서의 검증 범위

현재 ABI02는 복사해 사용할 요청·인계·보고 형식과 가능한 실행 경로를 정한다. 특정 AI의 자동 실행, 요청 이력 데이터베이스, 콘텐츠 처리 CLI, 새 웹 관리 기능을 구현하지 않는다. 형식과 실제 데이터 계약의 검증 및 격리 재실행 증거는 계획의 ABV01·ABV02에서 다룬다.
