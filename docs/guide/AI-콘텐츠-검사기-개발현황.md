# AI 콘텐츠 검사기 개발 현황

- 개발 건: AI-CONTENT-TOOLS / ACTV02, 2026-10-16, 사용자 판정 대기.
- 선행: ACTV01 사용자 통과 `7a37ee1`, 개발 브랜치 push 완료.
- 범위: [2차 개발계획](../plan/AI-콘텐츠-자동화-2차-개발계획.md)의 문서별 검사와 전체 관계·카테고리 검사를 구현했다. 실행 CLI·파일 적용·저장 차단은 후속 단계다.

## 이번에 생긴 기능

글 또는 Fragment의 파일 경로·종류·Markdown 원문을 전달하면, 원문을 바꾸지 않고 형식 오류를 돌려주는 검사 모듈을 추가했다. 잘못된 입력을 발견해도 파일을 자동으로 고치거나 날짜·ID를 새로 정하지 않는다. 호출한 프로그램이 원인을 보고 수정할 수 있도록 파일·필드·규칙·이유를 반환한다.

기존 블로그와 검사기가 다른 필수 필드 정의를 갖지 않도록 실제 글·Fragment 스키마를 공통 모듈로 분리했다. 기존 Astro 수집과 Fragment 저장은 같은 데이터 계약을 계속 사용한다. 공백 제목·달력 날짜·미완성 치환값 같은 작성 규칙은 별도 검사 모듈에서 보완한다.

ACTV02에서는 여러 문서를 함께 전달해 중복 ID·관계·등록 카테고리를 검사할 수 있다. 검사 결과는 실패해야 할 새 오류와 보존하기로 한 기존 문제를 분리한다. 모듈이 직접 파일을 찾는 구조는 아니므로, 전달받지 않은 파일까지 검사했다고 보장하지 않는다. 실제 저장소를 수집하는 CLI는 ACTC01에서 추가한다.

## 어떤 문제를 잡는가

아래 입력은 격리 테스트용 예시이며 운영 글을 수정한 내역이 아니다.

| 입력 예시 | 발생 가능한 문제 | 이번 검사 결과 |
| --- | --- | --- |
| 제목 필드 없음 | 필수 정보 없이 파일 준비 | `content.required`, `title` 누락 진단 |
| 제목이 공백뿐 | 문자열 형식만 맞아 기본 스키마 통과 | 공백 필수 문자열 진단 |
| 발행일 `2026-02-30` | 날짜 파서가 실제 다른 날짜로 보정 | `blog.date`, 실제 달력 날짜 오류 진단 |
| 날짜가 `2026-2-03` 또는 시간 포함 값 | 확정한 YYYY-MM-DD 형식과 다름 | 날짜 형식 오류 진단 |
| 제목이나 본문에 `{{TITLE}}`·`{{INTRO}}` 남음 | 작성 틀을 채우지 않은 상태 | `content.placeholder`와 필드 진단 |
| Fragment ID가 `../unsafe` 또는 대문자 포함 | 현재 ID 계약에 맞지 않음 | ID 필드 형식 오류 진단 |
| Fragment에 `draft` 추가 | 현재 Fragment 저장기가 지원하지 않는 필드 | `content.unknown-field` 진단 |
| YAML에 title 두 번 작성 | 앞 값을 덮어쓰거나 원문 해석이 달라짐 | `yaml.invalid`, 실제 줄·열 진단 |
| 앞에 다른 내용이 있는 문서 | 올바른 frontmatter 시작을 찾지 못함 | 구분자 오류 진단 |

날짜·태그·관계 등의 기본 타입은 공유 스키마를 따른다. 중첩 오류는 `tags.0`처럼 실제 필드 위치를 포함한다. YAML 오류는 원문을 추측해 복구하지 않고 진단으로 반환한다.

## 정상적인 설명 예제는 어떻게 구별하는가

템플릿 문법을 설명하는 글에서는 치환 표시 자체가 코드 예제일 수 있다. 그래서 본문의 인라인 코드와 fenced/들여쓰기 코드 블록은 미완성 본문 검사에서 제외한다. 일반 문장·링크·이미지 경로에 남은 대문자 `{{...}}` 표시는 검사한다.

예를 들어 인라인 코드로 쓴 `{{TITLE}}`는 설명 자료로 허용하고, 일반 본문에 남은 `{{INTRO}}`는 치환 누락으로 보고한다. 이 검사는 템플릿 표시의 제한된 패턴을 확인하는 것이며 본문의 사실성·문체·완성도를 판정하지 않는다.

## 여러 파일을 함께 검사해야 잡히는 문제

아래 A·B·C는 격리 테스트를 설명하는 임의의 Fragment ID다. 운영 파일의 ID를 바꾼 예시가 아니다.

| 입력 예시 | 문제가 되는 이유 | 검사 결과 |
| --- | --- | --- |
| 서로 다른 두 파일에 같은 ID `card-a` | 관계 대상이 어느 파일인지 모호함 | `fragment.duplicate-id`, 현재 파일과 먼저 발견한 파일 표시 |
| A의 관계 대상은 B인데 B 파일 없음 | 연결할 카드를 찾을 수 없음 | `fragment.missing-target`, 대상 필드와 값 표시 |
| A가 자기 ID A를 참조 | 자기 카드와의 관계로 현재 규약 위반 | `fragment.self-relation` |
| A → B를 쓰고 B → A도 작성 | 같은 두 카드에 관계를 두 번 저장 | `fragment.duplicate-relation` |
| A → B에 related와 prerequisite를 각각 작성 | 현재는 카드 쌍마다 관계 하나만 허용 | 유형이 달라도 관계 중복 진단 |
| A → B와 A → C 작성 | 서로 다른 카드 쌍의 정상 관계 | 다른 오류가 없다면 통과 |
| 새 글이나 Fragment에 미등록 `Infra` 사용 | 등록 정보와 콘텐츠 값이 불일치 | `category.unregistered`, 실제 경로와 값 표시 |

중복 ID를 피하려고 검사기가 새 ID를 발급하거나, 없는 관계를 임의로 삭제하지 않는다. ID·관계·카테고리를 정하는 권한은 요청자에게 있고 검사기는 충돌을 설명한다. 같은 제목이나 비슷한 본문의 의미 중복까지 판정하는 기능은 아니다.

일부 Fragment의 필수 필드가 없으면 카드 전체를 제대로 읽지 못한 상태다. 이때는 해당 형식 오류를 반환하고 `graphChecked: false`로 관계 검사 미수행을 표시한다. 읽지 못한 카드를 없다고 추정해 관계 검사가 끝났다고 보고하지 않는다. 중복 경로·중복 ID도 전체 대상을 확정할 수 없으므로 같은 방식으로 처리한다. `graphChecked: true`는 관계 검사를 수행했다는 뜻이며 관계 오류가 없다는 뜻은 아니다.

## 기존 Infra 4건을 보존하는 방법

현재 글 2개와 Fragment 2개는 `Infra`를 사용하지만 CATEGORIES에는 등록되어 있지 않다. 이를 즉시 오류로 막으면 기존 자료를 바꾸어야 하고, Infra를 모두 허용하면 새 미등록 사용도 통과한다. 그래서 [예외 목록](../../config/content-policy-baseline.json)에 **규칙 ID·정확한 파일 경로·문제 값**이 모두 같은 4건만 기록했다. 카테고리 등록이나 콘텐츠 이관은 하지 않았다.

예를 들어 `src/content/fragments/ept.md`의 `category: Infra`는 다음처럼 처리한다.

| 변경 예시 | 결과 | 이유 |
| --- | --- | --- |
| 같은 파일의 제목만 수정 | 기존 예외로 보고 후 허용 | 경로·규칙·문제 값이 같음 |
| 새 파일 `new-card.md`에 Infra 작성 | 실패 | 등록된 예외 경로와 다름 |
| ept.md의 카테고리를 다른 미등록 값으로 수정 | 실패 | 기존 예외의 문제 값과 다름 |
| ept.md의 제목 필드 삭제 | 실패 | 카테고리 예외로 다른 규칙을 면제하지 않음 |
| 별도 합의로 등록 카테고리로 변경 | 카테고리 오류 없음, 미사용 예외로 보고 | 예외가 더 이상 필요하지 않음을 알림 |

예외 파일에는 버전 1과 정확한 항목만 허용한다. 와일드카드·상위 경로 이동·중복 항목·알 수 없는 규칙·잘못된 버전은 설정 오류다. 현재 발생 중인 기존 문제는 `knownIssues`, 사용하지 않은 예외는 `unusedExceptions`, 실패할 오류는 `diagnostics`로 구별한다. 새 예외를 자동으로 추가하거나 오래된 예외를 자동 삭제하지 않는다.

파일 이동 시 예외가 자동으로 따라가지 않는 것은 이 선택의 비용이다. 기존 경로를 보존하거나 이동 의도와 새 예외를 별도로 검토해야 한다. 예외 파일을 사람이 직접 바꾸는 행위 자체를 사용자 인증으로 제한하는 기능은 없으며 Git 검토 절차를 따른다.

## 확인한 결과

ACTV01의 문서별 검사 42개에 ACTV02의 단위 검사 34개와 실제 콘텐츠 통합 검사 1개를 추가했다. 관계 중복·기존 예외의 정확한 범위·잘못된 예외 설정·입력 순서 독립성·입력 보존을 확인했다. 나머지 기존 기능을 포함한 전체 회귀 테스트는 212개 통과했다.

현재 글 로더 대상 13개와 Fragment 3개, 실제 CATEGORIES, 기존 예외 파일을 읽어 검사했다. 새 오류 0건·기존 예외 4건·미사용 예외 0건이며 관계 검사도 수행됐다. 각 콘텐츠와 예외 파일의 검사 전후 바이트도 일치했다. 기존 로더가 수집하지 않는 평면 Markdown 파일을 새 글로 포함하지 않았다.

타입 검사 오류 0·경고 0·기존 힌트 5개이며 일반 빌드는 11페이지·18이미지로 성공했다. 이번에는 기존 빌드·저장 스키마를 변경하지 않아 ACTV01에서 통과한 4개 격리 빌드와 브라우저 검사를 반복하지 않았다. 전체 실행 결과는 [ACTV02 작업 로그](../log/72-ACTV02.md)에 기록한다.

## 아직 하지 않는 일

1. 사용자가 실행할 검사 CLI는 ACTC01에서 제공한다. 현재 API는 문서 하나를 검사하는 `validateContentSource`와 전달한 문서 집합을 검사하는 `validateContentCollection`이다. 저장소를 자동으로 수집하는 실행 명령은 아직 없다.
2. 전체 검사 모듈을 기존 Astro 수집기나 웹 저장기에 연결하지 않았다. 새 정책을 운영 저장 과정에서 이미 차단하고 있다고 해석하지 않는다.
3. 파일 생성·부분 수정·재시도 기록·잠금·복구·실제 적용은 이후 작업이다. 이번 모듈에는 파일 읽기·쓰기 기능이 없다.
4. 콘텐츠 검사 결과를 커밋 차단에 연결하는 Hook과 데이터 검사를 수행하는 CI 연결은 ACTH01 범위다. 기존 승인 훅은 유지했다. 새 단위 검사는 기존 `npm test`의 실행 대상에 포함된다.
5. 화면·OAuth·실제 계정·외부 저장·main 반영·운영 배포는 변경하지 않았다.

## 이번 판정 대상

사람이 눌러 볼 새 화면이나 CLI는 아직 없다. 자동 검사는 에이전트가 수행했다. 이번 판단 대상은 기존 Infra 4건을 정확한 예외로만 보존하고 새 위반은 실패시키는 기준, 방향·유형에 무관한 카드 쌍 중복 기준이다. 자동 오류 수정이나 운영 데이터 이관은 포함하지 않는다. 통과 뒤 저장하고 ACTC01의 실제 실행 CLI로 진행한다.
