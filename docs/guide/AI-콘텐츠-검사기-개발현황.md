- 선행: ACTP01 사용자 통과 `bd33341`, 개발 브랜치 push 완료.
- 범위: [2차 개발계획](../plan/AI-콘텐츠-자동화-2차-개발계획.md)의 첫 번째 구현이다. 아직 전체 자동화 도구가 완성된 것은 아니다.

## 이번에 생긴 기능

글 또는 Fragment의 파일 경로·종류·Markdown 원문을 전달하면, 원문을 바꾸지 않고 형식 오류를 돌려주는 검사 모듈을 추가했다. 잘못된 입력을 발견해도 파일을 자동으로 고치거나 날짜·ID를 새로 정하지 않는다. 호출한 프로그램이 원인을 보고 수정할 수 있도록 파일·필드·규칙·이유를 반환한다.

기존 블로그와 검사기가 다른 필수 필드 정의를 갖지 않도록 실제 글·Fragment 스키마를 공통 모듈로 분리했다. 기존 Astro 수집과 Fragment 저장은 같은 데이터 계약을 계속 사용한다. 공백 제목·달력 날짜·미완성 치환값 같은 작성 규칙은 별도 검사 모듈에서 보완한다.

## 어떤 문제를 잡는가

아래 입력은 격리 테스트용 예시이며 운영 글을 수정한 내역이 아니다.

| 입력 예시 | 발생 가능한 문제 | 이번 검사 결과 |
| --- | --- | --- |
| 제목 필드 없음 | 필수 정보 없이 파일 준비 | `content.required`, `title` 누락 진단 |
| 제목이 공백뿐 | 문자열 형식만 맞아 기본 스키마 통과 | 공백 필수 문자열 진단 |
| 발행일 `2026-02-30` | 날짜 파서가 실제 다른 날짜로 보정 | `blog.date`, 실제 달력 날짜 오류 진단 |
| 날짜가 `2026-2-03` 또는 시간 포함 값 | 확정한 YYYY-MM-DD 형식과 다름 | 날짜 형식 오류 진단 |
| 제목이나 본문에 `{{TITLE}}`·`{{INTRO}}` 남음 | 작성 틀을 채우지 않은 상태 | `content.placeholder`와 필드 진단 |
| Fragment ID가 `../unsafe` 또는 대문자 포함 | 현재 ID 계약에 맞지 않음 | ID 필드 형식 오류 진단 |
| Fragment에 `draft` 추가 | 현재 Fragment 저장기가 지원하지 않는 필드 | `content.unknown-field` 진단 |
| YAML에 title 두 번 작성 | 앞 값을 덮어쓰거나 원문 해석이 달라짐 | `yaml.invalid`, 실제 줄·열 진단 |
| 앞에 다른 내용이 있는 문서 | 올바른 frontmatter 시작을 찾지 못함 | 구분자 오류 진단 |

날짜·태그·관계 등의 기본 타입은 공유 스키마를 따른다. 중첩 오류는 `tags.0`처럼 실제 필드 위치를 포함한다. YAML 오류는 원문을 추측해 복구하지 않고 진단으로 반환한다.

## 정상적인 설명 예제는 어떻게 구별하는가

템플릿 문법을 설명하는 글에서는 치환 표시 자체가 코드 예제일 수 있다. 그래서 본문의 인라인 코드와 fenced/들여쓰기 코드 블록은 미완성 본문 검사에서 제외한다. 일반 문장·링크·이미지 경로에 남은 대문자 `{{...}}` 표시는 검사한다.

예를 들어 인라인 코드로 쓴 `{{TITLE}}`는 설명 자료로 허용하고, 일반 본문에 남은 `{{INTRO}}`는 치환 누락으로 보고한다. 이 검사는 템플릿 표시의 제한된 패턴을 확인하는 것이며 본문의 사실성·문체·완성도를 판정하지 않는다.

## 확인한 결과

새 검사 사례는 42개다. 누락 필드·공백·실제 날짜·잘못된 ID·YAML·미완성 값·정상 코드 예제·BOM/CRLF를 검사했다. 같은 원문 재검사에서 같은 결과를 반환하고 입력을 변경하지 않는 것도 확인했다.

현재 수집 대상인 글 13개와 Fragment 3개를 읽기 전용으로 검사해 형식 진단 0건을 확인했다. 각 파일의 검사 전후 바이트도 일치했다. 이는 아래의 미구현 정책까지 통과했다는 뜻이 아니다.

전체 회귀 테스트·타입·일반 빌드·격리 빌드는 작업 로그에 실제 실행 결과를 기록한다. 기존 타입 힌트 5개와 기존 코드블록 언어명의 Shiki fallback 알림은 이번 범위에서 변경하지 않는다.

## 아직 하지 않는 일

1. 등록 카테고리·중복 ID·없는 관계 대상·자기 참조·관계 쌍 중복을 전체 콘텐츠에서 검사하는 기능은 ACTV02에서 추가한다. 따라서 기존 Infra 4건도 이번 단일 문서 검사에서 차단하지 않는다.
2. 사용자가 실행할 검사 CLI는 ACTC01에서 제공한다. 현재 프로그램 API는 `validateContentSource`이며 저장소 폴더를 자동으로 훑는 명령을 추가한 상태는 아니다.
3. 파일 생성·부분 수정·재시도 기록·잠금·복구·실제 적용은 이후 작업이다. 이번 모듈에는 파일 읽기·쓰기 기능이 없다.
4. 콘텐츠 검사 결과를 커밋 차단에 연결하는 Hook과 데이터 검사를 수행하는 CI 연결은 ACTH01 범위다. 기존 승인 훅은 유지했다. 새 단위 검사는 기존 `npm test`의 실행 대상에 포함된다.
5. 화면·OAuth·실제 계정·외부 저장·main 반영·운영 배포는 변경하지 않았다.

## 이번 판정 대상

사람이 눌러 볼 새 화면이나 CLI는 아직 없다. 자동 검사는 에이전트가 수행했다. 판단할 내용은 누락·잘못된 날짜·치환값을 자동 수정하지 않고 원인과 위치로 설명하는 방식, 코드 예제를 정상 자료로 구별하는 기준이다. 이 모듈을 확정한 뒤 전체 콘텐츠 정책 검사로 진행한다.
