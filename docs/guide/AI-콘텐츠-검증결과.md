## 실행 방법과 운영 보호

`npm test`는 기존 검사와 템플릿 통합 검사를 함께 실행한다. `npm run test:ai-content:build`는 합성 글·카드·카테고리·프로젝트로 실제 Astro 빌드 4건을 실행한다. PR과 배포의 공통 Verify 워크플로에도 같은 명령을 연결했다.

검증 폴더는 `.fragment-test/ai-content-<임의 접미사>/`이며 버전 관리하지 않는다. 앱 소스와 템플릿의 사본만 준비하고 운영 글·카드 디렉터리는 복사 대상에서 제외한다. 각 사본에 확정한 합성 데이터를 넣는다. 실제 원본·Git·환경 파일을 수정하거나 GitHub API를 호출하지 않는다. Fragment 관련 환경변수는 자식 빌드에서 제거해 외부 콘텐츠 경로나 운영 저장 설정을 물려받지 않는다.

성공 때는 사례별 PASS와 진단 폴더만 출력한다. 예상과 다른 실패 때는 해당 빌드 상세를 출력한다. 각 사본의 `build.log`와 산출물을 보존하므로 문제를 재현할 수 있다. 검증 스크립트는 고정 예시의 생성·검사용이며 사용자의 콘텐츠를 등록하는 명령이 아니다.

스키마 검사에서는 Astro의 컬렉션 등록·로더 어댑터만 대체하고 실제 `src/content.config.ts`와 Fragment 검증 함수를 실행한다. 실제 빌드 검사는 어댑터를 대체하지 않는다. ProjectItem은 실제 TypeScript 선언에서 필드·필수 여부·타입을 읽는다.

## 자동 검사로 보장하지 않는 것

1. 등록되지 않은 카테고리도 현재 글·Fragment 스키마를 통과한다. 공통 Fragment 검증은 같은 카드 쌍의 관계 중복까지 거절하지 않는다. 이 실제 한계도 테스트에 명시했으며 규약 준수 여부는 별도로 확인한다.
2. 글의 출처·사실·문체·설명 품질, 실제 경력·프로젝트 성과의 진위는 스키마나 빌드로 증명하지 않는다.
3. 프로젝트 항목의 영구 ID, 모든 AI의 중복 방지, 동일 자연어에서 동일 본문 생성, 자동 콘텐츠 처리 엔진을 제공하지 않는다.
4. 화면·작성기 동작을 변경하지 않아 브라우저 E2E를 재실행하지 않았다. 실제 OAuth·GitHub 저장·발행·운영 배포는 이번 검증 범위에 없다. CI 연결은 로컬에서 확인했고 원격 워크플로 실행 결과는 아직 없다.

## 이번 판정 대상

운영 화면을 변경하지 않았고 반복 가능한 검사는 에이전트가 수행했다. 사용자가 자동 검사나 diff 확인을 다시 할 필요는 없다. 판단할 내용은 위 결과로 확인한 범위와 남은 한계를 구분해 다른 AI에게 전달할 수 있는지다. 재실행·세션 인계 검증과 최종 완료 증거가 남아 있으므로 AI-BLOG 1차 전체 완료로 표시하지 않는다.
