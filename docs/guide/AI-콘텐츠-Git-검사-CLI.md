# AI 콘텐츠 Git 훅·공통 CI 검사

- 개발 건: AI-CONTENT-TOOLS / ACTH01, 2026-10-19 착수·2026-10-20 사용자 통과, `8065fd6` 커밋·개발 브랜치 push 완료.
- 선행: ACTS01 사용자 통과, `69cd526` 커밋·개발 브랜치 push 완료.
- 이번 대상: 기존 사용자 승인 검사 뒤 콘텐츠 정책 검사 추가, PR·개발 push·배포의 공통 검증 연결.

## 결론과 이번 판정

- 커밋은 스테이징된 Git tree, push는 실제 전송할 커밋의 Git tree를 검사하도록 연결함.
- 기존 사용자 승인 검사에 성공해도 콘텐츠 정책 오류가 있으면 커밋·push 중단함.
- PR·개발 브랜치 push·배포가 사용하는 공통 verify 워크플로에 콘텐츠 정책 검사와 실제 처리 도구 격리 빌드 추가함.
- 기존 승인 명령·승인 자료 형식·검토 트리/기준 커밋 대조·참조 삭제 차단 규칙 유지함. 자동 검사 성공을 대화의 통과 판정으로 바꾸지 않음.
- 사람이 직접 실행해야 할 항목 없음. 실제 합성 Git 저장소의 커밋·로컬 bare 원격 push와 파일 결과·종료 코드로 자동 검증함. 운영 콘텐츠·실제 외부 저장·화면 변경 없음.
- 이번 설명과 적용 경계에 대한 판정 대기임. 통과 후 이번 변경 커밋·개발 브랜치 push, 실제 GitHub Actions 실행 확인 예정임.

## 왜 작업 폴더와 Git 대상을 구별하는가

- 파일을 저장하는 것과 git add로 스테이징하는 것은 별개임. 커밋에는 스테이징된 내용이 들어가므로 작업 폴더 파일만 검사하면 다른 결과를 볼 수 있음.
- 예: 잘못된 카테고리를 스테이징한 뒤 작업 폴더에서만 고침 → 작업 폴더 검사는 통과할 수 있으나 실제 커밋에는 오류가 남음. 새 훅은 스테이징된 오류를 확인하고 중단함.
- 반대 예: 승인한 정상 내용을 스테이징한 뒤 작업 폴더에서 다른 수정 중 → 승인된 정상 커밋은 허용하고 아직 포함하지 않은 작업 폴더 내용은 보존함.
- push는 스테이징 상태와도 다름. 보낼 커밋이 현재 HEAD와 다를 수 있으므로 pre-push가 받은 실제 커밋 ID를 사용함.

| 시점 | 사용자 승인 확인 | 콘텐츠 검사 대상 |
| --- | --- | --- |
| commit | 기존 승인기의 기준 커밋·스테이징 tree 일치 | 해당 인덱스의 tree |
| push | 기존 승인기의 각 전송 커밋 tree·부모 일치 | 전송할 각 고유 tree |
| CI | 로컬 대화/승인 파일 인증 없음 | 체크아웃된 커밋의 콘텐츠·타입·테스트·실제 빌드 |

- Git tree는 한 시점의 파일 목록·모드·바이트를 가리키는 Git 객체임. 변경계획의 SHA-256과 다른 종류의 지문임.
- pre-push 입력은 한 번 읽어 승인기에 그대로 전달한 뒤 같은 참조 목록의 콘텐츠를 검사함. 여러 참조를 보낼 때 일부 입력을 잃지 않음.
- 삭제 참조는 기존 승인기가 계속 거절함. 실제 전송 내용이 없는 호출은 새 콘텐츠 적용으로 취급하지 않음.

## 연결한 프로그램과 검사 범위

- 두 훅은 scripts/git-gates.mjs를 실행함. 이 실행기는 기존 scripts/manual-review.mjs의 check-commit/check-push를 먼저 호출하고, 승인 검사가 통과했을 때만 콘텐츠 검사를 수행함.
- Git tree의 문서·정적 CATEGORIES·기존 예외 JSON을 OS 임시 폴더의 사본에 준비한 뒤 기존 checkContentRepository를 재사용함. 다른 검사 규칙을 복제하지 않음.
- 글은 기존 폴더/index.md, Fragment는 기존 .md 수집 규칙 사용함. 평면 블로그 Markdown·아직 추적하지 않은 파일을 새 글로 포함하지 않음.
- 정책 데이터는 Git 대상에서 읽음. 작업 폴더의 다른 카테고리·예외 JSON으로 검사 대상을 바꾸지 않음. 기존 예외는 규칙·정확한 경로·값만 허용하며 다른 경로의 같은 값은 실패함.
- Git 링크·submodule을 콘텐츠 검사 경로에서 발견하면 따라가지 않고 실패함. 해석할 수 없는 경로·Git 응답·필수 파일 누락도 통과로 간주하지 않음.
- 사본에는 정책 검사에 필요한 Markdown·설정·예외 바이트만 읽음. 이미지 같은 자산 바이트 전체를 복사하지 않음. Git 응답에는 64MiB 버퍼 한계가 있으며 초과하면 실패함.
- 자신이 만든 임시 폴더 하나만 경계 확인 후 제거함. 실제 사용자 파일·인덱스 내용·승인 파일을 검사기가 고치지 않음. Git tree 생성에 필요한 Git 객체 기록은 발생할 수 있음.
- 실제 프로젝트 대상 선택·부분 수정·요청/계획/완료 기록의 일치 검사는 [도구 요청 계약](./AI-콘텐츠-요청-계약.md)과 각 Tool이 담당함. Git 정책 검사는 현재 문서 형식·등록 카테고리·Fragment 관계·예외 규칙이며 모든 작업 의도를 판독하는 기능은 아님.

## 로컬 준비와 평소 사용

- 현재 작업 폴더의 core.hooksPath는 .githooks임을 확인함. 최초 체크아웃은 AGENTS의 기존 설정 절차를 따름. 다른 커스텀 훅 경로가 있으면 덮어쓰지 말고 통합 필요함.
- 기존 두 훅이 100644로 추적되어 Linux에서 생략될 수 있음을 발견함. 이번에 두 파일을 Git 실행 권한 100755로 등록하고 재발 방지 검사 추가함. Windows의 파일 속성 변경만으로 해결했다고 주장하지 않음.
- 일반 콘텐츠 검사는 `npm run content:check`, 훅 통합 사례만 확인할 때는 `npm run test:git-gates` 사용 가능함. 둘 다 에이전트가 실행하고 사용자에게 반복 실행을 요청하지 않음.
- 평소 완료 순서는 기존과 같음: 자동 검사 → 로그·스테이징 → 사용자 통과 → 기존 approve → commit → 개발 브랜치 push임.
- git-gates.mjs에는 approve 모드 없음. 검사 실패를 해결하려고 승인 파일을 조작하거나 훅을 끄는 우회 없음. 콘텐츠를 고치면 새 검증·현재 변경 판정 필요함.
- 실패 시 승인 오류 또는 콘텐츠의 규칙·실제 경로·이유를 보고함. 오류가 생겼다고 인덱스나 최신 작업 폴더를 자동 복원하지 않음.

## 공통 CI에 추가한 검사

- 기존 .github/workflows/verify.yml에 npm run content:check와 npm run test:content-ops:build 추가함. 타입·전체 단위/통합·기존 격리 빌드·일반 빌드·preview/기존 브라우저 검사는 유지함.
- 새 Git 훅 통합 테스트는 기존 npm test에 포함됨. CI에서 같은 파일을 별도 명령으로 중복 실행하지 않음.
- PR/개발 push는 기존 ci.yml, main/수동 배포는 기존 deploy.yml이 같은 verify를 호출함. 새 별도 검사 경로를 만들지 않음.
- 일반 빌드와 Pages 아티팩트 업로드 전에 새 검사가 실행됨. 검증 job이 실패하면 기존 needs 관계로 배포 job 진행 불가함.
- main·fragments-draft 처리, 배포 트리거·권한·OAuth 입력·배포 아티팩트 경로는 변경하지 않음. 브랜치 보호·필수 상태 검사 설정도 이번에 변경하지 않음.

## 자동 검증과 남은 확인

- Red → Green: 실제 훅이 승인된 미등록 카테고리 커밋을 허용하던 실패, 공통 CI 명령 부재 실패, 두 훅의 실행 권한 누락 실패를 각각 확인 후 구현함.
- 신규 Git/CI 통합 22개 포함 전체 608개·32파일 통과함. 승인 누락/변경·삭제 참조 차단, 정상 커밋/push, 다른 HEAD/인덱스/작업 폴더, 다중 참조 입력, Git 링크/submodule, 한글·공백 경로, Fragment 중복 ID, 카테고리 제거, 정확한 예외, 미수집 글, 필수 설정 누락 검사함.
- 테스트의 승인·Git 객체·커밋·push는 합성 저장소와 그 안의 로컬 bare 원격에 한정함. 실제 Blog의 승인·참조를 시험용으로 변경하거나 외부 서비스에 시험 데이터를 전송하지 않음.
- 테스트 준비 중 기존 승인기가 최초 HEAD를 요구해 합성 빈 부모 객체를 준비함. 이는 기능의 Red로 세지 않음. Git이 커밋 훅 출력을 stderr로 전달하는 경우도 있어 출력 스트림 가정만 보완했으며 차단/허용 기대값은 유지함.
- 타입 검사 126파일 오류 0·경고 0·기존 힌트 5, 일반 Astro 빌드 11페이지·18이미지 성공함. 네 대상 실제 CLI/격리 빌드 회귀 통과함. 현재 콘텐츠 검사 오류 0·기존 Infra 예외 4·미사용 예외 0 확인함.
- 실제 현재 개발 브랜치 HEAD의 Git tree도 새 사본 검사기로 읽기 전용 검사해 오류 0 확인함. 작업 폴더·인덱스·실제 사용자 승인 자료 변경 없이 수행함.
- 화면·웹 저장기 코드를 바꾸지 않아 브라우저 E2E를 이번에 다시 실행하지 않음. 기존 CI의 브라우저 검사 단계는 유지함.
- ACTH01 통과 뒤 실제 commit/push에서 승인·콘텐츠 정책 훅 모두 성공함. 정확한 `8065fd6`의 [원격 Actions 실행](https://github.com/avocadosmasher/avocadosmasher.github.io/actions/runs/39275844500)도 두 작업 모두 성공함. 정책·타입·608개 단위/통합·두 격리 빌드·일반 Build·기존 브라우저 62개 통과 확인함. 운영 writer·실패 업로드·Pages 산출물 업로드는 조건에 따라 생략됐으며 운영 배포는 수행하지 않음.

## 보장 경계와 다음 작업

- 훅은 로컬 설정이 활성화된 일반 Git 경로의 검사임. 체크아웃된 검사 프로그램·훅의 고의 변조나 파일 쓰기 권한 자체를 차단하지 않음. CI는 커밋된 코드로 다시 검사하지만 필수 상태 검사·권한 통제는 별도 설정임.
- 출처·사실성·프로젝트의 의미 중복·사용자의 실제 대화 판정까지 인증하지 않음. 데이터 검사·Tool 계약·사람의 판정 역할을 구별함.
- 콘텐츠 Git 검사는 전체 TypeScript 타입·이미지 빌드·UI 판정을 대신하지 않음. 해당 자동 검사는 공통 CI와 기존 완료 절차에서 계속 필요함.
- ACTA01의 [자동화 운영 가이드](./AI-콘텐츠-자동화-운영가이드.md)와 [2차 최종 보고서](../AI-콘텐츠-자동화-2차-최종보고서.md)에 최종 사용 흐름·원격 증거·한계를 정리함. 최종 자료의 로컬 609개와 ACTH01 원격 608개의 차이는 예시 계약 호환성 검사 1개임.
