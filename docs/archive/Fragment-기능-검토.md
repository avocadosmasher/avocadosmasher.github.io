# Fragment 기능 구현 검토

검토일: 2026-09-11. 현재 프로젝트 소스와 공식 문서를 기준으로 작성한 구현 전 검토다. 사용자 선호는 웹에서 직접 작성·수정이며, 불가능할 경우 Markdown을 대안으로 사용한다. 아래 구조와 일정은 제안이며 확정 요구사항이 아니다.

## 판단

Astro + GitHub Pages를 유지하면서 카드, 카테고리, 검색, 그래프, 페이지네이션, 팝업을 모두 구현할 수 있다. 플랫폼 이전은 이 기능들의 필수 조건이 아니다.

GitHub Pages는 정적 파일을 제공한다. 브라우저 JavaScript로 검색·그래프·팝업을 구현할 수 있지만, Pages 자체가 방문자의 입력을 저장소에 기록하는 서버 역할을 하지는 않는다.

## 저장 방식 선택

| 방식 | 작성과 반영 | 장점 | 추가 고려사항 |
| --- | --- | --- | --- |
| Markdown + Git | 로컬 편집 → push → Actions 배포 | 기존 운영 흐름과 동일, 변경 이력과 백업 확보 | 사이트 반영은 배포 완료 후, 모바일 작성 편의 제한 |
| Git 기반 웹 편집기 | 로그인 → 웹 폼 편집 → 저장소 커밋 → 배포 | 브라우저로 작성하면서 Markdown 유지 | CMS 설정, GitHub 인증 연동 필요. 예: Decap CMS의 GitHub backend는 인증용 서버 필요 |
| 외부 DB/API | 로그인 → API 저장 → 브라우저가 최신 데이터 조회 | 여러 기기에서 즉시 작성·조회 | 작성자 권한, DB 정책, 서비스 운영 추가. Pages 프런트엔드는 유지 가능 |
| 브라우저 로컬 저장 | 현재 브라우저에 저장 | 서버 없이 빠른 입력 | 기기 간 동기화가 없고 데이터 삭제에 취약. 주 저장소보다 임시 메모와 내보내기에 적합 |

우선 제안은 Git 기반 웹 편집기다. 사용자는 웹 폼으로 작성하고 실제 데이터는 Markdown으로 저장하므로 로컬 편집도 병행할 수 있다. 공개 조회를 기본 가정으로 검토했으며, 비공개 학습 노트가 필요하면 저장·인증 설계를 별도로 해야 한다. 공개 정적 JSON에 담긴 데이터는 화면에서 숨겨도 비공개가 아니다.

### 웹 작성 우선안

블로그에 `/admin/` 관리 화면을 추가하고 Decap CMS의 GitHub backend를 연결하는 방안을 우선 검증한다. 작성자는 GitHub 로그인 후 용어·설명·카테고리·관계를 폼으로 입력하며, 저장은 현재 저장소의 Markdown 커밋으로 이어진다. `main` 반영 후 기존 Actions가 사이트를 다시 배포한다. 관계 대상은 CMS의 relation 위젯으로 기존 카드를 검색해 선택하도록 구성한다.

이 방식에는 GitHub OAuth 앱 설정과 외부 인증 서비스가 필요하다. 인증 비밀값은 해당 서비스에 보관하고 정적 사이트에 넣지 않는다. 저장소 쓰기 권한이 있는 계정으로 작성하며, 일반 방문자는 조회한다. 관리 화면은 같은 사이트에 두되 편집 UI는 CMS 전용 화면이다. 공개 카드 팝업 안에서 바로 입력·수정하는 완전 맞춤 편집 UI는 별도 개발 범위다.

‘저장 완료’와 ‘공개 사이트 반영 완료’는 다르다. 작성 화면은 저장소 내용을 읽지만 공개 페이지는 마지막 성공 빌드 결과다. 빌드 실패 시 이전 사이트가 유지되며 Actions에서 실패 원인을 확인하는 흐름을 운영 가이드에 포함한다. 여러 기기의 편집 충돌과 ID 변경에 따른 관계 훼손도 검증한다.

실제 연결 전 작은 샘플로 GitHub 로그인 → 카드 생성 → 커밋 → Actions 실행 → 공개 페이지 반영 → 다른 기기 수정 흐름을 검증한다. 인증 서비스 제공자와 OAuth 앱 설정은 구현 준비 후 선택·연결할 외부 구성이다. 서비스 선택 전에는 호스팅 요금이나 무상 운영을 확정하지 않는다.

## 화면과 기능

- 상단 메뉴에 `Fragments` 추가, `/fragments/`로 이동한다. 명칭은 변경 가능하다.
- 화면 위쪽에 검색창·카테고리 필터·카드/그래프 보기 전환을 둔다.
- 카드에는 용어, 별칭, 핵심 설명, 카테고리, 태그를 표시한다. 상세 메모와 관계는 팝업에서 본다.
- 기본 검색은 용어·별칭·설명·태그·카테고리 대상으로 한다. 영문 대소문자와 유니코드를 정규화하며, 용어/별칭 완전 일치 결과를 우선한다. 본문 검색과 오타 허용은 추가 범위로 둔다.
- 카테고리는 카드 데이터에서 집계해 블로그의 고정 카테고리와 분리한다. 주 카테고리 하나와 태그 여러 개로 시작한다.
- 검색과 카테고리는 AND 조건으로 결합하고, 필터 결과에 페이지네이션을 적용한다. 초기 제안은 페이지당 12개다.
- `?q=...&category=...&page=2&card=ept` 형태로 조회 상태를 보존한다. 필터 변경 시 1페이지로 돌아가며 새로고침·뒤로가기·팝업 직접 링크를 지원한다.
- 팝업은 `<dialog>`를 활용하고 배경을 어둡게 처리한다. 닫기 버튼, Escape, 포커스 복원, 모바일 스크롤을 확인한다.

## 데이터 모델

블로그와 별도의 `fragments` 컬렉션을 만든다. 하나의 파일은 나중에 따로 찾고 연결할 수 있는 하나의 개념 단위를 담는다. 같은 용어의 추가 파편은 제목으로 구분할 수 있으며, 제목 중복 자체를 오류로 취급하지 않는다.

```yaml
---
id: ept
title: EPT
aliases: [Extended Page Tables]
summary: 게스트 물리 주소를 호스트 물리 주소로 변환하는 데 사용하는 하드웨어 지원 페이지 테이블.
category: Infra
tags: [가상화, 메모리]
relations:
  - target: gpa
    type: related
  - target: shadow-page-table
    type: contrasts
---
필요할 때만 짧은 보충 설명, 예시, 출처 링크를 작성한다.
```

필수 필드는 `id`, `title`, `summary`, `category`로 최소화한다. 별칭·태그·관계·본문은 선택이다. 파일명과 제목을 바꾸어도 관계가 유지되도록 명시적 ID를 사용하며, ID는 고유하고 안정적으로 유지한다.

관계 예시는 연결 대상 카드가 실제로 존재할 때만 사용한다. 중복 ID, 없는 대상, 자기 자신을 가리키는 관계를 검사한다. 관계 유형은 `related`(관련), `prerequisite`(선행 개념), `part-of`(상위 개념), `contrasts`(비교) 정도로 제한한다. 방향은 ‘현재 카드 → 대상’으로 정의하고, 선행/상위 개념은 대상이 선행/상위임을 명시한다. 대칭 관계는 그래프에서 중복 간선을 제거한다.

## 그래프

카드가 노드이고 명시적으로 작성한 관계가 간선이다. 자동 배치는 라이브러리가 수행하지만 의미 관계는 작성자가 정한다. AI 관계 추론은 이번 견적에 포함하지 않는다.

Cytoscape.js를 후보로 검토한다. 확대·축소·이동, 노드 클릭 이벤트, 레이아웃을 제공하므로 별도의 그래프 DB 없이 브라우저에서 구현할 수 있다. 그래프 보기 진입 시에만 라이브러리를 불러온다.

처음에는 선택 카드와 직접 연결된 이웃을 보여주는 방식으로 시작한다. 전체 그래프는 별도 전환으로 제공한다. 카드 목록의 현재 페이지가 그래프의 연결 범위를 제한해서는 안 된다. 검색 결과를 중심으로 이웃까지 표시할 경우 필터 밖 이웃은 구분해서 표시한다. 노드 클릭은 동일한 카드 팝업으로 이어지고, 팝업의 관련 개념 목록도 제공해 그래프 없이 탐색할 수 있게 한다.

## 변경 위치

| 위치 | 제안 변경 |
| --- | --- |
| `src/consts.ts` | NAV에 Fragments 메뉴 추가 |
| `src/content.config.ts` | fragments 로더와 스키마 추가 |
| `src/content/fragments/*.md` | 새 카드 콘텐츠와 작성 예시 |
| `src/pages/fragments/index.astro` | 검색·필터·카드 목록·페이지네이션 |
| `src/components/fragments/` | 카드, 팝업, 그래프 컴포넌트 |
| `src/scripts/fragments.ts` | 검색·URL·페이지·팝업 상태 관리 |
| `src/utils/fragments.ts` | 데이터 정규화, 관계 검증, 검색 보조 함수 |
| `src/styles/fragments.css` | 기존 색상 토큰을 사용하는 기능 전용 스타일 |
| `public/admin/index.html`, `public/admin/config.yml` | 웹 편집기와 Fragment 입력 폼 설정 |
| 외부 인증 서비스 | GitHub OAuth 콜백과 인증 비밀값 관리 |

기존 BaseLayout, 테마, 내부 링크용 href()를 재사용한다. 기존 PostCard는 블로그 글 메타데이터와 페이지 이동에 맞춰져 있어 새 카드 컴포넌트를 만든다. 기존 목록 스크립트의 필터 방식은 참고하되 URL 동기화를 포함해 새 상태 로직을 작성한다.

전역 검색(Ctrl/Cmd+K)에 Fragment를 섞는 것은 필수 기능으로 가정하지 않는다. 첫 버전은 Fragment 전용 검색을 제공하고, 통합 검색을 원하면 결과 유형과 링크 처리까지 추가한다.

## 규모와 검증

첫 버전은 짧은 카드 수백 개를 목표로 메타데이터를 한 번 읽고 클라이언트에서 검색·페이징한다. 표시할 카드만 DOM에 구성하고, 긴 상세 본문이 늘면 ID별 정적 데이터 파일을 팝업을 열 때 읽도록 분리한다. 클라이언트 페이지네이션은 초기 데이터 다운로드 자체를 줄이지 않는다.

성능은 카드 수만으로 단정하지 않고 실제 본문 크기와 그래프 간선 수를 포함해 확인한다. 0·1·12·13개 결과, 한글/영문 별칭, 결과 없음, URL 복원, 잘못된 페이지와 카드 ID, 팝업 키보드 이동, 모바일·다크 모드, 끊어진 관계를 검증한다. 수백 카드와 관계가 밀집한 샘플에서 검색 응답과 그래프 조작도 확인한다.

개발 중 `npm run dev`로 확인하고, 배포 전에는 `npm run build`와 생성 결과를 확인한다. 현재 사전 조사에서는 개발 서버 및 기존 공개 페이지 응답까지 확인했으며 프로덕션 빌드는 검증하지 못했다.

## 대략적인 작업 견적

아래는 기존 디자인 재사용, Markdown 저장, 공개 조회, 짧은 텍스트 카드, 개발자 1명 기준의 설계·구현·검증 포함 추정치다. 확정 납기나 비용 견적은 아니며 콘텐츠 작성과 배포 승인 대기는 제외한다.

| 단계 | 범위 | 예상 작업 시간 |
| --- | --- | --- |
| 1 | 데이터 스키마·작성 템플릿·탭·카드·카테고리·검색 | 8–14시간 |
| 2 | 팝업·페이지네이션·URL 복원·모바일/키보드 검증 | 6–10시간 |
| 3 | 명시적 관계·그래프·카드 연결·지연 로딩·성능 검증 | 10–18시간 |
| 합계 | 요청한 여섯 기능, Markdown 저장 기준 | 24–42시간 |

선택 추가: Git 기반 웹 CMS는 인증·배포 환경에 따라 8–20시간, 별도 DB 기반 작성/수정/삭제 및 로그인은 24–48시간을 추가 추정한다. 둘은 대안이며 합산하는 항목이 아니다. 외부 서비스 요금은 제공자와 운영 규모가 정해진 뒤 산정한다.

사용자 선호를 반영한 첫 배포 범위는 1+2단계와 웹 CMS(22–44시간)를 권장한다. 그래프까지 포함하면 총 32–62시간 추정이다. CMS 표준 관리 화면을 사용하는 기준이며, 공개 화면과 동일한 디자인의 맞춤 편집기 비용은 포함하지 않는다. 관계 필드는 처음부터 포함해 두고 실제 카드가 쌓인 후 3단계를 적용하면 그래프의 관계 유형과 표시 방식을 실제 사용에 맞출 수 있다.
