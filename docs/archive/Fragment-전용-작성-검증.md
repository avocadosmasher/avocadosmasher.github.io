## G05/G06-UI 재로그인·초안 복구 — 이번 수동 테스트 (2026-09-17)

**테스트 대상:** 저장·삭제 중 로그인이 만료되거나 권한이 확인되지 않을 때, 실패 안내 영역 안에서 바로 **다시 로그인**하고 입력한 초안 그대로 같은 작업을 마무리하는 흐름. 실패 안내가 어떤 버튼을 다시 눌러야 하는지 이름으로 알려준다.

**준비:** https://fragment-cms-test.pages.dev/fragments/ 에 접속해 새로고침한다. 최신 테스트 배포는 `08a46335`이다. 기존 GitHub 작성자 계정과 테스트 저장소 `avocadosmasher/fragment-cms-auth-test` / `cms-test`를 사용한다. 휴대폰 폭(390px)이나 브라우저 창을 좁혀 확인하면 안내 위치를 함께 볼 수 있다. 에이전트가 최신 원격 카드로 빌드·배포했다.

**테스트 방법 / 예상 결과:**

1. **기본 확인:** 로그인 → 새 카드 입력 → **로그아웃**. 저장 버튼이 비활성으로 바뀌고 입력은 그대로 남아야 한다. 다시 로그인하면 저장 버튼이 다시 활성화된다.
2. **만료 재현:** 로그인한 뒤 카드 내용을 입력하고, 다른 탭의 GitHub에서 이 OAuth 앱의 권한을 취소(Settings → Applications → Authorized OAuth Apps → Revoke)한 다음 **카드 저장**을 누른다. 실패 안내에 `로그인이 만료되었습니다`와 **다시 눌러야 할 버튼 이름**(‘같은 내용으로 다시 저장’ 등)이 보이고, 안내 안에 **다시 로그인** 버튼이 있어야 한다. 입력한 용어·요약·카테고리·관계는 그대로 남아야 한다.
3. **안내 안의 다시 로그인**을 누른다. GitHub 로그인 팝업이 뜨고, 승인하면 안내가 `다시 로그인했습니다. 입력은 그대로 유지했습니다. ‘…’을 다시 눌러 마무리해주세요.`로 바뀌며 **다시 로그인** 버튼은 사라지고 포커스가 저장 버튼으로 이동해야 한다.
4. 이어서 저장 버튼을 누르면 같은 내용이 한 번만 저장되고, 목록·상세와 GitHub 결과 링크에 반영되어야 한다. 카드가 중복 생성되면 안 된다.
5. **삭제도 같은 방식:** 기존 카드 수정 화면에서 같은 만료 상태를 만든 뒤 **카드 삭제 → 확인**을 누른다. 안내에 만료 사유와 ‘카드 삭제’ 이름, **다시 로그인** 버튼이 보이고 카드는 목록에 남아 있어야 한다. 다시 로그인하면 포커스가 삭제 버튼으로 이동하고, 삭제를 다시 누르면 성공해야 한다.
6. **로그인 취소:** 3번이나 5번에서 팝업을 그냥 닫는다. 안내가 `다시 로그인하지 못했습니다`와 취소 사유를 보여주고 **다시 로그인** 버튼이 남아 있어야 하며, 입력과 목록은 그대로여야 한다.
7. 관계 중복·삭제 차단·요청 한도 등 로그인과 무관한 실패에는 **다시 로그인** 버튼이 나오지 않고 기존 안내만 보여야 한다(예: 관계가 있는 카드 삭제 시 참조 카드 안내).

**자동 검사 결과:** 신규 단위 5개(실패 분류·재로그인 안내)와 신규 브라우저 2개(저장·삭제 만료 후 재로그인·재시도) 통과. Vitest 12파일/64개 통과, OAuth 브라우저 34개 통과, 일반 브라우저 8개 통과, `astro check` 오류·경고 0(기존 hint 4개), 일반·테스트 빌드 각 12페이지 성공, 배포 후 고정 주소 HTTP 200 확인. **미확인:** `tests/integration/oauth-runtime.test.ts` 3개는 이 PC에 `node_modules/workerd` 바이너리가 없어 `spawn UNKNOWN`으로 실행하지 못했다(`npm install` 후에도 복구되지 않음). 이번 변경은 Worker 코드를 건드리지 않았다. 실제 GitHub 계정의 만료·재로그인은 자동 검사 대상이 아니며 전체 preview E2E와 운영 배포도 미실행이다.

## 관계·삭제 피드백 수정 — 이전 수동 테스트 (2026-09-17, 사용자 통과·90617a1)

**테스트 방법 / 예상 결과:**

1. A 수정에서 B를 선택해 관계를 추가한다. B 옵션이 `이미 연결됨`으로 비활성화되고 관계 유형을 바꾸어도 B를 또 추가할 수 없어야 한다. **수정 저장** 후 다시 열면 관계 하나가 유지되어야 한다.
2. B를 수정한다. 반대 방향의 대상 A도 `이미 연결됨`으로 선택할 수 없어야 한다. 다른 카드와의 관계 추가는 가능하다. 카드당 관계 하나 제한이 아니다.
3. B의 **카드 삭제 → 확인**을 누른다. 버튼 근처의 테두리 있는 안내에 참조 카드 A와 **해당 카드 수정 → 관계 제거 → 수정 저장 → 삭제 재시도** 순서가 보여야 한다. 안내로 포커스가 이동하며 작은 화면에서도 보여야 하고 B는 유지되어야 한다.
4. A에서 B 관계를 **제거 → 수정 저장**한다. 다시 열었을 때 관계가 없어야 한다. B를 삭제하면 이번에는 성공하고 목록에서도 사라져야 한다. 새로고침/새 탭에서 최신 조회가 성공한 뒤 같은 결과와 GitHub 결과 링크를 확인한다.
5. 이전에 제거가 실패했던 카드도 같은 순서로 확인한다. 실패하면 화면에 나온 안내와 재현 순서를 전달한다. 조회 실패·요청 한도는 입력을 유지하고, 조회 실패는 쓰기 요청 전 중단했음을 안내한다. 실제 저장 응답 유실은 같은 내용으로 재시도해 확인한다.

## G04-UI + G08-UI — 이전 수동 테스트 (수정 전 기록)

**준비:** 실행 명령 없이 https://fragment-cms-test.pages.dev/fragments/ 에 접속해 새로고침한다. 최신 테스트 배포는 `16a3fff0`이다. 기존 GitHub 작성자 계정으로 로그인하고 **관계검증 A**, **관계검증 B**라는 새 카드 두 개를 각각 저장한다. 필수 요약과 카테고리를 채우고 최초 관계는 비워둔다. 대상 저장소/브랜치는 `avocadosmasher/fragment-cms-auth-test` / `cms-test`다. 기존 카드를 테스트용으로 삭제할 필요는 없다.

**테스트 방법 / 예상 결과:**

1. A의 **카드 수정**에서 **연결된 개념**까지 내려간다. **관계 카드 검색**에 B의 이름을 입력하고 **관계 대상**에서 B, **관계 유형**에서 **관련 개념**을 선택해 **관계 추가**를 누른다. `관련 개념 · 관계검증 B`가 목록에 표시되어야 한다. 같은 관계를 다시 추가하면 중복 안내가 나오고 한 개만 남아야 한다. A 자신은 대상으로 나오지 않아야 한다.

3. A 창을 닫고 B의 **카드 수정 → 카드 삭제 → 확인**을 누른다. A가 참조하고 있어 삭제할 수 없다는 안내가 나오고 B가 유지되어야 한다. 삭제 완료 안내가 나오면 실패다.
4. B 창을 닫고 A를 수정한다. B 관계 옆의 **제거 → 수정 저장**을 누른다. 제거 버튼만 누르는 것은 저장이 아니므로 반드시 저장한다. 다시 A를 열었을 때 연결이 없어야 한다.
5. B의 **카드 수정 → 카드 삭제 → 확인**을 다시 실행한다. 이번에는 성공하고 목록·검색·그래프에서 B가 사라져야 한다. 새로고침 후에도 같아야 한다. 결과 GitHub 링크에서 B 파일 하나만 삭제됐는지 확인한다. 원하면 검증용 A도 삭제해 정리한다.

3. 다시 **카드 삭제 → 확인**을 누른다. 처리 중에는 버튼과 닫기가 비활성화되고, 성공하면 창이 닫히며 삭제 완료 안내가 나타나야 한다. 해당 카드는 목록·검색·그래프에서 빠지고 새 탭이나 새로고침에서도 나타나지 않아야 한다.
4. 결과 GitHub 링크를 연다. `cms-test`에서 검증용 카드 파일 한 개만 삭제됐는지 확인한다. 가능하면 이 커밋 링크를 판정과 함께 남긴다.
5. 다른 카드가 참조하는 기존 카드를 열어 삭제를 시도한다. 예를 들어 EPT의 관계가 GPA를 가리킨다면 GPA는 삭제가 차단되고 참조 카드 제목이 표시되어야 한다. 입력과 카드가 유지되어야 한다. 참조를 확인한 카드에만 이 차단 테스트를 수행한다.
6. 선택 사항: 수정 창을 연 상태로 개발자 도구 Network에서 Offline을 켜고 삭제를 확인한다. 실패 안내와 입력·목록이 유지되어야 한다. Online으로 복구한 뒤 다시 삭제하면 최신 상태를 확인해야 한다. 충돌·응답 유실·권한 거부는 자동 테스트에서도 검증했다.

**자동 검사 결과:** Vitest 47개, OAuth/작성/수정/삭제/그래프 Playwright 25개, 일반 Playwright 8개 통과. 타입 검사 오류 0·경고 0(기존 hint 4개). 일반·테스트 빌드 각 12페이지 성공. 배포 주소 HTTP 200, 최신 카드 7개, 390px 가로 넘침·페이지 오류 없음, 로그인 전 삭제 숨김 확인. 자동 쓰기는 mock이며 실제 계정 삭제·커밋 확인과 전체 preview E2E는 미검증이다.

**문서 확인:** 이 절의 삭제 차단 정책·재시도 안내가 실제 동작과 맞는지 확인한다. `../plan/Fragment-TDD-개발계획.md`의 G08-UI는 수동 판정 대기이며, 최신 작업 로그 항목(`../log/`)에는 위 자동 검사와 실제 계정 미검증 범위가 구분되어 있어야 한다.

**판정 요청:** 직접 확인 후 ‘통과’ 또는 ‘수정: [문제와 재현 방법]’으로 알려주세요.

### 삭제 실패와 복구

- 다른 카드가 참조하면 먼저 참조하는 카드의 수정 창에서 해당 관계를 **제거 → 수정 저장**한 뒤 삭제를 다시 시도한다. GitHub Markdown의 `relations`를 직접 수정하는 방법도 가능하다. 관계를 자동 제거하거나 다른 카드 파일을 함께 삭제하지 않는다.
- 수정 창을 연 뒤 파일 내용이 바뀌면 삭제하지 않는다. 필요한 입력을 복사한 뒤 새로고침하고 최신 내용을 검토한다. 관계 검사 중 저장소가 바뀌면 중단하며, 재시도할 때 전체 관계를 다시 확인한다.
- 응답을 받지 못한 경우 삭제 성공으로 표시하지 않는다. **카드 삭제**를 다시 누르면 전체 최신 목록을 확인한다. 이미 삭제된 경우 추가 쓰기 없이 그 사실을 안내한다. 권한 만료 시 다시 로그인한다.
- 삭제 복구가 필요하면 결과 커밋의 부모 버전에서 파일 원문을 가져와 같은 파일명·ID로 복원한다. 관계도 확인한 뒤 저장한다. 사이트에는 최신 조회 이후 반영된다.

### G03-LIVE — 목록·상세 최신 내용 반영 (이번 판정 대상)

**준비:** 별도 실행 명령 없이 https://fragment-cms-test.pages.dev/fragments/ 에 접속한다. 보기에는 로그인이 필요 없고 저장할 때 기존 쓰기 권한 계정으로 로그인한다. 수정 기능의 이전 통과 판정은 `847260e`로 커밋·push 완료했으며, 이번 목록 반영은 새 판정 대상이다.

1. 페이지를 새로고침하고 `최신 카드를 불러왔습니다.`를 확인한다. 이전에 수정한 용어·요약이 로그인하지 않은 목록과 상세에도 보여야 한다.
2. 기존 카드의 수정 화면에서 용어·요약·보충 설명을 바꾸고 저장한다. 창이 닫히면 현재 목록에 변경 내용이 바로 보이고 상세에도 같은 내용이 나타나야 한다. 변경한 용어로 검색해도 찾을 수 있어야 한다. 기존 검색/필터와 맞지 않게 변경하면 해당 조건의 목록에서는 빠지는 것이 정상이다.
3. 새로고침하거나 새 탭에서 열어 `최신 카드를 불러왔습니다.`를 확인한다. 로그인 없이도 같은 수정 내용이 유지되어야 한다. 카테고리 집계와 그래프의 이름도 최신 데이터에 맞아야 한다.
4. 새 카드 한 개를 저장한다. 목록에 한 번만 추가되고 새로고침 후에도 유지되어야 한다. 공개 목록에서 새 카드의 상세·수정 화면으로 진입할 수 있어야 한다.

**자동 검사:** Vitest 40개, 일반 Playwright 8개, OAuth/저장/동기화 Playwright 총 16개 시나리오 통과(전체 15개 실행 후 추가 동기화 테스트를 포함한 3개 재검증). 타입 검사 오류·경고 0(기존 hint 4개), 일반·테스트 빌드 각 12페이지 성공. 실제 배포에서 로그인 없는 GitHub 최신 목록 조회·7개 카드·모바일 수정 진입을 확인했다. 쓰기 자동 테스트는 모의 API이며 실제 계정 저장 후 화면 반영은 사용자 확인 대상이다. 전체 preview E2E는 이번에 재실행하지 않았다.

직접 확인 후 ‘통과’ 또는 ‘수정: [문제와 재현 방법]’으로 알려주세요.

### G03-UI — 기존 카드 수정 (이전 통과 기능의 회귀 확인)

**준비:** 별도 실행 명령 없이 https://fragment-cms-test.pages.dev/fragments/ 에 접속한다. 테스트 저장소의 `cms-test` 브랜치에 쓰기 권한이 있는 기존 GitHub 계정을 사용한다. 2026-09-16 테스트 빌드는 저장소의 기존 카드 7개를 읽어 표시한다. 로컬 공개 카드 원본이나 원격 카드 파일을 준비 과정에서 수정하지 않았다.

1. 목록에서 `따끈따끈` 등 기존 카드를 연 뒤 **로그인하고 수정**을 누른다. **카드 수정** 창이 열리고 로그인 전에는 저장이 비활성화되어야 한다.
2. **GitHub 로그인**을 누른다. 로그인·쓰기 권한 확인 후 용어·요약·카테고리·별칭·태그·보충 설명이 GitHub 최신 내용으로 채워져야 한다. 이미 로그인했다면 **카드 수정**을 눌렀을 때 바로 읽는다. 공통 목록에 없는 원래 카테고리는 `(기존 카테고리)` 옵션으로 유지한다.
3. 용어와 요약에 `수정 확인`을 덧붙이고 Escape로 닫는다. 다시 **카드 수정**을 누르면 입력이 유지되어야 한다. 새 카드 초안과 기존 카드별 수정 초안은 각각 유지된다.
4. **수정 저장**을 누른다. 작성·상세 창이 닫히고 목록 위에 완료 안내와 GitHub 링크가 나타나야 한다. 링크에서 기존 파일 한 개가 수정됐고, 파일명과 `id`, 기존 `relations`가 유지됐는지 확인한다. 이름만 다른 새 파일이 추가되면 실패다.
5. 새 탭에서 같은 사이트와 원래 카드를 열고 로그인 후 수정 화면으로 들어간다. 3번에서 저장한 용어·요약이 나타나야 한다. 목록·상세도 최신 카드 조회 성공 후 같은 내용을 표시한다.

이전 G03-UI 자동 검사와 수동 통과 증거는 개발 기록을 참조한다. 가능하면 수정 결과 커밋 링크도 함께 전달한다.

### 새 카드 생성 — 기존 회귀 확인 방법

카테고리 화살표는 오른쪽 테두리에서 여유를 두고 표시된다. 화살표 부분을 눌러도 목록이 열리며, 모바일에서도 선택한 글자와 겹치지 않아야 한다.

1. 위 주소에서 **새 카드**를 누른다. 블로그 스타일의 작성 폼과 위 테스트 저장 대상이 보여야 한다.
2. **GitHub 로그인**을 누른다. 테스트 저장소에 쓰기 권한이 있는 계정으로 승인하면 팝업이 닫히고 저장 버튼이 활성화되어야 한다. 취소하거나 창을 닫으면 안내 후 다시 로그인할 수 있고 기존 입력은 유지되어야 한다.
3. 용어 `전용 폼 저장 테스트`, 요약 `블로그에서 작성한 카드`를 입력한다. 카테고리 선택창을 열면 블로그 사이드바와 동일한 `AI`, `Frontend`, `Backend`, `DevOps`, `Database`, `회고/생각`이 같은 순서로 보여야 한다. `DevOps`를 선택한다. 카테고리를 선택하지 않으면 저장 제출이 차단되어야 한다. 별칭·태그·보충 설명은 비워도 된다.
4. 저장 전에 작성 창 바깥의 어두운 영역을 누른다. 창이 닫히고 **새 카드** 버튼으로 포커스가 돌아와야 한다. 다시 열면 입력과 기존 검색 조건이 유지되어야 한다. 입력란 안을 클릭하면 닫히지 않아야 한다.
5. **카드 저장**을 누른다. 성공하면 창이 자동으로 닫히고 목록 위에 저장한 용어와 완료 안내, **GitHub에서 저장 결과 확인** 링크가 표시되어야 한다. 링크는 선택적인 검증 수단이며 누르지 않아도 저장은 완료된다. 테스트 저장소의 생성 커밋과 Markdown 내용을 확인할 수 있다.
6. **새 카드**를 다시 누르면 빈 입력과 `카테고리를 선택해주세요`로 시작하고 로그인은 유지되어야 한다. 로그아웃하면 저장이 비활성화된다. 저장 중에는 닫기 버튼·바깥 클릭·Escape로 창을 닫을 수 없으며, 실패하면 입력과 재시도 버튼이 유지되어야 한다. 재시도하는 동안 카테고리 선택값은 변경할 수 없으며 같은 값으로 저장된다.

저장 확인 후 현재 목록·상세에 즉시 반영한다. 새로고침/새 탭은 로그인 없이 공개 테스트 저장소의 최신 내용을 읽는다. 빌드 시점의 데이터는 조회 실패 시 대체 목록으로 사용하며 이전 내용일 수 있다는 안내와 다시 불러오기 버튼을 표시한다. 운영 사이트의 자동 빌드·배포 연결은 별도 인수다.

검증 후 `통과` 또는 `수정: [문제와 재현 방법]`과 생성 커밋 링크를 전달한다. 토큰이나 Client Secret을 공유하지 않는다.

## 오류 처리와 현재 제약

- 최신 조회는 테스트 환경에서 공개 GitHub tree와 blob을 읽는다. 네트워크 오류·요청 제한·잘못된 관계·중복 ID·불완전한 목록이면 부분 결과로 교체하지 않고 기존 목록과 재시도를 유지한다. 전체 데이터가 정상이면 0개 카드도 반영한다.
- 다른 탭에서 변경한 내용을 자동으로 반복 조회하지는 않는다. 새로고침으로 최신 내용을 가져온다. 읽기는 로그인 없이 가능하지만 저장은 기존 로그인·쓰기 권한 검사를 거친다.
- 삭제는 위 G08-UI 수동 판정 대기다. 참조하는 카드가 있으면 삭제를 차단하고, 실패 시 입력·목록을 유지한다.

- 작성 카테고리는 블로그 사이드바와 동일한 `src/consts.ts`의 `CATEGORIES`에서 읽는다. 설정 변경 후 빌드하면 두 화면에 함께 반영된다. 작성 폼에서는 목록 중 하나를 선택한다. 기존 Fragment의 카테고리와 목록 필터는 보존한다.

- 로그인 정보는 현재 페이지의 메모리에만 둔다. localStorage/sessionStorage에 토큰을 기록하지 않는다. 로그아웃은 이 페이지의 토큰을 지우며 GitHub 계정의 OAuth 승인 자체를 취소하는 기능은 아니다.
- 브라우저의 GitHub 로그인과 기존 앱 승인이 유지되면 로그인 버튼을 눌렀을 때 빠르게 인증될 수 있다. 테스트용 로그인 생략은 아니다.
- 새로고침·페이지 이탈 시 입력도 사라진다. 영구 초안 저장은 이번 범위가 아니다.
- 저장 요청 이후에는 ID와 입력을 고정한다. 통신 실패로 결과가 불확실할 때 **같은 내용으로 다시 저장**을 누르면 같은 경로를 먼저 읽고 내용이 일치하는지 확인한다. 이미 저장됐으면 추가 커밋을 만들지 않는다.
- 새 파일 생성 요청에는 덮어쓰기 SHA를 보내지 않는다. 기존 카드 수정은 읽어 온 SHA로 같은 파일을 갱신한다. 다른 세션에서 먼저 수정했으면 덮어쓰지 않고 입력을 보존한다. 필요한 입력을 복사한 뒤 새로고침하고 최신 원문을 다시 불러온다. 충돌 병합 UI는 후속 작업이다.
- 원문 ID가 선택한 카드와 다르거나 지원하지 않는 메타데이터가 있으면 필드를 버리지 않고 수정을 중단한다. 현재 파일 경로는 `src/content/fragments/` 아래 영문·숫자·하이픈·밑줄 이름의 `.md` 파일(하위 폴더 포함)을 지원한다.
- 권한 거부·토큰 만료 시 입력을 유지하고 로그인을 다시 제공한다. 권한·브랜치 보호·API 제한 때문에 실제 저장이 거부될 수 있으며, 오류를 성공으로 표시하지 않는다.
- 로그인 서버는 `https://fragment-cms-test.pages.dev`만 허용한다. 로컬 주소나 배포별 임시 URL에서는 실제 인증을 인수하지 않는다. Worker의 origin을 넓히거나 비밀값을 변경하지 않았다.

## 재현 가능한 테스트 빌드

```powershell
node scripts/build-writer-test.mjs
# 실제 테스트 저장소의 기존 카드를 읽어 수정 인수용 빌드
node scripts/build-writer-test.mjs --remote
```

`.fragment-test/writer-site`에 공개 테스트 대상이 고정된 산출물을 만든다. 자동 배포하지 않는다. 기본 모드는 로컬 공개 콘텐츠를 읽는다. `--remote`는 테스트 브랜치의 커밋 하나를 고정하고 카드들을 `.fragment-test/writer-snapshot-*/src/content/fragments`에 내려받아 빌드한다. 읽기 실패 시 빌드를 중단하며 테스트 저장소에는 쓰지 않는다. `_headers`에 검색엔진 제외 지시를 포함한다.

```powershell
npx wrangler pages deploy .fragment-test/writer-site --project-name fragment-cms-test --branch main --commit-dirty=true
```

위 명령의 `main`은 별도 Cloudflare 테스트 프로젝트의 배포 슬롯이다. 블로그 Git 저장소의 `main`에 커밋·push하는 명령이 아니며, 카드의 GitHub 저장 브랜치는 여전히 `cms-test`다. 배포는 해당 테스트 사이트 갱신이 작업 범위에 포함될 때만 수행한다.
