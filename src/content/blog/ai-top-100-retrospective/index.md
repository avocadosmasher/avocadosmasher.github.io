요즘은 AI를 활용해 문제를 풀어보는 대회 소식도 제법 눈에 들어옵니다. 앞으로는 AI를 활용하는 능력이 더 중요해지고, 그 능력을 확인하는 시험이나 대회도 많아지지 않을까 싶습니다.

저도 이런 흐름을 직접 경험하면서 제 AI 활용 능력을 시험해 보고 싶었습니다. 그래서 카카오임팩트에서 진행한 AI_TOP_100에 참가했고, 얼마 전인 2026년 10월 31일에 예선전을 치렀습니다.

처음 겪어 보는 형식의 대회였고, 대회 측에서 요구한 사전 준비 사항도 있었습니다. 나름대로 준비해 보니 생각보다 손이 많이 가더군요.

대회에서 요구한 준비에 더해, 여러 코딩 AI가 작업을 나눠 맡고 수집한 정보를 다시 꺼내 쓸 수 있는 환경도 제가 별도로 구성했습니다. 대회에서 사용해 보니 인물관계와 새로 발견한 내용을 정리하는 구조는 잘 준비했다는 생각이 들었습니다. 다만 다음 질문을 고르는 전략에는 아쉬움이 남았습니다.

예선 제출을 마친 지금, 그 환경을 어떻게 준비했고 대회에서 어떻게 활용했는지, 무엇이 부족했으며 다음에는 어떤 방식으로 바꿔 보고 싶은지 돌아보려고 합니다.

> **공개 범위 안내**
>
> 대회 규정에 따라 제공된 문제·데이터·지시사항은 종료 후에도 공개할 수 없습니다. 이 글은 구체적인 문제와 제공 자료·인터뷰 기록·풀이를 생략하고, 개인의 준비·협업 방식과 개선점을 중심으로 정리했습니다.

## 1. 대회 방식과 사전 준비의 범위

예선은 다섯 시간 동안 진행됐습니다. 공식 소개에 따르면 참가자는 가상의 인물들과 인터뷰하면서 정보를 얻고, 그에 맞는 AI 에이전트를 제작합니다. 개인전이며 활용할 AI 도구는 자유롭게 선택할 수 있었습니다. [대회 소개와 FAQ](https://aitop100.org/)

> **용어 참고 · 코딩 AI와 제출 에이전트**
>
> 코딩 AI는 구현·자료 정리·검증에 사용한 도구입니다. 제출 에이전트는 대회 과제를 수행하도록 만든 결과물입니다.

문제에 맞춘 기능은 당일 인터뷰로 정보를 얻으면서 구현해야 했습니다. 사전에는 그 작업을 시작할 수 있도록 메시지 연결과 모델의 도구 호출 흐름, 서버 배포·상태 확인, 여러 코딩 AI의 협업 환경을 준비했습니다. 도구 호출의 뼈대도 미리 만들어 동작을 확인해 두었습니다.

## 2. 협업 환경의 전체 구성과 역할 분담

여러 코딩 AI를 함께 쓰려면 각 AI가 어떤 역할을 맡을지 정해야 했습니다. 작업을 전달하고 기록하는 방법과 각자의 결과를 합치는 절차도 필요했습니다. 이 역할과 도구를 한곳에 모으면 다음과 같습니다.

| 구분 | 구성 요소 | 맡긴 역할 |
| --- | --- | --- |
| 지휘·통합 | Claude Code | 요구사항 정리, 작업 배분·결과 확인·병합·배포 |
| 구현 | Codex | 기능 코드·외부 연동 구현과 테스트 |
| 검증 | Antigravity CLI | 문서 검토, 평가 사례 작성·실행과 누락 점검 |
| 작업 전달 | Herdr | 코딩 AI 실행·상태 확인·지휘 담당의 작업 전달 |
| 공간 분리 | Git worktree | 브랜치별 작업 폴더로 구현·검증 공간 분리 |
| 공통 규칙 | `AGENTS.md` | 역할·담당 범위·기록·보고 기준 공유 |

여기서 하네스는 각 AI가 작업을 진행하고 결과를 주고받을 수 있도록 마련한 환경을 말합니다. 앞서 소개한 도구와 규칙에 더해, 정보를 저장하는 구조와 작업을 전달하고 결과를 합치는 절차도 하네스에 포함됩니다.

### 작업 공간 분리와 통합 책임·공통 규칙을 정한 이유

구현과 검증을 병행하기 위해 각 담당의 브랜치와 작업 공간을 나누기로 했습니다. 그래서 Git worktree를 사용해 같은 저장소를 바탕으로 브랜치별 작업 폴더를 마련하고, 구현은 `.worktrees/impl`, 검증은 `.worktrees/qa`에서 진행하게 했습니다. 여기에 더해 역할별로 담당 파일도 정해, 같은 파일을 동시에 고치는 일을 줄이려고 했습니다.

각 담당의 작업 결과는 하나의 에이전트로 합쳐야 했으므로, 통합 책임은 지휘 담당에게 맡겼습니다. 구현·검증 담당에게 작업을 전달하고 보고를 받은 뒤, 변경 내용을 확인해 병합하고 서버에 반영하도록 했습니다.

작업 전달과 진행 상황 확인에는 Herdr를 사용했습니다. Herdr로 각 AI의 작업 화면과 상태를 한곳에서 볼 수 있었기 때문에, 지휘 담당은 구현·검증 담당이 작업 중인지, 입력을 기다리는지, 승인에서 멈췄는지를 확인할 수 있었습니다.

여러 AI가 함께 움직이는 환경에서는 각 AI가 따를 규칙도 맞춰 둘 필요가 있었습니다. 도구마다 비슷한 지시를 따로 적으면 수정할 때 내용이 어긋날 수 있어, 공통 규칙은 `AGENTS.md`에 모으고 역할 전용 지시는 구분해 관리했습니다.

외부 스킬을 추가할 때도 이 공통 규칙과 충돌하지 않을지 생각해야 했습니다. 대회 직전에 낯선 규칙을 더하기보다는, 필요한 원칙을 공통 규칙에 반영하는 쪽을 택했습니다.

### 규칙 작성 후 실제 작업 흐름을 시험한 이유

규칙을 마련한 뒤에는 각 AI가 실제로 지시를 읽고 작업을 주고받을 수 있는지 확인해야 했습니다. 대회 전에 아래 흐름을 시험하면서, 역할 인식부터 통합·서버 반영까지 이어지는지 살펴봤습니다.

| 확인 대상 | 실제로 해본 일 | 확인하려던 문제 |
| --- | --- | --- |
| 규칙과 역할 | 각 AI가 규칙을 읽고 역할·브랜치·담당 범위를 답하도록 요청 | 지시문이 읽히지 않거나 역할을 혼동하는 상황 |
| 작업 전달과 보고 | 지휘 담당이 작업을 맡기고 결과를 받는 흐름 실행 | 전달 누락, 작업 중단, 보고 형식의 차이 |
| Git·테스트·배포 | 작업 공간에서 변경·테스트를 진행하고 통합·서버 반영까지 확인 | 권한 승인과 통합·실행 단계에서 막히는 지점 |

이 과정에서는 다음 두 문제가 드러났고, 각 도구가 사용하는 경로와 명령 형태에 맞춰 설정을 조정했습니다.

| 실제로 막힌 지점 | 조정한 내용 |
| --- | --- |
| 구현 담당이 사용하는 Git 정보가 작업 폴더 밖에 있어 병합·커밋 때 승인 대기 | 해당 저장소의 Git 정보 경로를 구현 담당의 쓰기 허용 범위에 추가 |
| 검증 담당의 명령 허용 설정이 예상대로 적용되지 않음 | 당시 도구의 명령 전체 일치 방식에 맞춰 고정된 실행 명령과 허용 조건을 정리 |

조정한 환경에서는 구현·검증 담당이 병합·테스트·커밋을 진행하고, 지휘 담당이 결과를 확인해 통합하는 흐름을 다시 시험했습니다. 사전 점검에서 해당 작업이 승인 대기에서 멈추지 않고 이어지는 것을 확인했습니다.

## 3. 하네스의 폴더 구성과 대회 중 작업 흐름

여러 AI가 작업을 이어 가려면 역할과 절차에 더해, 대회 중 얻은 정보를 보관하고 다시 꺼내 쓸 구조도 필요했습니다. 그래서 원문과 인물별 정리, 전체 현황, 에이전트가 참고할 지식을 용도별로 나눴고, 필요한 파일은 대회 중에도 보완했습니다.

### 원문·정리본·실행용 지식을 나눈 폴더 구성

아래는 제가 만든 작업 구조에서 하네스를 설명하는 부분만 간추린 구성입니다. 개별 인물·제공 문서의 파일명과 내용, 문제를 추측할 수 있는 세부 항목은 생략했습니다.

```text
프로젝트/
├─ AGENTS.md
├─ .worktrees/
│  ├─ impl/
│  └─ qa/
├─ docs/contest/
│  ├─ inbox/
│  ├─ interviews/
│  ├─ people/
│  ├─ sources/
│  ├─ overview.md
│  ├─ requirements.md
│  ├─ timeline.md
│  ├─ learnings.md
│  ├─ board.md
│  ├─ log.md
│  └─ handoff/
├─ prompts/
│  ├─ system.md
│  └─ knowledge.md
└─ evals/
   ├─ scenarios.json
   └─ results/
```

정보를 받아 보관하고 정리한 뒤 에이전트가 참고하기까지, 각 단계의 용도에 따라 파일을 나눴습니다.

| 위치 | 용도 | 이렇게 나눈 이유 |
| --- | --- | --- |
| `inbox/` | 제가 넣는 답변과 지휘 담당이 전달할 질문 | 자료를 주고받는 공간과 보존할 기록을 분리 |
| `interviews/`, `sources/` | 질문·답변 원문과 받은 자료 | AI의 요약·해석을 나중에 원문과 대조 |
| `people/` | 인물별 역할·발언·관계 정리 | 누가 무엇을 말했는지 다시 찾는 기준 마련 |
| `overview.md`, `requirements.md`, `timeline.md` | 전체 현황, 요구·미확인 사항·모순, 사건의 연결 | 개별 답변을 연결하고 다음에 확인할 빈칸 파악 |
| `learnings.md` | 진행하며 발견한 질문 요령과 새로 알게 된 내용 | 이후 질문과 작업에서 다시 참고 |
| `prompts/system.md` | 제출 에이전트의 역할·응답 방식·행동 기준 | 에이전트가 어떻게 응답하고 행동할지 지시 |
| `prompts/knowledge.md` | 수집·정리한 지식과 참고 자료를 합친 내용 | 에이전트가 응답할 때 참고할 자료를 한데 모음 |
| `board.md`, `log.md`, `handoff/` | 할 일·담당·상태, 결정 이유, 역할별 결과 보고 | 병행 작업의 진행 상황과 판단 근거 보존 |
| `evals/` | 자체 검증 사례와 실행 결과 | 수정한 동작을 같은 기준으로 다시 확인 |

원문과 정리본, 실행용 자료를 구분하고 인물관계와 새로 발견한 내용을 연결해 두어, 다음 질문을 고르거나 지식을 보완할 때 다시 참고할 수 있는 구조를 마련했습니다. 이런 정보 정리 구조는 이번 준비에서 잘한 부분이라고 생각합니다.

다만 정보가 들어갈 자리를 마련하는 일과 실제 내용을 채우는 일은 달랐습니다. 사전에는 협업과 실행의 기반을 준비했고, 문제를 접한 뒤 답변 원문과 인물관계, 문서 목록, 사건 정리를 추가했습니다. 파일을 만들어 두었어도 필요한 정보가 충분한지는 별도로 확인해야 했습니다.

### 질문·답변이 에이전트의 지식과 구현으로 이어지는 과정

대회 중에는 인터뷰로 얻은 답변을 원문으로 보관하고 지식으로 정리한 뒤, 에이전트의 구현과 검증에 반영하는 흐름으로 운영했습니다. 각 단계의 담당과 결과를 정리하면 다음과 같습니다.

| 단계 | 담당 | 하는 일과 남기는 결과 |
| --- | --- | --- |
| 1. 질문·답변 전달 | 본인 | 질문을 보내고 받은 답변을 전달 공간에 입력 |
| 2. 원문 보관 | 지휘 담당 | 질문·답변을 보존하고 나중에 근거를 찾을 수 있게 정리 |
| 3. 정보 연결·지식 반영 | 지휘 담당 | 인물별 기록·요구사항·새로 배운 내용을 연결하고 실행용 지식 보완 |
| 4. 구현과 자체 검증 | 구현·검증 담당 | 배분받은 기능을 수정하거나 평가 사례를 실행하고 결과 보고 |
| 5. 결과 확인·통합 | 지휘 담당 | 보고를 확인하고 필요한 수정·병합·배포 진행 |

표는 정보가 흘러가는 순서를 정리한 것으로, 실제 대회에서는 여러 작업이 병행됐습니다. 제가 다음 질문과 답변을 주고받는 동안에도 구현과 평가가 이어졌고, 새 정보와 작업 결과를 이후 작업에 반영했습니다.

위 표의 ‘정보 연결·지식 반영’ 단계에서 정리한 내용과 수집 자료를 모아 `prompts/knowledge.md`를 갱신했습니다. 제출 에이전트는 응답할 때마다 이 파일을 다시 읽도록 구성해, 새로 정리한 내용을 다음 응답의 참고 자료로 전달할 수 있었습니다. 원문은 별도로 보관했으므로, 갱신한 지식을 원문과 대조하며 보완할 수 있는 구성이었습니다. 다만 필요한 정보만 검색해 전달하는 방식은 제한 시간 안에 검증하지 못해 적용하지 않았습니다.

이렇게 지식과 코드를 보완할 때는 자체 평가도 함께 진행했습니다. 평가에서 드러난 문제는 구현이나 지시문 수정으로 연결하고, 고친 뒤 다시 확인했습니다.

> **검증 범위**
>
> 여기서 말하는 평가는 정해진 사례와 당시 조건에서 진행한 자체 검증입니다. 주최 측 공식 심사 결과와는 별개이며, 보강한 뒤에도 완전히 해결되지 않은 항목이 남아 있었습니다.

다음에는 이 평가의 범위를 더 분명히 남기려고 합니다. 기능·지식·응답 속도를 구분해 확인하고, 각 평가에 사용한 조건도 함께 기록할 계획입니다.

### 대회 중 바뀐 질문 추천 방식과 남은 병목

처음에는 지휘 담당에게 질문을 여러 개씩 묶어 추천받기로 했지만, 대회 중에는 답변을 받을 때마다 다음 질문을 하나씩 추천받도록 제가 방식을 바꿨습니다. 앞선 답에 맞춰 다음 질문을 조정하기 위해서였습니다.

질문을 보내고 답을 받아 파일에 넣는 일은 계속 제가 맡았습니다. 질문 추천과 구현·평가를 병행하더라도, 그 사이의 자료 전달은 사람이 이어 줘야 했습니다. 이 운영 방식을 돌아보니 전달 과정과 함께, 다음 질문을 고르는 전략도 더 준비할 필요가 있었습니다.

## 4. 질문 탐색의 한계: 진행도·탐색 순서·가설 점검

정보를 기록할 구조는 준비했지만, 무엇을 어떤 순서로 물을지 정하는 전략은 늦게 마련했습니다. 질문 탐색에서 돌아볼 부분은 크게 네 가지였습니다.

| 돌아본 지점 | 당시 부족했던 점 |
| --- | --- |
| 질문 효과 점검 | 진행도 확인을 질문 유형별 효과 비교로 연결하는 일이 늦었음 |
| 탐색 순서 | 다음 질문과 큰 탐색 방향을 당일에 정하려 했음 |
| 답을 얻지 못한 이유 점검 | 표현을 바꾸는 것 외의 조건 가설 준비가 부족했음 |
| 해석과 결정 | AI의 해석이 결정된 사실처럼 제시된 경우가 있었음 |

### 진행도와 질문 유형별 효과를 처음부터 함께 기록하지 못한 점

탐색의 진행도는 어떤 유형의 질문에서 새로운 정보를 얻었는지와 함께 살펴야 했습니다. 진행도를 주기적으로 확인하자는 원칙은 초반에 정해 두었지만, 질문 유형별 효과를 비교하는 표는 대회 중반이 지나 제가 비교 체계를 만들자고 제안한 뒤에야 마련됐습니다.

또 AI가 효과가 있어 보이는 질문을 관찰하고도 바로 탐색 방향을 바꾸지 않은 구간이 있었습니다. 같은 화제를 이어 물었지만 새 정보를 충분히 얻지 못한 기록도 남아 있습니다. 나중에는 제가 정체를 지적하고 전략 수정을 요청한 뒤에야 질문의 방향이 달라졌습니다.

다음에는 이런 정체를 더 일찍 알아차릴 수 있도록 인물별 진행도와 질문의 목적·유형, 확인 시점을 함께 기록하려고 합니다. 이 기록을 바탕으로 진행도 확인 → 정체 판단 → 질문 방식 변경 → 다시 확인까지 작업 절차에 넣고, 변화가 적으면 다른 주제나 접근을 시도할 계획입니다.

이때 여러 질문을 묶어 진행한 구간은 전체 결과로 비교하고, 확인된 변화를 특정 질문 하나의 효과로 단정하지 않으려 합니다.

### 인물관계에서 전체 업무 흐름과 세부 규칙으로 탐색하기

질문의 효과를 점검하는 일과 함께 아쉬웠던 부분은 탐색의 큰 순서였습니다. 다음에 무엇을 물을지도 당일에 정하려 했는데, 큰 탐색 방향을 미리 준비해 두었다면 정보를 얻을 때마다 다음 질문을 고르기가 더 수월하지 않았을까 싶습니다.

다음에 시도해 보고 싶은 순서는 인물관계 → 전체 업무 흐름 → 세부 규칙과 예외입니다. 먼저 누가 누구와 연결되어 있고 어떤 역할을 맡는지, 전체 업무는 어떻게 이어지는지 확인한 뒤 각 단계의 세부 내용으로 좁혀 가는 접근입니다.

탐색 중 새 정보가 나오면 이 순서도 바꿔 가려고 합니다. 세부 내용을 확인하다가 더 알아봐야 할 역할이나 연결이 드러나면, 인물관계와 전체 흐름으로 돌아가 보완하는 방식입니다.

### 답이 막힌 원인 점검과 다음 질문의 선정 기준

탐색 중 원하는 답을 얻지 못했을 때는 질문의 표현과 함께 다른 원인도 살펴봐야 했습니다. 이때 어떤 가능성부터 점검할지 기준을 더 준비해 둘 수 있었다는 아쉬움이 남았습니다.

앞으로 인터뷰를 설계할 때는 답을 얻지 못한 원인을 정보 부족, 질문의 모호함, 추가 확인이 필요한 사항으로 나누어 살펴보려 합니다. 아직 확인하지 못한 내용은 가설로 기록하고, 실제 답변과 자료로 검증한 뒤 작업 기준에 반영하려고 합니다.

질문을 고를 때는 답이 막힌 원인과 함께, 그 답을 어디에 사용할지도 생각해야 했습니다. 실제로 대회 후반에는 구체적인 사실을 더 묻는 데서 나아가, 그 사실을 어떻게 판단하는지와 에이전트가 어떤 도움을 주면 좋은지를 확인하는 쪽으로 질문을 바꿨습니다.

이 경험을 바탕으로, 다음에는 질문을 고를 때 아래 항목을 함께 살펴보려고 합니다.

- 이 질문이 채우려는 정보의 빈칸은 무엇인가.
- 앞선 질문과 달리 새로 확인할 내용이 있는가.
- 상대가 실제로 판단하거나 답할 수 있는 범위인가.
- 답을 얻으면 에이전트의 처리나 사람의 판단이 어떻게 달라지는가.

이 기준이 실제로 질문을 고르는 데 도움이 되는지는 다음 작업에서 기록하고 비교해 보려 합니다.

### 자료의 해석과 결정 권한 구분

어떤 내용을 더 질문해야 할지 정할 때는 AI가 자료에서 찾은 사실과 해석해서 제안한 내용을 구분할 필요도 있었습니다. 해석이 들어간 제안에는 추가 확인이 필요한 부분이 남아 있기 때문입니다. 하지만 당시 작업 기록에는 AI가 근거와 선택지를 먼저 보여 주기 전에, 특정 처리 방식을 이미 결정한 것처럼 제시한 일이 남아 있습니다.

이를 바로잡기 위해 제안된 방식은 잠정안으로 남기고, 선택 이유를 설명한 뒤 결정 권한이 있는 인터뷰 상대에게 확인하는 과정을 거쳤습니다. 확인 후에는 처음 제안과 다른 방향으로 바뀐 결정도 있었습니다.

자료에서 확인한 사실, AI의 해석, 최종 결정은 구분해서 다뤄야 했습니다. AI에게 맡길 범위도 이 구분을 바탕으로 정할 필요가 있었습니다.

## 5. 질문·답변 전달과 운영 점검의 개선 과제

### 질문 전달·답변 수집 자동화의 검토 조건

질문을 고르는 전략에 더해, 질문을 보내고 답변을 옮기는 방식도 개선해 보고 싶습니다. 이 과정은 제가 직접 맡았기 때문에, 도구의 도움을 더 받을 수 있었다면 전달에 쓰는 시간을 줄일 수 있지 않았을까 하는 생각이 들었습니다.

> **자동화 검토의 전제**
>
> 아직 구현하거나 효과를 측정한 내용은 아닙니다. 구체적인 방식을 정하기 전에 대회 규정에서 허용하는 범위를 확인해야 합니다.

자동화로 전달 시간을 줄일 수 있더라도, 질문 수가 늘어난 만큼 필요한 정보를 더 얻을 수 있을지는 따로 확인해야 합니다. 질문 전략까지 함께 개선하며 살펴볼 부분입니다.

### 입력 보존·비용·제출 형식의 사전 점검

실제 운영에서는 전달 파일을 언제 처리할지부터 비용과 제출 형식까지, 기능 구현 외에 맞춰 둬야 할 조건도 있었습니다. 당시 기록에 남은 문제와 다음에 적용할 기준을 정리하면 다음과 같습니다.

| 항목 | 당시 겪은 일 | 다음에 적용할 기준 |
| --- | --- | --- |
| 입력 보존 | 제가 처리 신호를 주기 전에 AI가 답변 전달 파일을 비움. 답은 별도 원문에 보관돼 있었음 | 입력 완료 신호를 받은 뒤 처리하고, 전달 파일을 비우기 전에 보관본 확인 |
| 비용·한도 | 잔액과 토큰 한도를 제출 뒤에 확인 | 대회 시작 전에 비용·한도를 확인하고 운영 점검에 포함 |
| 제출 형식 | 제출용 설명문의 표가 원하는 대로 표시되지 않아 마감 직전 일반 텍스트로 재작성 | 실제 제출 화면에서 미리 형식을 확인하고 텍스트 대안 준비 |

답변 원문은 별도로 남아 있었지만, AI가 전달 파일을 비운 시점은 제가 입력을 마쳤다는 신호를 주기 전이었습니다. 이후에는 입력 완료 신호를 받은 뒤 처리하고 보관본을 남기는 규칙을 추가했습니다. 입력한 내용을 보존하려면 저장 위치에 더해, 사람이 입력을 마치고 AI가 처리하는 순서도 맞춰야 했습니다.

잔액과 토큰 한도를 확인한 시점은 제출 뒤였습니다. 정리한 지식을 프롬프트에 함께 넣는 방식이었고 심사 중에도 에이전트가 계속 동작해야 했으므로, 다음에는 대회 시작 전에 확인하고 운영 중에도 점검할 항목으로 두려고 합니다.

기능 구현 일정에는 제출 준비에 쓸 시간도 포함하려고 합니다. 기능 구현을 멈출 시각과 제출 준비를 시작할 시각을 미리 정해 두고, 설명문이 실제 제출 화면에서도 원하는 형식으로 보이는지 확인할 계획입니다.

## 6. 다음 참가 때 바꿀 준비와 운영 기준

이번 대회에서 유지하고 싶은 부분은 인물관계와 새로 발견한 내용을 연결하고, 필요할 때 원문을 다시 확인할 수 있게 만든 정보 정리 구조입니다. 여러 AI가 함께 작업하도록 역할과 공간을 나누고, 작업 전달부터 통합까지 미리 시험하는 방식도 다음 작업에 이어 가려고 합니다.

다음에는 정보를 정리하는 구조와 함께, 질문을 고르는 전략도 더 일찍 준비해 보려 합니다. 질문의 큰 순서를 정하고, 탐색이 정체됐다는 신호를 알아차려 접근을 바꾸는 절차까지 마련하려고 합니다. 전달 과정과 운영 점검도 함께 보완해, 제 AI 활용 능력을 시험해 보겠다는 참가 동기를 다음 작업 환경의 개선으로 이어 가고 싶습니다.
