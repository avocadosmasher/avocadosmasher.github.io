프로젝트를 새로 만들거나 작업 환경을 옮길 때마다, 직접 만든 스킬과 자주 쓰는 스킬을 다시 설치해야 했습니다. 프로젝트마다 따로 설정하다 보니 번거로웠고, 전에 어떤 스킬을 썼는지 기억나지 않는 경우도 있었습니다.

직접 써 보고 괜찮다고 생각한 스킬인데, 정작 다시 필요해졌을 때 무엇을 썼는지부터 찾아야 하는 상황이 생기는 거죠.

그래서 사용해 보고 만족한 스킬과 제가 만들어 쓰는 스킬을 한곳에 모아 두기로 했습니다. 필요할 때 다시 꺼내 쓸 수 있는 제 스킬 보관소, [skill-storage](https://github.com/avocadosmasher/skill-storage)를 만든 이유입니다. 만들 때는 모아 둔 스킬 중 필요한 것만 골라 설치하고 싶었고, 다른 사람에게도 공유하고 싶었습니다. 그런데 실제로 운영할 구조를 정하려니 스킬을 어디에 넣을지뿐 아니라, 어떤 단위로 배포할지와 외부 스킬을 어떻게 구분할지도 정해야 했습니다.

이번 글에서는 저장소를 만든 계기부터 배포·설치 구조를 선택한 이유, 환경에 맞게 조정할 부분, 앞으로 운영하고 싶은 방향까지 정리해 보겠습니다. 현재 구성에 관한 설명은 **skill-storage 1.10.0**, 커밋 `567835c`를 기준으로 합니다. [기준 버전](https://github.com/avocadosmasher/skill-storage/blob/567835c5bc8e0ab859ef83a2826356124e30a2c6/.claude-plugin/plugin.json)

## 1. 스킬의 구성과 skill-storage의 보관 대상

우선 여기서 말하는 스킬이 무엇인지 짧게 짚고 가겠습니다.

Agent Skills에서 스킬의 기본 단위는 `SKILL.md`를 담은 폴더입니다. 이 파일에는 스킬의 이름과 설명, 특정 작업을 어떻게 수행할지에 관한 지시가 들어갑니다. 필요하면 실행할 스크립트, 참고 문서, 템플릿 같은 자료도 함께 묶을 수 있죠. [Agent Skills 공식 설명](https://agentskills.io/home)

예를 들어 블로그 글쓰기 스킬이라면 "친근하게 써줘"라는 문장에 더해, 자료를 먼저 읽는 순서, 글쓴이가 전달해주지 않은 내용들은 어떻게 할지, 문체를 적용하는 기준 등을 함께 보관할 수 있습니다. AI가 읽을 절차와 그 절차를 수행하는 데 필요한 자료를 하나의 폴더에 담는 셈입니다.

한마디로, 어떤 스킬을 썼는지 기억에만 의존하기보다, 사용해 보고 남길 만하다고 판단한 것을 한곳에 저장해서 나중에 다시 찾을 수 있게 하고 더 나아가 사용하기 위한 준비까지 도와주도록 하고 싶었던거죠.

그렇다고 저장소 안의 모든 스킬을 제가 처음부터 만들었나? 그건 또 아닙니다. 직접 만든 것뿐만 아니라 다른 사람의 스킬을 바탕으로 개선한 것, 외부 스킬을 들여온 것들을 함께 보관하고 있습니다.

"단순히 내가 만든 스킬을 모아놓은 저장소" 보다는 "내가 즐겨 사용하는 스킬들이 모여있는 저장소"를 만들고 싶었던거죠

| 저장하는 방식 | 현재 저장소에서 볼 수 있는 예 |
| --- | --- |
| 필요한 작업 방식을 직접 정리 | 저의 글쓰기 스타일을 본떠서 만든 블로그 글쓰기 방식인 `thinking-aloud-writing` |
| 외부 스킬을 바탕으로 개선 | Matt Pocock의 `grill-me`를 바탕으로 한 `grill-me-plus` |
| 외부 스킬 패키지 도입 | `archify`, `find-skills`, `eli5` |

`grill-me-plus`의 CREDITS에는 원본에서 가져온 부분과 추가한 규칙이 나뉘어 있고, 외부에서 가져온 스킬에도 출처와 도입 범위가 기록돼 있습니다. 저장소에 들어 있다는 사실과 제가 만든 부분은 구분해서 설명해 원작자의 저작권을 해치지 않도록 했습니다. [grill-me-plus 출처](https://github.com/avocadosmasher/skill-storage/blob/567835c5bc8e0ab859ef83a2826356124e30a2c6/skills/productivity/grill-me-plus/CREDITS.md), [archify 도입 범위](https://github.com/avocadosmasher/skill-storage/blob/567835c5bc8e0ab859ef83a2826356124e30a2c6/skills/engineering/archify/CREDITS.md), [find-skills 출처](https://github.com/avocadosmasher/skill-storage/blob/567835c5bc8e0ab859ef83a2826356124e30a2c6/skills/engineering/find-skills/CREDITS.md), [eli5 출처](https://github.com/avocadosmasher/skill-storage/blob/567835c5bc8e0ab859ef83a2826356124e30a2c6/skills/productivity/eli5/CREDITS.md)

## 2. 플러그인 배포 구조와 스킬 설치 방식

처음 의도만 보면 워크플로우마다 플러그인을 하나씩 만들면 될 것 같습니다. 그런데 스킬이 늘어나고 워크플로우도 그만큼 늘어나면, 환경을 옮길 때마다 플러그인을 하나하나 찾아서 설치하고 하는? 설정이 번거롭다는 초기의 문제를 다시 만나게 됩니다.

> 여기서 워크 플로우는 사용자의 사용 시나리오별로 묶은 스킬 셋입니다. 예를들어 idea-banking으로 아이디어를 수집하고 gated-tdd로 개발을 하니까 이 두개가 묶어서 하나의 사용 시나리오인거죠.

저장소의 초기 구조도 함께 쓰는 스킬을 여러 플러그인으로 묶는 형태였습니다. 이후에는 정식 공개 스킬을 `skill-storage`라는 플러그인 하나로 배포하는 구조를 선택했습니다. 사용자는 묶음을 한 번 설치하고, 스킬을 추가하는 쪽에서는 공개 목록과 배포 목록을 함께 관리하는 방식입니다. [배포 구조 결정 기록](https://github.com/avocadosmasher/skill-storage/blob/567835c5bc8e0ab859ef83a2826356124e30a2c6/.agents/adr/0001-single-plugin-bucket-layout.md)

그럼 다음과 같은 경우들은 어떻게 되는 걸까요?

### 설치 경로별 선택 단위: 플러그인·skills.sh·폴더 복사

우선 현재는 플러그인의 스킬들의 적용 범위, 관리 방식에 따라 설치 경로 방식을 다르게 하여 구분할 수 있도록 하였습니다.

| 설치 경로 | 선택하는 단위 | 적합한 목적 |
| --- | --- | --- |
| `skill-storage` 플러그인 | 정식 공개 스킬 묶음 | 모음을 설치하고 배포 버전의 업데이트를 받아 쓰기 |
| `skills.sh`의 설치 CLI | 개별 스킬 선택 가능 | 필요한 스킬을 골라 프로젝트에 설치하기 |
| 스킬 폴더 직접 복사 | 개별 폴더와 포함 자료 | 가져온 사본을 직접 관리하고 고쳐 쓰기 |

즉, 현재 플러그인은 항상 스킬마다 설치 여부를 따로 고르는 구조가 아닙니다. 필요한 스킬만 선택하려면 `skills.sh` 경로를 이용하거나 해당 스킬 폴더를 가져와야 합니다. 이렇게 함으로써 사용자가 원하는 사용 방식과 설치 단위를 구분해 혼동이 줄어들도록 하였습니다. [저장소의 설치 안내](https://github.com/avocadosmasher/skill-storage/blob/567835c5bc8e0ab859ef83a2826356124e30a2c6/README.md#설치)

예를 들어 `skills.sh`의 CLI에서 `grill-me-plus`를 지정하는 명령은 다음과 같습니다.

```bash
npx skills@latest add avocadosmasher/skill-storage --skill grill-me-plus
```

실행할 프로젝트와 설치 대상 에이전트는 자신의 환경에 맞게 선택하면 됩니다. 현재 CLI의 설치 대상·옵션은 [skills 공식 안내](https://github.com/vercel-labs/skills#install-a-skill)에서 확인할 수 있습니다.

### 워크플로우별 구성의 현재 상태와 향후 분리 조건

사실 워크 플로우의 경우 현재는 아직 제가 가진 스킬셋이 많지 않고 서로 충돌하는 경우가 없어 현재 구조로도 굳이 워크 플로우별로 나눌 필요는 없는듯? 싶습니다. 하지만 이 부분은 사용하는 워크플로우가 늘어나고 그에 따른 사용하는 스킬 구성들이 나뉘고?

이렇게 구분함으로써 충돌을 막을 수 있다면 추후에 워크 플로우별로 스킬셋을 나눠서 저장하는 구조로 개선하려고 계획중입니다.

## 3. 저장소 디렉터리 구조와 mod의 별도 배포

설치 방법만 정하면 구조가 끝날까요? 스킬을 보조하는 기능까지 들어오면서 구분할 것이 하나 더 생겼습니다.

현재 저장소에는 `idea-banking`으로 저장한 아이디어를 패널에서 살펴보는 `idea-bank-viewer` 같은 보조 기능도 있습니다. 이런 Claude Code용 함수 훅 플러그인을 mod라고 부릅니다.

이 mod는 스킬과 별도로 설치합니다. 예를 들어 `skill-storage`를 설치했다고 아이디어 패널까지 자동으로 설치되지는 않습니다. 스킬의 절차를 읽어 쓰는 것과, 세션에서 파일을 읽는 보조 기능을 추가하는 것은 선택할 범위가 다르기 때문입니다. mod는 별도 플러그인으로 등록하고 버전도 독립적으로 관리하도록 정했습니다. [mod 분리 결정 기록](https://github.com/avocadosmasher/skill-storage/blob/567835c5bc8e0ab859ef83a2826356124e30a2c6/.agents/adr/0002-optional-mods-as-separate-plugins.md)

현재의 구조를 간단히 보면 다음과 같습니다.

```text
skill-storage/
  skills/
    engineering/     정식 공개하는 코드 작업 스킬
    productivity/    정식 공개하는 그 밖의 작업 스킬
    in-progress/     베타, 정식 플러그인 묶음에서 제외
    misc/            보관용, 공개 목록에서 제외
    deprecated/      더 사용하지 않는 스킬 분류
  mods/              별도로 선택 설치하는 보조 플러그인
  docs/              사람이 읽는 스킬 사용 안내
  .claude-plugin/    배포할 스킬·플러그인 목록
  .agents/           저장소 운영 규칙과 설계 결정
```

`engineering`과 `productivity`에 있는 정식 스킬은 설명 문서와 플러그인 목록에도 등록합니다. 베타나 보관용으로 분류한 스킬은 정식 묶음에 넣지 않습니다. 여기서 ‘목록에서 제외’는 비공개 저장 공간이라는 뜻이 아닙니다. 공개 Git 저장소 안의 파일에 비밀 정보를 보관하는 구분으로 쓰는게 아니라는 점. [현재 운영 규칙](https://github.com/avocadosmasher/skill-storage/blob/567835c5bc8e0ab859ef83a2826356124e30a2c6/AGENTS.md)

이 구조에는 관리할 목록이 여러 군데라는 애로 사항도 있습니다. 스킬을 하나 추가할 때 해당 폴더만 만들고 끝내면 설명 목록이나 배포 목록에서 빠질 수 있으므로, 등록할 위치를 운영 규칙으로 함께 정해 두었습니다.(어차피 관리를 AI를 사용해서 하기 때문이지요 호호)

### 부록: mod의 실행 권한과 설치 전 확인 사항

mod를 별도로 구분해 놓은 이유는 혹~시나 만약에 제 플러그인을 사용하시는 분들이 mod 설치를 꺼려하실 수 있으니 구분해 놓았습니다. mod는 Claude 공식에서도 언급했지만, 약간 위험할 수 있는 기능입니다.

Claude Code의 mod는 샌드박스(Sandbox) 없이 사용자의 컴퓨터 권한을 그대로 이어받아 실행하기 때문이지요.

여기서 자세히 다루지는 않고 간단하게만 살펴보면 다음과 같은 일들을 mod가 할 수 있기 때문이라고 합니다.

1. 사용자 계정이 읽을 수 있는 파일과 환경 변수·설정 파일의 API 키 등에 접근
2. 세션의 프롬프트와 도구 호출 읽기
3. 프롬프트·도구 호출 변경 및 조건에 따른 도구 호출 사전 승인
4. 프로그램 실행과 네트워크 요청

다만 승인 창에 표시되는 내용 자체를 바꾸는 것은 허용되지 않으며, 관리형 설정이나 조직 계정 정책에 따라 사전 승인에도 제약이 있습니다. 설치 전에는 `claude plugin validate`로 mod가 처리하는 이벤트와 호출 목록을 확인할 수 있습니다.

그러니 사용에 주의해야하고 특히, 남이 만든 mod는 악의적인 동작을 하도록 하는 기능이 들어가있을 수 있으니 검사를 철저히 해야합니다.

이러한 경고는 [Anthropic 공식](https://code.claude.com/docs/en/plugins/mods/overview#decide-whether-to-trust-a-mod)에서도 언급을 하고 있으니 더 주의해야합니다.

## 4. 프로젝트 환경에 맞춘 스킬·하네스 조정

저는 스킬과 하네스가 개인과 조직의 작업 방식에 맞게 다듬어져야 한다고 생각합니다. 여기서 하네스는 에이전트가 사용할 도구와 권한, 실행 환경, 훅처럼 작업을 둘러싼 구성을 가리키는 뜻으로 쓰겠습니다.

같은 스킬이라도 프로젝트에 이미 있는 규칙과 만나면 조정할 부분이 생깁니다. 예를 들어 독립적으로는 결정을 `DECISIONS.md`에 기록하는 스킬이, 다른 개발 절차 안에서는 기존 결정 문서와 역할이 겹칠 수 있습니다.

실제로 `gated-tdd`의 설계 기록에는 `grill-me-plus`와 함께 쓸 때 결정을 기존 계획·요구·결정 문서에 남기도록 연결한 내용이 있습니다. Git 훅을 이미 사용하는 프로젝트에서는 기존 훅의 자리를 덮어쓰지 않고 이어 붙이도록 바꾼 결정도 있습니다. 스킬 하나가 잘 작성됐는지와 여러 도구가 함께 동작하는지는 따로 살펴야 하는 것입니다. [다른 도구·스킬과의 공존 결정](https://github.com/avocadosmasher/skill-storage/blob/567835c5bc8e0ab859ef83a2826356124e30a2c6/.agents/design/gated-tdd/022-coexistence-and-parallel-branches.md)

이 블로그에는 현재 변경에 대한 명시적인 통과 뒤 커밋·push하도록 정한 규칙이 적용돼 있습니다. 공개 스킬의 최신 절차와 프로젝트에 이미 적용한 규칙은 각각 확인해야 합니다.

스킬에 적힌 지시와 자동 장치의 검사 범위도 구분해야 합니다. 읽기 쉬운 글인지, 사실관계가 정확한지, 사용자가 실제로 판단했는지까지 Git 훅 하나가 모두 확인할 수는 없습니다. 필요한 부분은 코드와 검사로 확인하고, 내용과 의도처럼 사람이 판단할 부분은 남겨 두어야 합니다.

새 환경에 가져간 뒤에는 스킬이 요구하는 도구와 경로, 기존 프로젝트 규칙, 다른 스킬과의 기록 위치를 확인하려고 합니다. 설치 명령을 줄이는 것과 환경마다 필요한 검토가 사라지는 것은 다른 문제이기 때문입니다.

## 5. 운영 방향: 스킬 검증·개선·제작과 공유

skill-storage의 시작은 단순히 프로젝트마다 반복하던 설정을 줄이고, 써 보고 좋았던 스킬을 다시 찾기 위해 시작했지만 앞으로는 제 작업 방식에 맞게 개선해 나가는 과정을 담아가고자 합니다.

앞으로도 새로운 스킬을 만나면 직접 써 보고, 쓸 만한 것은 라이선스 조건을 확인한 뒤 출처와 함께 추가하고 필요하면 수정해서 저에게 맞춰갈 생각입니다.

또한 앞서 살펴본 `grill-me-plus`의 출처 기록처럼, 가져온 부분과 바꾼 부분을 구분하면 나중에도 어떤 필요 때문에 고쳤는지 살펴볼수 있으니 출처 기록과 변경 사유도 같이 남기면서 말이지요.

좋은 스킬에서 배울 점을 찾는 것만큼, 제 환경에서 무엇이 맞지 않는지 확인하는 일도 중요하다고 생각합니다. 그렇게 다른 사람이 만든 스킬의 장점을 흡수하고, 제 스킬은 더 발전시키고, 필요한 것은 직접 만들어 가려고 합니다.

그렇게 제게 맞는 도구를 쌓아 가다, 언젠가는 다른 사람도 이 저장소를 찾아와 자신의 작업에 가져다 쓰고 싶어 하는 스킬을 만날 수 있었으면 합니다.
