AI Agent
목표를 이루기 위해서 계획하고, 생각하고, 필요한 도구를 호출찾아서 호출하고 다시 고치는 과정을 반복하며 AI가 스스로 목표를 향해 나아가는 것



rpa vs AI Agent
추론, 사고, 판단 이 필요하면 AI Agent가 더 효율적
단순 반복, 결과와 해결 방법이 명확하다면(a.k.a 노가다) rpa가 효율적

오버 엔지니어링은 X. 문제와 상황에 따라서 적절한 방안을 선택하는 것은 엔지니어의 역량.

AI가 생각하는 최고의 결과와 사람이 생각하는 최고의 결과가 다르고
사람이 생각하는 최고의 결과도 사바사이고 상황에 따라 뭐가 베스트인지가 바뀌기 때문.
온톨로지가 중요한거 아닐까. 내가 생각하는 가치를 AI가 잘 따라오도록 해야함.

실패 케이스가 중요한 이유
결과 판단의 근거로써 Agent의 다음 행동을 정하고 반복을 통해 올바른 방향으로 개선하기 위해서 중요.


```plain_text
1. AI Agent 설계
	단일 종목 분석을 통해 매수/보유/매도 의견을 알려주는 AI Agent.
1-1 내가 원하는 목표를 작성
	시장의 상황, 종목 관련 뉴스, 국제적 뉴스, 유사 종목의 평균 PER, 한 달 내에 있었던
	증권사의 의견을 기준으로 해당 종목의 현재 가격을 기준으로 매수/보유/매도 판단을 해주기
2. 목표를 이루기 위한 tool 2개 이름만 작성
	pos_neg_decide : 해당 종목과 관련된 뉴스를 기준으로
					시장, 개별 종목, 국제 뉴스, 증권사 보고서 조사 후 긍정/중립/부정 제시
	avg_per_calc : 유사 종목의 평균 PER을 계산하여 현재 해당 종목의 PER대비
					   어느정도 이격이 있는지 파악
2-1 tool의 spec . 입력 출력 실패 기준 작성
	news_collectors
		- 입력 : 뉴스 내용
	avg_per_calc
		- 입력 : 유사 종목 per, 현재 종목의 per
3. 최종 응답형식 예상
	하이닉스는 현재 per이 30배로 업계 평균인 20배에 비해 높은 상태입니다.
	하지만 최근 반도체 가격 인상을 예상한 forward per을 생각했을 때 주가 상승의 여력이
	있습니다. 또한 최근 하이닉스 ADR 상장으로 인한 시장의 기대감 및 상호전환의 가능성으로
	주가 상승의 여력이 추가적으로 확인되었기에
	매수 의견을 제시합니다.  
```

## 5. 시스템 아키텍처 (Architecture)

### 5.1 전체 구조도

```
[사용자] → [인터페이스(웹/CLI/Slack 등)] → [Agent Core(LLM)]
                                              ├─ Tool 1
                                              ├─ Tool 2
                                              └─ Memory / RAG
```

> 다이어그램으로 대체 가능 (draw.io, mermaid 등)

### 5.2 기술 스택

|구성 요소|선택|선택 이유|

|LLM 모델|(예: Claude Sonnet, GPT-4o)|비용/성능/한국어 품질 등|
|Agent 프레임워크|(예: LangGraph, OpenAI SDK, 직접 구현)||
|인터페이스|(예: Streamlit, FastAPI, Slack Bot)||
|배포 환경|(예: 로컬, Docker, 클라우드)||

## 9. 대화 흐름 & 상태 관리 (Flow & State)

### 9.1 정상 흐름 (Happy Path)

```
1. 사용자 요청 수신
2. 의도 파악 → 도구 선택
3. 도구 실행 → 결과 검증
4. 최종 응답 생성
```

### 9.2 분기 처리

- 요청이 모호할 때: (예: 되묻기 기준)
- 여러 도구가 필요할 때: (순차/병렬 실행 전략)
- 최대 반복 횟수(loop limit): (예: 도구 호출 최대 5회 — 무한 루프 방지)

---

## 10. 오류 처리 & 엣지 케이스 (Error Handling)

|상황|대응 방법|
|---|---|
|도구/API 호출 실패|(예: 1회 재시도 후 사용자에게 안내)|
|LLM이 잘못된 형식으로 응답|(예: 파싱 실패 시 재요청)|
|사용자가 범위 밖 요청|(예: 할 수 없는 이유 + 대안 안내)|
|할루시네이션 위험|(예: 출처 없는 답변 금지, 도구 결과 기반 응답만)|

---

## 11. 안전성 & 가드레일 (Safety & Guardrails)

- **금지 행동**: Agent가 절대 하면 안 되는 것 (예: 데이터 삭제, 임의 결제)
- **권한 최소화**: 각 도구에 꼭 필요한 권한만 부여했는가?
- **프롬프트 인젝션 대비**: 외부 데이터(웹, 문서)에 포함된 지시문을 따르지 않도록 설계했는가?
- **비용 상한**: 요청당 최대 토큰/도구 호출 횟수 제한
